### C6 详细说明（重复提交判幂等成功）

用户第一次借 222 成功 → 又说"帮我借周三下午 222" → 系统查证发现预约 #118 已存在 → 回复"您此前已提交过（预约 #118），无需重复提交"，终态 DONE。

**不判 REJECTED**，因为事情已经办成了。判 REJECTED 会让用户以为"没办成"，而实际上库里有一条有效记录。

### C8 详细说明（时段重叠是否含边界）

预约 A 是 13:00–14:00，预约 B 是 14:00–15:00。

- **不含边界**：不算重叠（A 结束时 B 才开始，两人不会同时在教室）
- **含边界**：算重叠（14:00 这个时刻同时属于两个预约）

需实测存量系统怎么判，然后向它对齐。**不能我们自己定一套**，否则会出现"我们说能借、存量系统说冲突"的不一致。

### C14 详细说明（未登记业务码进查证）

调用返回 `code 450`（规则表里没登记过这个业务码）→ 不直接判成功或失败 → 先查证库里到底有没有这条记录 → 查证也查不清才落 UNRESOLVED。

**不能直接判失败**：因为 `code 450` 可能是"服务端处理了但返回了一个我们不认识的码"，此时记录可能已经存在。直接判失败→重试→可能重复写入。

### C5 详细说明（安全阈值）

查证时拉全量预约列表做内存比对。如果列表超过 500 条：

- 继续逐条比对 → 可能因为数据量太大而漏判（比对逻辑有 bug 或超时）
- **直接判"查不清"转人工** → 保守，不猜

阈值 500 是初始值，需实测确认（取决于存量系统的数据量和比对性能）。

### D7 详细说明（最关键决策：增加多步写入场景）

**问题**：当前主链路（借一间教室）只有一个写入步骤，补偿机制永远不会被触发。第 09 章 D5 实验（补偿失败登记）无法执行。

**决策：方案 B——增加同身份的第二步写入。**

做法：让"一次借两间教室"成为合法输入。用户说"帮我借周三下午 222 和 123" → 系统依次提交 → 222 成功 → 123 失败 → 补偿撤销 222。

**为什么选 B 不选其他**：

| 方案 | 评价 |
|---|---|
| A 不动 | 补偿只能讲设计，拿不出运行证据 |
| **B 同身份第二步** | **不新增接口、不试探禁令、不伪造业务**，只是让"用户一次说两件事"成为合法输入 |
| C 跨身份第二步（教室+座位） | 业务语义怪（既订整间又订座位），且身份变复杂 |
| D 故障注入制造第二步失败 | 需要先有第二步，且注入制造的是"响应丢失"不是"真实失败" |

**前置条件**：意图计划需支持"一个意图含多个资源目标"；降级与补偿的交互需理清（第一间被占时是降级换教室还是判定整个请求失败并补偿）。

**★ 一审回填（2026-09-25）**：上述两项前置条件已理清——
- **降级与补偿的交互**：**降级优先于补偿**（第 07 章 C2"任务不会再继续才补偿"的直接推论）。第二间失败且降级穷尽时，才撤销已成功的第一间；
- **多资源场景的结构落点**：见第 04 章 §5.8（运行 = 单资源生命周期，编排层组合多次运行，补偿清单跨运行共享；不新增状态、不新增 `SUBMITTING` 入边，8 条自检不受影响）。

**影响**：D5 实验可执行；第 12 章演示分镜可增加补偿一幕（是否增补属演示设计待决，见第 12 章一审注）。

### F1 详细说明（注入粒度）

**按"接口 + 第 N 次调用"**，而不是"接口 + 全部调用"。

例子：指定"第 1 次调用 `edu.reservation.classroom.create` 时丢弃响应"。这样能精确复现"第一次提交成功、响应丢失"这一半成功场景。

若按"接口 + 全部调用"，则每次调用都丢响应，无法复现"第一次成功、第二次正常"的场景，也无法复现"查证时正常、提交时丢失"的场景。

### 10.1 三审实测回填（2026-09-25，复位基线上的真实调用 + 源码核对）

> 以下条目已在三审中实测钉死，**原"倾向"被实测结论替换**；详录见变更记录《2026-09-25-架构三审-开工Gate关闭与实测回填》。

| 条目 | 实测结论（决策列回填） |
|---|---|
| **J3** 预约有效状态集合与类型过滤 | **有效状态 = 仅 `ACTIVE`**。枚举只有 `ACTIVE/CANCELLED/EXPIRED`：`EXPIRED` 由定时任务（每 60s）将 `end_time` 已过的 ACTIVE 置位；主动撤销/管理员取消/爽约取消置 `CANCELLED`。`GET /admin/reservations` 无参返回**全部状态、全部类型**记录（复位基线 86 条 = CLASSROOM 23 + SEAT 63；ACTIVE 0），已撤销记录**留存**；`GET /reservations`（mine）**只返 ACTIVE**（另有 `/reservations/history` 返非 ACTIVE，不纳管）。**教室级占用谓词**：`status='ACTIVE' AND start_time<申请end AND end_time>申请start`，CLASSROOM 行按 `resource_id`、SEAT 行按 `classroom_id`（SEAT 行 100% 带 classroom_id），与存量冲突检测 SQL 完全对齐。`keyword` 为 `user_id/resource_id/reason` 三字段 CAST 模糊匹配（`keyword=4` 实测命中 16 条），禁止精确过滤 |

| **D10** 撤销接口返回码 | 不可撤销一律 **`HTTP 200 + code 400`**：`end_time` 已过 → "历史预约不能取消"，已撤销 → "该预约已取消"（实测两者均 400）；仅并发状态竞争才返 `code 409`；记录不存在返 **`code 404`**。补偿收到 400 → 按 `recordId` 查证，记录为 CANCELLED/EXPIRED 即判"撤销已生效"（第 06 章 §8.1 谓词覆盖）；查不清 → 三级处置 |
| **C19** 节次与钟点 | **存量系统无节次表/节次枚举**，预约时间是自由 `OffsetDateTime` 区间；前端仅统计页有"上午 7–12 / 下午 12–18 / 晚上 18–22"口径，可预约时段配置为 07:00–22:30。**归一化采用三段区间**（具体值见 K2 三审结论） |
