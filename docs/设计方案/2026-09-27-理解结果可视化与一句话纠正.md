## 一、问题与目标

**现状事实**（已核验，含修订订正）：

1. 理解层输出 `{ intent, slots, confidence, status, clarifyQuestion, reasoning, candidates }`，
   `status` 有**三种**：`ok` / `clarify` / `out-of-domain`（`understanding.js:86-101`）；
   `slots` 存**用户原话片段**（如 `{ classroomName: '数智楼222', datePhrase: '下周三', timeSegment: '下午' }`）。
   槽位中文名的公开入口是 `getGlossary().slots`（`config-store.js:60`；`:164` 的 `slotLabels` 只是启动校验的局部变量，不是导出）。
2. **理解结果已在事件流里、且默认可见**（修订订正 §一.2 原判断错误）：
   - `chat-bridge.js:55-66` 已在 P1 发 `decide:understand` 决策，文案由 `#understandSummary`（`:284`）生成：
     「识别为「借教室」；条件：教室=数智楼222、日期=下周三、时间=下午」；
   - `useThinking.js:85` 把 P1 的 `decision` 收进 L2（焦点行），`:125` 强制 `focus = true`（**永远可见**），`:133` 它同时进 L3 明细、计 1 步。
   - 所以真正缺失的只有**结构化载荷**（`intentId` / `slots` 数组 / `confidence` 不下发）与**卡片化呈现/纠正交互**。
3. 前端助手侧内容一律由事件派生（§6.1）；`ChatPane` 渲染：用户消息 → ThinkingBlock（思考过程，L2 首行即理解摘要）→
   澄清追问 → AnswerBubble（结论）。
4. 引擎可复用的能力：**取消**（写请求发出前 `CANCELABLE`，P3+ 拒绝）、**对话延续与补偿**（"那改成周四"带会话记忆重新理解；改期/降级走"退旧办新"，P5 恢复阶段）。
5. 前端事实：`task.js:106` `canCancel` 在**挂起态也返回 true**（改口判据必须排除，见 B2）；`ChatPane.vue:63 send()` **无 pending 守卫**、
   `Composer.vue:53` 回车直接 `emit('send')`——运行中按回车已是"并发起第二个任务"的洞（B3 顺带修）。

**目标**：

- 每次理解成功（槽位齐备、即将执行）后，对话流里亮出**人话理解卡**："我理解成：借教室 · 下周三 · 下午 · 数智楼222"。
- 用户发现理解不对，**一句话纠正**：写入前无损中止重来；写入后自然流入下一条对话，走既有"退旧办新"补偿。
- 普通用户路径不变：只跟对话框说话，不引入任何表单；调试入口保持开发者定位。

## 二、设计（分三层）

### 1. 引擎：扩展 `decision:understand` 载荷（不新增事件类型）

- **承接展示的数据源**：把结构化字段并入既有 `decide:understand` 决策条目，事件流 `decision` 事件透传：

```json
{
  "seq": 12, "taskId": "T-…", "type": "decision", "phase": "P1",
  "status": "done", "evidenceRef": "T-…:12", "at": "…",
  "text": "识别为「借教室」；条件：教室=数智楼222、日期=下周三、时间=下午",
  "intentId": "borrow-classroom",
  "intentName": "借教室",
  "slots": [
    { "key": "classroomName", "label": "教室", "value": "数智楼222" },
    { "key": "datePhrase",    "label": "日期", "value": "下周三" },
    { "key": "timeSegment",   "label": "时间", "value": "下午" }
  ],
  "confidence": 0.92
}
```

- **生成时机移到合并之后**（B7）：现状 `#decide(decide:understand)` 在 `chat-bridge.js:55` 发出，
  早于 `:86` 的 `taskContext.slots = { ...taskContext.slots, ...understanding.slots }` 合并。
  修订：**合并之后**再生成 summary 与结构化载荷——展示的是"即将执行"的那份（跨追问轮累积后），
  不是本轮单抽的。`confidence` 取最后一次理解的值。
- **中文化在引擎做**：`#understandSummary` 扩展出结构化版（`intentName` + `slots` 的 label/value 数组），
  label 取 `getGlossary().slots`、value 是原话片段。**text 与 slots 用同一份格式化逻辑，不另起第二套**（修订订正）。
- **澄清/越界不发结构化载荷**：`clarify` / `out-of-domain` 路径维持现状（`input-required` 追问、REJECTED 终态），不动。
- **登记**：不新增 type → 三处闭集（对外接口清单 §四 / `access.test.mjs:300` / `sse.js:14`）**都不用改 type 集合**；
  但接口清单 §四 `decision` 行补一句"理解决策带结构化载荷（intentName/slots/confidence）"登记（走变更记录）。

### 2. 前端：理解卡承接展示，"谁承接、谁退场"（B1）

- **承接**：新组件 `frontend/src/components/UnderstandingCard.vue`，插在 ChatPane 用户消息之后、ThinkingBlock 之前；
  从 `turn.events` 里 P1 的 `decision` 事件（带 `intentName`）派生——遵守 §6.1 不自行推断。
  卡片形态：浅色底（`--surface-2`/细边框）、小圆角；首行"我理解成："+ 意图中文名；槽位 chip（`label: value`）；
  右下角**改一下**按钮（行为见 §2.3）。
- **退场**：`useThinking.js:125` 对 P1 decision 的强制 `focus = true` 取消——理解摘要由消息流卡片承接展示，
  L2 焦点行退为普通明细（`focus` 不再强制；`details` 计数与步数**不变**，decision 仍计 1 步）。
  **同步修改**界面方案 §三/§四 层级表与 `useThinking.js:8,31` 注释（避免"两份真相"）。
  ⚠️ 改 `useThinking.js` 前先跑 `cd frontend && npm test`（AGENTS.md）。

### 3. 纠正交互（复用既有能力，引擎零新增控制通道）

- **触发点与判据（B2/B3）**：拦截落在 `ChatPane.send()`——**覆盖回车路径**（`Composer` 回车直接 `emit('send')`，
  光禁用发送按钮挡不住）。判据严格限定：
  `turn.status === 'running' && !turn.writeIssued`（即 P3 前）。
  **显式排除 `suspended`**：挂起态输入是追问回复（`ChatPane.vue:68` 走 `store.reply`），**不接管**，保持既有链路。
  顺带修现状洞：`send()` 增加 `pending` 守卫（`taskStatus === 'running'` 时忽略新输入，杜绝"运行中回车并发第二个任务"）。
- **写入前改口（running && !writeIssued）**：① `apiCancel` 原任务；② 原轮进入**改口中**态（UI：思考过程折叠、
  顶部提示"正在按你的新说法重来…"、输入区锁定不接受新输入）；③ **等原轮终态事件到达**（B4：不靠轮询兜底）——
  `settleCancelledTurn` 收口、`_loadFinal`/`ensureEvidence` 正常跑，原轮留痕完整，标注"已改口"才立得住（与 I3 一致）；
  ④ 终态到后自动把纠正文本 `startChat` 发为新轮，渲染新理解卡。
- **写入后（writeIssued）**：不拦截——纠正话自然流入当前任务之后的下一条对话，引擎带会话记忆重新理解，
  执行"退旧办新"（P5，既有能力）。理解卡"改一下"按钮置灰，title/aria 提示"已经开始办理，改的话会自动退旧办新"。
- **改一下按钮行为（修订订正）**：点击 → 聚焦输入框并切换占位文案"直接说正确说法，比如：不是周三，是周四"（不预填、不自动发）。
- **兜底**：若取消请求返回 409（写请求已发出，理论按判据不会发生，但兜底要有）——如实提示"已经开始办理…"，不进入改口流程。

## 三、关键决定（四件套，含修订）

| # | 决定 | 事实 | 选项 | 决定 |
|---|---|---|---|---|
| 1 | **扩展既有 `decision:understand` 载荷**，不新增 type | 理解结果已在事件流（decide:understand，L2 默认可见），只缺结构化字段；事件由 `mapEntryToEvent` 机械映射、type 闭集三处登记 | a) 新增 `understanding` 类型 b) 扩展 decision 载荷 c) 前端从 text 解析 | b：闭集不动、天然不重复、成本最低；a 会造成"卡片+L2 焦点行+L3 留痕"三处重复且步数 +1 |
| 2 | 改口复用「cancel + 等终态 + 新任务」 | 引擎已有 P3 前 CANCELABLE、终态事件、对话延续/补偿 | a) 复用 b) 新增"改口"API/状态 | a：最小引擎改动、不破坏状态机 |
| 3 | slots 中文化在引擎做（label + 原话片段） | `getGlossary().slots` 有槽位中文名、slots 存原话片段 | a) 引擎下发人话版 b) 前端做映射 | a：前端零转换、口径单源（与 #understandSummary 同源） |
| 4 | 理解卡位于用户消息后、思考过程前；P1 decision 从 L2 焦点行退场 | 界面方案定"先核心输出、过程按需展开"；L2 焦点行与卡片重复 | a) 卡在前、焦点行退场 b) 只升级 L2 行样式 | a：理解是每轮最该先看见的，且不产生双份展示 |
| 5 | 改口拦截限定 `running && !writeIssued`，排除 suspended | `task.js:106` 挂起态 canCancel 也是 true，而挂起输入是追问回复 | a) 限定 running b) 照字面用 canCancel | a：照字面会取消追问回复、砸掉追问链路 |
| 6 | 等原轮终态再起新轮 | `_openStream` 会 close 旧流，改口后原轮收不到终态；轮询兜底不跑 `_loadFinal`/`ensureEvidence` | a) 等终态再起新轮 b) 轮询兜底+补拉证据 | a：原轮留痕完整、与 I3"不假装停住"一致（慢但正确） |

## 六、相邻缺陷（本次核验撞出，另立任务，不在本方案范围）

1. **会话记忆的槽位恒空**：`task-runner.js:151 #chatSummary` 读 `tc.chat?.slots`，全仓无写入点（实证恒 `{}`）——
   记忆只注入"上一轮原话 + intent + 终态"，槽位从未进记忆。若要让"数智楼123"这类上下文真正沿用到下一轮
   （prompt 的 few-shot 例子已含，掩盖了缺失），需修 `#chatSummary` 写入点。
2. **会话记忆端到端断言假绿**：`access.test.mjs:619` 断言"assistant 消息含 数智楼123"，实际注入记忆是
   `{"intent":"borrow-classroom","slots":{},"outcome":"DONE"}`——命中该断言的是 prompt 自带 few-shot 例子。
   要么修 `#chatSummary`（与 1 同源），要么把断言收紧到注入的那条消息。
3. **取消轮进记忆**：`http-server.js:411` 对每轮 chat 都 `recordTurn`，被取消轮以 REJECTED 记入。可接受（现状行为），
   本方案不为此加引擎改动；若将来补 slots 记忆再一并议"是否过滤被取消轮"。
