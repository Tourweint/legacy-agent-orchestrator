## 一、交付形态：录视频（这件事改变了很多要求）

| 项 | 现场演示 | **录视频（现状）** |
|---|---|---|
| 容错 | 一次机会 | **可以重录** |
| 节奏 | 现场计时 | 可以剪，但**每一步必须真实发生**（不能造假、不能摆拍） |
| 对"确定性"的要求 | 现场不复现就翻车 | **更高**：录不到就没法用；所以**只录能被稳定复现的东西** |
| 不能出现的画面 | 临场慌乱 | **报错弹窗、命令行窗口、接口 URL、残留测试数据、主题忽深忽浅** |
| 现场类准备（投影、计时彩排） | 必需 | **降级为可选**；换成"录制环境自检" |

**三条纪律（录制前必须满足）**：

1. **可复现**：每一个镜头都要能**重复录第二次**（数据可复位、步骤可脚本化）。
2. **不演小概率**：网络分区、进程崩溃、依赖服务挂掉这类**录不到也不用录**；超时、被占、维修中、冲突这类**大概率且能稳定制造**的，要录（这是鲁棒性的正面证据）。
3. **失败不是主菜**：主线是"能办什么、办得多顺、过程多透明"；失败镜头**短**（每条 ≤15 秒）且**必须有下文**（它怎么处理了）。

## 二、基础鲁棒性工作清单（"最基础"的边界＝本文全部勾完）

> **范围声明**：这是"提交前必须做完的最小集合"，不是全面加固。**每项都标了现状**（✅ 已有 / ⚠️ 部分 / ❌ 缺），**只做 ❌ 与 ⚠️**。
> **现状标注的依据**：阶段 0–8 的实现与变更记录，**不是本轮逐条实测**。凡是我不确定的一律标 ⚠️"需确认"；执行这批工作时，第一步就是把所有 ⚠️ 变成实测结论（✅ 或补做）。

### A. 进程与启动层（**今天刚踩过两个坑，优先级最高**）

| # | 项 | 现状 | 最小动作 | 怎么验 |
|---|---|---|---|---|
| A1 | **入口能被启动**（"测试全绿但进程起不来"） | ❌ 曾发生：引擎入口一处笔误让 `npm start` 直接崩，而单测与自检都不覆盖入口 | 加一条**入口冒烟**：用临时端口真起一次进程再退出，并纳入门禁 | 门禁多一条且能失败 |
| A2 | 门禁本身能跑完 | ✅ 已修（此前一年时间里约束检查会崩） | 保持 | `npm run check` 8/8 + 4/4 |
| A3 | 依赖未就绪时给**人话提示** | ⚠️ 引擎启动不检查依赖，跑起来才发现 401 | 启动时探活存量系统与 Redis，缺了就在控制台明确说"缺什么、怎么起" | 停掉 Redis 启动引擎，看到明确提示 |
| A4 | 端口被占用时行为明确 | ✅ 一键启动脚本会跳过并提示 | 保持 | 重复启动两次 |
| A5 | 一键启动可重复执行 | ✅ | 保持 | 连着跑两遍 |

### B. 外部依赖异常（**大概率，正是要录进视频的部分**）

## 四、录制 SOP（每段视频都走一遍）

```text
1. 跑"录制前检查"脚本 → 全绿才开始
2. 复位数据（生效记录 = 0）
3. 确认混沌撤防（默认即撤防，检查脚本会核）
4. 打开引擎、前端；统一主题；清空浏览器控制台
5. 按分镜脚本操作（台词照读）
6. 录完立即复位；把这一段视频与检查结果归档
7. 复核：画面里有没有不该出现的东西（见 §一 表格最后一行）
```
