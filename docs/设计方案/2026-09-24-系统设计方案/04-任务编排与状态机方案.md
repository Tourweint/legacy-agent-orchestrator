# 04 · 任务编排与状态机方案

> 本章解决：**一件事怎么被走完，以及"不该发生的事"怎么被结构性地禁止。**
>
> **本章不含代码。** §五 的转移表是**规格**：将来实现时逐行落地，实现与表格不一致即为缺陷。
>
> 依据：`docs/基线文档/智能体设计.md` §四（不变量 I1–I6）、§六（六命题 P1–P6）。

---

## 一、为什么状态机必须自研

**决定：自研表驱动状态机，不引入工作流引擎，也不用"顺序脚本 + 分支"。**

| 备选 | 为什么不选 |
|---|---|
| **顺序脚本 + if/else** | 它**表达不了"不知道"**。脚本的隐含假设是"每步都有明确结果"，于是超时只能被写成"失败"。而 I3 要求第三种取值。硬塞进去会变成散落各处的 `if (result === 'unknown')`，无法穷举、无法审查 |
| **引入工作流引擎（Flowable / Temporal 等）** | ① 状态机是本项目的**核心自研对象**，引入引擎等于把创新点外包；② 需求规模是十余个状态、单进程，远未到需要引擎的量级；③ 引擎把状态转移藏在配置或注解里，**"副作用只能从一个状态发出"这条约束就变得不可检查了** |
| **状态机库（通用 FSM 库）** | 通用库解决的是"状态转移合法性"，而本项目要解决的问题更靠前：**转移表本身就是设计产物**（它是命题的投影）。用库替代，等于把设计方案交给库的抽象 |

**自研的产出不是一个类，是一张表。** 表可以被评审、被自检、被逐行对照命题——这才是它不可替代的地方。

## 二、状态机要表达的三件事

一个只能表达"什么被允许"的状态机是不够的。它必须同时表达：

| # | 要表达的 | 表达方式 | 缺失会怎样 |
|---|---|---|---|
| 1 | **什么被允许** | 转移表（合法边） | —— |
| 2 | **什么被禁止** | **未列出的边一律非法**，命中即报错并留痕 | 会出现"莫名其妙地跳过校验直接提交"这类缺陷，且**不报错** |
| 3 | **"不知道"怎么办** | 必须有**专门的状态**承载不确定，且该状态**没有通往终态的边** | 不确定会被就近塞进"失败"或"成功"里——这正是本项目要消除的 |

> **第 2 条是本项目的一个教训来源。** 早期实现中曾出现"提交已写入数据库、对外却报错"的缺陷，根因就是状态机允许了一次非法跳步，而代码没有校验。**这条缺陷反过来证明了"非法边必须报错"的价值**——若当时静默放过，这个 bug 会以"偶尔对外报错但实际成功"的形式长期潜伏。

> **第 3 条是本章与普通状态机最大的不同。** 见 §六。

## 三、状态集合（15 个）

分四类：**流程态**（10 个）、**挂起态**（1 个）、**终态**（4 个）。

### 3.1 流程态

| # | 状态 | 语义 | 唯一入边来源 | 允许的出路 |
|---|---|---|---|---|
| 1 | **IDLE** | 请求已接收，尚未开始 | （初始） | 启动理解 / 直接进实体消解（结构化任务路径） |
| 2 | **UNDERSTANDING** | 理解层工作中（含格式重试） | IDLE、AWAIT_CLARIFY | 意图确立 / 槽位不全 / 超域 / 理解失败 |
| 3 | **RESOLVING** | 实体消解：人读标识 → 系统标识 | IDLE（`START_STRUCT`）、UNDERSTANDING | 解析成功 / 解析失败 |
| 4 | **GATHERING** | 收集命题所依赖的事实 | RESOLVING、DEGRADING | 事实齐备 / 部分事实不可得 |
| 5 | **VALIDATING** | 逐条判定命题 | GATHERING | 全部成立 / 有不成立（可降级）/ 有不成立（不可降级）/ 幂等命中 / **仅查询** / **无法确认（保守拒绝）** |
| 6 | **SUBMITTING** | **唯一能发出副作用的态**（正向写入与补偿撤销都从这里发出） | **VALIDATING、VERIFYING、COMPENSATING（仅此三处）** | 三值结果之一 |
| 7 | **JUDGING** | 对调用结果做最终定性 | SUBMITTING | 确定成功 / 确定失败（`CALL_UNKNOWN` / `CALL_CONFLICT` **不经过此态**，从 `SUBMITTING` 直达 `VERIFYING`，见 §5.2） |
| 8 | **VERIFYING** | 业务键查证，消解歧义 | SUBMITTING（`CALL_UNKNOWN` / `CALL_CONFLICT`） | 命中 / 未命中 / 查不清 / 查证次数超限 |
| 9 | **DEGRADING** | 换教室或换时段重试 | VALIDATING、JUDGING | 新方案可校验 / 待用户确认（换时段） / 退化轮次超限 |
| 10 | **COMPENSATING** | 逆序回滚已完成步骤 | JUDGING（`ROLLBACK_NEEDED`）；`JUDGING` / `VERIFYING` 在"目的 = 补偿撤销"下的成功收敛（见 §5.7） | 提交一次补偿 / 补偿已全部完成 |

> **注（本表与 §五 的维护关系，二审对齐）**：本表的"唯一入边来源"与"允许的出路"两列是**索引**，§五 各分表是**权威**，两者必须逐行一致。二审发现三处不一致并已修正：① `RESOLVING` 漏记 `IDLE --START_STRUCT-->`（一审新增的边）；② `VERIFYING` 误记来源含 `JUDGING`（`CALL_UNKNOWN` / `CALL_CONFLICT` 从 `SUBMITTING` 直达）；③ `JUDGING` 误记出路含"不确定"（三值里的"不确定"在 `SUBMITTING` 层就分流了，`JUDGING` 只见二值）。**今后任何一处加边或改边，两处必须同时改。**
>
> **三审修正（2026-09-25）**：二审把 `DEGRADE_ACCEPTED` 的去向改为 `GATHERING`（§5.4 注一）后，本表 `VALIDATING` 的入边仍残留"`GATHERING`、`DEGRADING`"，与转移表矛盾，现删除 `DEGRADING`——`VALIDATING` 的唯一入边是 `GATHERING`。

### 3.2 挂起态

| # | 状态 | 语义 | 与终态的区别 |
|---|---|---|---|
| 11 | **AWAIT_CLARIFY** | 已向用户追问，等待补充。**任务没结束，只是暂停** | 它**有出边**（见 §5.5：用户回复、取消、追问超限三条）。终态没有出边 |

> **这个区分是必须的，不是学究。** 状态机自检时若把"没有出边的状态"一律判为死状态会误报，而 `AWAIT_CLARIFY` 的实际情况是：**它有出边，但出边的触发依赖外部输入（人在场）**。终态则是**设计上不存在任何出边**。**必须把"等外部输入"与"结束"分开建模。**
>
> **二审修正**：本节此前写作"它没有出边是因为在等人"，与上一列"它有出边"自相矛盾，已改正。

### 3.3 终态

| # | 状态 | 语义 | 是否产生副作用 |
|---|---|---|---|
| 12 | **DONE** | 明确完成（含"幂等命中"：这件事已经成了） | 可能有（正常成功） |
| 13 | **REJECTED** | 明确拒绝，**未产生任何副作用** | 无 |
| 14 | **FAILED** | 明确失败，副作用**已收敛**（补偿完成或确认未生效） | 无（已收敛） |
| 15 | **UNRESOLVED** | **无法收敛，需人工介入** | **可能有且未知** |

> **`UNRESOLVED` 存在的必要性**：I6 要求"副作用必须被补偿或**显式登记为不可补偿**"。若没有这个状态，补偿失败就只能被塞进 `FAILED`——而 `FAILED` 的语义是"失败但干净"，会把"可能有半成品留在库里"这件事**悄悄说没了**。**必须有一个诚实的终态来承载不干净的结果。**

### 3.4 三个"不写"的纪律

| 纪律 | 说明 |
|---|---|
| 不设 `RETRYING` 状态 | 重试不是一个状态，是**从 VERIFYING 走回 SUBMITTING 的一条边**。若设成状态，会出现"在重试中"这种无法判定结果的滞留态 |
| 不设 `INIT` / `READY` 等框架性状态 | 与业务无关的状态会让转移表变长而信息量不变 |
| 不设"成功但不确定"这类复合状态 | 三值语义在**结果判定**里表达（第 05 章），不在状态里表达。状态要互斥且穷举 |

## 四、事件集合

事件是外部世界的输入。**同一个事件在不同状态下可以有不同的去向**——这正是表的意义。

### 4.1 理解阶段

| 事件 | 由什么触发 |
|---|---|
| `START` | 收到一次办事请求（自然语言路径） |
| `START_STRUCT` | 以**结构化任务**入口发起（第 03 章 §十：无 LLM 路径，直接给出意图 + 槽位） |
| `INTENT_RESOLVED` | 意图确立且置信度达标 |
| `SLOTS_INCOMPLETE` | 必填槽位有缺口（**由注册表机械计算**，不采信模型） |
| `OUT_OF_DOMAIN` | 超出业务域 |
| `UNDERSTAND_FAILED` | 格式重试耗尽，或模型不可用且无降级路径 |
| `USER_REPLIED` | 用户补充了信息 |
| `USER_CANCELLED` | 用户放弃 |
| `CLARIFY_LIMIT` | 追问轮次达上限 |

### 4.2 事实与判定阶段

| 事件 | 由什么触发 |
|---|---|
| `ENTITY_RESOLVED` | 人读标识成功映射到系统标识 |
| `ENTITY_UNRESOLVED` | 映射不到（**须携带候选列表**，用于生成可读的提示） |
| `FACTS_READY` | 命题所需事实**全部**已获得 |
| `FACT_UNAVAILABLE` | 某条事实**取不到**（权限失效、接口异常、查不清） |
| `PROPOSITIONS_OK` | 命题校验**通过**——全部命题成立，**或**命中 I1 显式豁免且已登记豁免（**唯一豁免项**：`P-NOT-ALREADY-MINE` 事实不可得时继续提交，决策 C17；**携带豁免载荷**，见 §5.2 注二） |
| `PROPOSITIONS_FAILED` | 有命题不成立，且**换方案也救不回来** |
| `PROPOSITIONS_UNCONFIRMED` | 有命题**无法确认**（其依赖的事实不可得，且该命题声明的处置是"保守拒绝"）→ 终态 `REJECTED`（二审新增，第 08 章 §三） |
| `DEGRADABLE_CONFLICT` | 有命题不成立，但**存在可尝试的替代方案**（换教室/换时段） |
| `CHECK_ONLY` | 该意图只查询、不写入 |
| `ALREADY_DONE` | 前置查重（`P-NOT-ALREADY-MINE`）命中：本人此前已提交过**同一件事**（决策 C6：判幂等成功，不判拒绝） |

### 4.3 调用与结果阶段

| 事件 | 由什么触发 |
|---|---|
| `CALL_SUCCESS` | 调用被判定为**确定成功** |
| `CALL_FAILURE` | 调用被判定为**确定失败**（业务层拒绝，如"已过可预约时间"） |
| `CALL_UNKNOWN` | 调用结果**无法判定**（超时、断连、语义不明） |
| `CALL_CONFLICT` | 收到**歧义信号**（协议层示例：`code 409`，见第 05 章 §六。**编排层看不到 HTTP 状态码与业务码本身**，只收到接触层归一化后的"歧义"结论——二审澄清表述） |
| `JUDGE_SUCCESS` / `JUDGE_FAILURE` | 定性完成 |
| `ROLLBACK_NEEDED` | 已完成的步骤需要回滚（多步写入场景） |

### 4.4 收敛阶段

| 事件 | 由什么触发 |
|---|---|
| `VERIFY_FOUND` | 查证**命中**——这条记录确实存在（是"我写的"或"已存在"） |
| `VERIFY_NOT_FOUND` | 查证**未命中**，且在可信范围内（未超安全阈值） |
| `VERIFY_INCONCLUSIVE` | 查证**查不清**（超出安全阈值、查证身份失效、时间无法比对） |
| `VERIFY_LIMIT` | 查证次数达上限（**补偿语境下该上限为 1 次**，决策 D8，见 §七） |
| `DEGRADE_ACCEPTED` | 找到可行的替代方案（**换教室**，或用户已确认的**换时段**） |
| `TARGET_CONFIRM_NEEDED` | 替代方案涉及**换时段**——时段是用户的核心诉求，**必须由用户确认**后才能继续（二审新增，第 08 章 §8.1） |
| `DEGRADE_EXHAUSTED` | 替代方案用尽 |
| `COMPENSATION_READY` | 补偿清单非空且当前项已确定需要撤销 |
| `COMPENSATION_DONE` | 补偿清单已全部处理完（成功或已登记） |

## 五、完整转移表

**读法**：行是状态，列是事件。空格 = **非法转移**（命中即报错并留痕，不静默通过）。

### 5.1 主表

| 状态 ＼ 事件 | `START` | `START_STRUCT` | `INTENT_RESOLVED` | `SLOTS_INCOMPLETE` | `OUT_OF_DOMAIN` | `UNDERSTAND_FAILED` | `USER_REPLIED` | `USER_CANCELLED` | `CLARIFY_LIMIT` |
|---|---|---|---|---|---|---|---|---|---|
| IDLE | UNDERSTANDING | **RESOLVING** | — | — | — | — | — | — | — |
| UNDERSTANDING | — | — | RESOLVING | AWAIT_CLARIFY | REJECTED | REJECTED | — | REJECTED | — |
| AWAIT_CLARIFY | — | — | — | — | — | — | UNDERSTANDING | REJECTED | REJECTED |
| RESOLVING | — | — | — | — | — | — | — | — | — |

> **注（`IDLE --START_STRUCT--> RESOLVING`）**：这是"无 LLM 也能跑"（第 03 章 §十）的结构落点。此前该边只写在 §3.1 的"允许的出路"里、不在表上——而"未列出的边一律非法"，故一审回填补入。`IDLE` 由此**恰好两条出边**：自然语言走 `START`，结构化任务走 `START_STRUCT`。
>
> **注（`RESOLVING` 行 `USER_CANCELLED` 列从略）**：`USER_CANCELLED` 在各分表中不重复列出，完整规格统一见 §5.9（一审回填，决策 B8）。

| 状态 ＼ 事件 | `ENTITY_RESOLVED` | `ENTITY_UNRESOLVED` | `FACTS_READY` | `FACT_UNAVAILABLE` |
|---|---|---|---|---|
| RESOLVING | GATHERING | REJECTED | — | — |
| GATHERING | — | — | VALIDATING | VALIDATING（见下注） |

> **注（`FACT_UNAVAILABLE` 的去向是 `VALIDATING` 而不是直接失败）**：缺一份事实不必然导致不能办——**它取决于缺的是哪一份**。若缺的是"维修窗口"，正确处置是**保守拒绝**；若缺的是"座位布局"（本就不在主链路），可以继续。所以它必须**进入判定**由命题各自决定，不能在状态机层次一刀切。
>
> 代价：命题层需要能表达"依赖的事实不可得"这一种判定结果（第 08 章 §四）。这个代价是必要的——**只有在命题层才能知道"缺的这份重不重要"**。

### 5.2 判定与提交

| 状态 ＼ 事件 | `PROPOSITIONS_OK` | `PROPOSITIONS_FAILED` | `PROPOSITIONS_UNCONFIRMED` | `DEGRADABLE_CONFLICT` | `CHECK_ONLY` | `ALREADY_DONE` |
|---|---|---|---|---|---|---|
| VALIDATING | **SUBMITTING** | REJECTED | **REJECTED（保守拒绝）** | DEGRADING | DONE | **DONE（幂等命中）** |
| DEGRADING | — | — | — | — | — | — |

> **注（`ALREADY_DONE` → `DONE`）**：这是决策 C6（重复提交判幂等成功）在 `VALIDATING` 层面的结构落点。前置查重命中"本人已提交过同一件事"时，终态是 `DONE`（幂等命中）而非 `REJECTED`——**事情已经办成了**。它是 `VALIDATING` 唯一通向成功终态的边，也是全部命题中唯一的"不成立却不拒绝"特例（命题侧见第 08 章 `P-NOT-ALREADY-MINE` 的终态特例行）。此边此前缺失，一审回填。

> **注二（`PROPOSITIONS_OK` 的豁免载荷，二审回填）**：决策 C17 允许 `P-NOT-ALREADY-MINE` 在事实不可得时"继续提交"。它**不新增 `SUBMITTING` 入边**（`SUBMITTING` 的入边必须恰好三条，自检项 5）——实现方式是该情形**仍走 `PROPOSITIONS_OK`** 进入 `SUBMITTING`，但**必须携带"已豁免的命题清单"这一载荷**，并在证据链与用户可见结果中标注"未能确认是否重复"。其他命题（F1/F3/F6 类）的事实不可得**不得**套用此载荷，只能走 `PROPOSITIONS_UNCONFIRMED`。

> **注三（`PROPOSITIONS_UNCONFIRMED` → `REJECTED`，二审新增）**：命题"无法确认"（其依赖事实不可得，且该命题声明的处置为"保守拒绝"）的去向是 `REJECTED`——此时**尚未发出任何副作用**，`REJECTED` 的语义（明确拒绝、未产生副作用）与之一致；而 `UNRESOLVED` 的语义是"可能存在未知副作用、需人工介入"，在这里过重（第 08 章 §三 二审修正）。它是 `VALIDATING` 六个出边事件之一（另有 §5.9 的 `USER_CANCELLED` 从略），与 `PROPOSITIONS_FAILED` **去向相同但事件不同**——自检项 3 检查的是"同一事件的去向唯一"，不是"同一去向的事件唯一"。

| 状态 ＼ 事件 | `CALL_SUCCESS` | `CALL_FAILURE` | `CALL_UNKNOWN` | `CALL_CONFLICT` |
|---|---|---|---|---|
| SUBMITTING | JUDGING | JUDGING | VERIFYING | VERIFYING |

> **`CALL_CONFLICT` 直达 `VERIFYING`，不经过 `JUDGING`。** 因为冲突信号的含义是"结果未知"，判定层对它没有可做的定性——**直接进入消解**。

### 5.3 结果判定与收敛

| 状态 ＼ 事件 | `JUDGE_SUCCESS` | `JUDGE_FAILURE` | `ROLLBACK_NEEDED` | `DEGRADABLE_CONFLICT` |
|---|---|---|---|---|
| JUDGING | DONE | FAILED | COMPENSATING | DEGRADING |

| 状态 ＼ 事件 | `VERIFY_FOUND` | `VERIFY_NOT_FOUND` | `VERIFY_INCONCLUSIVE` | `VERIFY_LIMIT` |
|---|---|---|---|---|
| VERIFYING | DONE（幂等命中，是我写的）**／REJECTED**（别人写的，见注三） | **SUBMITTING**（见下注） | UNRESOLVED | UNRESOLVED |

> **注（`VERIFY_NOT_FOUND` → `SUBMITTING`）**：这是**唯一一条回到副作用的边**，它对应"重试"。它成立的前提是查证**确定未生效**（不是"没查到"）。
>
> **这条边的存在就是 M4「写操作永不自动重试」的结构表达**：重试不是"再发一次请求"，而是"查证未命中之后才允许再发一次请求"。**没有查证，就没有这条边。**

> **注（`VERIFY_FOUND` 在补偿语境下的去向）**：若本次提交的**目的是补偿**，则"查证命中"的含义是"撤销已生效"，目标状态是**回到 `COMPENSATING` 处理下一项**。同名事件在两种目的下的去向不同——见 §5.7。

> **注三（正向语境下 `VERIFY_FOUND` 必须按"命中记录是谁的"拆分去向）**：第 06 章 §八与本章 §9.2 早已要求"命中且是别人写的 → 落 `REJECTED`"，但主表上此前没有这条边——一审回填补齐。
>
> - 命中且**是我写的**（Q1+Q2 同时成立）→ `DONE`（幂等命中，决策 C6）
> - 命中且**是别人写的** → `REJECTED`（"该时段已被占用"）
> - 是否在"别人写的"之后继续**降级换教室**：~~属一审新增待决 J1~~ **三审已拍板（2026-09-25）：不降级**——落 `REJECTED` 并给出可改选的其他教室，不增加 `VERIFYING → DEGRADING` 的边
> - 自检项 3 的"出边事件不重复"检查，对此类"同一事件按载荷分流"的边，按 `(状态, 目的, 载荷)` 分组进行

### 5.7 「目的」是转移表的第三个维度

**决定：`目的`（正向写入 / 补偿撤销）是状态机的一等上下文，转移表以 `状态 × 目的 × 事件` 为索引。**

**为什么需要这个维度**：同一个事件（例如 `JUDGE_SUCCESS`）在两种目的下应当导向不同状态——正向成功意味着"任务完成"，补偿成功意味着"撤销了一步，继续处理清单"。

| 若不做这个区分 | 后果 |
|---|---|
| 正向成功与补偿成功都落 `DONE` | **谎报**：补偿只是"收回了一步"，任务本身是失败的。落 `DONE` 等于告诉用户"办成了" |
| 用两个独立状态机 | 补偿链路得不到三值判定与查证的保护（见 §六 约束一） |

**规格**：

1. `SUBMITTING` 被进入时，必须携带本次提交的目的标记
2. `JUDGING` / `VERIFYING` 的判定行为**不因目的而变**（判定规则是统一的，见第 05 章）；但**查证的搜索目标**因目的而异——正向找"已存在一条我的有效记录"，补偿找"该记录已不存在或已失效"，谓词规格见第 06 章 §8.1（一审澄清）
3. **只有终态的选择**因目的而变

**两种目的下的去向对照（规格）**：

| 结果 | 目的 = 正向写入 | 目的 = 补偿撤销 |
|---|---|---|
| 确定成功 | `DONE` | `COMPENSATING`（处理清单下一项）；清单空则 `FAILED` |
| 确定失败 | `FAILED`（业务失败） | `UNRESOLVED`（**撤销失败，副作用未收敛**） |
| 不确定 → 查证命中 | `DONE`（幂等命中） | `COMPENSATING`（撤销已生效） |
| 不确定 → 查证未命中 | `SUBMITTING`（重试） | `SUBMITTING`（重试撤销，**上限 1 次**，决策 D8） |
| 不确定 → 未命中且**已达该目的的重试上限** | `UNRESOLVED`（`VERIFY_LIMIT`，正向上限 2 次） | `UNRESOLVED`（`VERIFY_LIMIT`，补偿上限 1 次，**不再重试撤销**） |
| 不确定 → 查不清 | `UNRESOLVED` | `UNRESOLVED` |

> **注意"补偿失败 → `UNRESOLVED`"这一行。** 它不能落 `FAILED`——`FAILED` 的语义是"失败但干净"，而"撤销失败"意味着**库里留着一条不该有的记录**。这个事实必须被诚实登记（I6），不能被一个看起来整洁的终态抹掉。

4. 自检时，"同一事件两种去向"的检查按 `(状态, 目的)` 分组进行

> **可行性评估点**：需要你确认是否接受"目的"作为转移表的第三维。我判断不了的是：实现时把目的做成状态的一部分（如 `SUBMITTING_FORWARD` / `SUBMITTING_COMPENSATE`）还是做成独立字段，哪种更不容易出错。**功能上两者等价**；前者让转移表变长但自检更简单，后者表更短但需要额外的检查。

### 5.4 降级与补偿

| 状态 ＼ 事件 | `DEGRADE_ACCEPTED` | `TARGET_CONFIRM_NEEDED` | `DEGRADE_EXHAUSTED` | `COMPENSATION_READY` | `COMPENSATION_DONE` |
|---|---|---|---|---|---|
| DEGRADING | **GATHERING**（见注一） | **AWAIT_CLARIFY**（换时段须用户确认，见注二） | REJECTED | — | — |
| COMPENSATING | — | — | — | **SUBMITTING** | FAILED |

> **注一（`DEGRADE_ACCEPTED` → `GATHERING`，且不直达 `SUBMITTING`）**：换了一间教室或一个时段之后，**该方案的事实与全部前置命题必须从零重来**。若允许降级直达提交，就等于"因为第一间不行，所以第二间直接借"——这正是脏数据最常见的来源。
>
> **为什么落到 `GATHERING` 而不是 `VALIDATING`（二审修正）**：判定的前提是事实。换教室会改变 F1/F3/F6，**换时段会改变 F3/F4/F6**——事实必须先重取，才谈得上重验。此前本表写作 `DEGRADE_ACCEPTED → VALIDATING`，与 §3.1"`GATHERING` 的来源含 `DEGRADING`"、第 08 章 §6.3"降级换教室时会对每个候选重复收集一轮"、§8.2"新方案的全部命题从零重验"**三处都不一致**（不能只重验命题而沿用旧事实）。**这条边是"降级不等于跳过校验"的结构表达。**
>
> **注二（`TARGET_CONFIRM_NEEDED` → `AWAIT_CLARIFY`）**：降级方案中涉及**换时段**时，时段是用户的核心诉求，**不得自动改写**（第 08 章 §8.1）。状态机在此挂起等确认；用户确认后走 `AWAIT_CLARIFY → UNDERSTANDING` 重新理解——这也让"新时段的事实"由常规收集路径自然取得。换教室**不经过**此边（`DEGRADE_ACCEPTED` 直落 `GATHERING`）。

> **注（补偿走 `SUBMITTING`）**：`COMPENSATING --COMPENSATION_READY--> SUBMITTING` 是补偿的**唯一**出口。补偿请求发出后，走与正向完全相同的 `JUDGING` / `VERIFYING` 机制（详见 §六 约束一与第 07 章）。
>
> `COMPENSATION_DONE` 表示**补偿清单已全部处理完**，任务落 `FAILED`（失败但已收敛）。

### 5.5 挂起态的出边补全

| 状态 ＼ 事件 | `USER_REPLIED` | `USER_CANCELLED` | `CLARIFY_LIMIT` |
|---|---|---|---|
| AWAIT_CLARIFY | UNDERSTANDING | REJECTED | REJECTED |

> 追问后再问一次理解层，而不是直接把用户补充的片段拼进去。理由：用户补充的话同样可能是不完整的自由文本（"下周三吧"），需要同样的三道闸门。

> **注（入边与计数口径，二审补齐）**：`AWAIT_CLARIFY` 有**两条**入边——`UNDERSTANDING --SLOTS_INCOMPLETE-->`（缺槽位追问）与 `DEGRADING --TARGET_CONFIRM_NEEDED-->`（换时段请用户确认，见 §5.4 注二）。**"追问轮次上限 3 轮"只计前者**：换时段确认**不消耗**追问轮次——它不是"槽位不全"（用户没有说不清，只是需要拍板），把它计入会让"降级 3 轮 + 追问 3 轮"互相挤占额度。

### 5.6 非法转移与"忽略型无边"的处理规格

| 项 | 规格 |
|---|---|
| 判定 | 转移表中该格为空，或目标状态不在状态集合内 |
| **例外：忽略型无边**（二审新增） | §5.9 中标注为"**忽略**"的格（`SUBMITTING` / `JUDGING` / `VERIFYING` / `COMPENSATING` 的 `USER_CANCELLED`）**不属于非法转移**——它表达的是"该事件在此状态下**设计上不生效**"。处置是**记录一条审计条目后不改变任何状态、继续当前流程**，既不抛错也不终止。**两类空格的区分必须显式标注**，不得留给实现者猜 |
| 处置 | **抛错并终止本次任务**（不猜测意图、不就近处理） |
| 留痕 | 记录：来源状态、事件、当时的中间数据快照 |
| 终态 | 落入 `UNRESOLVED`——因为"非法转移"意味着**我们不知道系统处于什么状态**，只能按最保守的方式登记 |
| 测试 | 见 §十一；**非法转移**与**忽略型无边**必须**各有用例**，不能只靠"实际没触发过" |

### 5.8 多资源场景（决策 D7 的结构落点）

**决策 D7 使"一次借两间教室"成为合法输入。本节规定它的结构形态——此前 D7 只定了"要做"，结构未定，一审回填。**

**核心决定：状态机的一次运行承载一个资源目标的完整生命周期；多资源意图由编排层按计划顺序组合多次运行。**

| # | 规格 | 说明 |
|---|---|---|
| 1 | **运行 = 单资源生命周期** | 与 §9.1 任务键的粒度一致（任务键 = 身份 + 资源 + 时段，本来就是按资源定义的）。转移表**不新增状态、不新增 `SUBMITTING` 入边**，§十一 的 8 条自检不受影响 |
| 2 | 实体消解一次完成 | 多个教室名在 `RESOLVING` 一次解出；第二次及以后的运行从 `GATHERING` 起（该资源的事实从零收集） |
| 3 | 资源**顺序**执行 | 前一资源运行落定后才发起下一资源；禁止并发提交两个资源（第 01 章 M5 有界并发原则） |
| 4 | 幂等业务键按资源独立 | 每个资源一个键（身份 + 该资源 + 时段），互不干扰（第 06 章 §二） |
| 5 | **补偿清单跨运行共享** | 任一运行产生的已生效副作用都进入同一份清单 |
| 6 | 步数预算按任务累计 | 双资源正常链路约 30 步，§七 的总步数上限（三审定为 **60**）跨运行累计适用；若未来资源数 > 2，需重新评估该值 |
| 7 | 证据链任务级连续 | 多次运行的证据条目连续编号，任务级可导出（P6） |

**运行级终态 → 任务级处置的映射**：

| 运行级终态 | 任务级处置 |
|---|---|
| `DONE` 且尚有后续资源 | 发起下一资源的运行（从 `GATHERING` 起） |
| `DONE` 且为最后一个资源 | 任务 `DONE` |
| `REJECTED` / `FAILED`，且任务尚可继续（后续资源仍可尝试） | 继续后续资源的运行（从 `GATHERING` 起）。**注意**：该资源的降级机会已在它自己的运行内用尽——`DEGRADING` 只能发生在落终态之前，运行一旦落终态就不得再回去降级（二审修正：原表述"在运行内走现有 `DEGRADING` 机制"在运行已终态时不成立） |
| 任务**不可继续**（降级穷尽 / 不可降级失败），且补偿清单非空 | 进入补偿：以一次"目的 = 补偿撤销"的运行按清单**逆序**逐项处理（复用现有 `COMPENSATING → SUBMITTING → JUDGING / VERIFYING` 机制），清单处理完落任务 `FAILED` |
| 补偿清单为空 | 运行级终态即任务级终态 |

**降级与补偿的交互（D7 的遗留前置条件，在此理清）**：**降级优先于补偿**。这是第 07 章 C2（"任务不会再继续"才允许补偿）的直接推论——只要还有可尝试的替代方案，就不该撤销已完成的步骤。落到场景上：第二间教室失败且降级穷尽时，才撤销已成功的第一间；第一间自己失败时，清单为空，直接落 `REJECTED`，无补偿。

**单资源兼容性**：单资源任务 = 一次运行，映射表的"清单为空"行适用，行为与 D7 之前完全一致。

### 5.9 用户取消的落点（决策 B8 的结构落点）

**决策 B8：取消只在写请求发出前生效；发出后取消转为"提交后查证"。此前该决策未落进转移表，一审回填。各分表中 `USER_CANCELLED` 列从略，本表是取消边的完整规格。**

| 所处状态 | `USER_CANCELLED` 的去向 | 依据 |
|---|---|---|
| UNDERSTANDING / AWAIT_CLARIFY | `REJECTED`（已有边，见 §5.1 / §5.5） | —— |
| RESOLVING / GATHERING / VALIDATING / DEGRADING | **`REJECTED`** | 写请求尚未发出，无任何副作用，取消 = 用户放弃；`REJECTED` 的语义（未产生副作用）与之吻合 |
| SUBMITTING / JUDGING / VERIFYING | **忽略型无边**（取消不生效） | 决策 B8：请求已发出，此时取消会制造不确定态；任务继续走查证收敛，不受取消影响 |
| COMPENSATING | **忽略型无边，且禁止中断** | I6：补偿一旦开始，必须走到清单处理完或显式登记，不接受中途放弃 |
| 终态 | 无边（真终态，无任何出边） | —— |

> **二审澄清（"忽略型无边"与"非法转移"的区别）**：本节前两行之外的"无边"**不是** §5.6 意义上的非法转移——它表达"该事件在当前状态下**设计上不生效**"，处置是**记录一条审计条目、不改状态、继续流程**；而 `SUBMITTING` 等处**未列出的其他事件**仍然是非法转移（抛错 → `UNRESOLVED`）。**两类空格的区分必须由实现显式标注**（第 04 章 §5.6 表的"忽略型无边"行），否则"用户在提交中点取消"会被错误地判成非法转移并落 `UNRESOLVED`。

**前端约束**：取消按钮的显隐与禁用必须按本表实现（第 10 章 §4.5）。

## 六、三处由结构（而非自觉）保证的约束

这三条是本章最重要的产出。它们不是"注意不要…"，而是"**在表上做不到**"。

### 约束一：副作用只能从 `SUBMITTING` 发出

`SUBMITTING` 的**入边只有三条**，每一条都对应**一次显式的决策事件**：

| 入边 | 决策事件 | 它保证了什么 |
|---|---|---|
| `VALIDATING --PROPOSITIONS_OK-->` | 全部前置命题成立 | **I1**（事实齐备） |
| `VERIFYING --VERIFY_NOT_FOUND-->` | 已确定此前**未生效** | **I2**（不重复写入） |
| `COMPENSATING --COMPENSATION_READY-->` | 已确定**需要且可以**撤销某一步 | **I6**（副作用收敛） |

**关键点：`SUBMITTING` 同时承载"正向写入"与"补偿撤销"两种目的。**

- 它们走**完全相同**的机制：同样的提交 → 三值判定 → 按需查证
- 区别只在**状态机记录的"本次提交目的"**这一个标记上，而不是两条代码路径
- **为什么这样设计**：补偿请求同样会超时、同样会返回歧义信号、同样需要查证。若给它另开一条路径，它就得不到三值判定与查证的保护——**而"补偿失败"恰恰是最需要被正确判定的事情**（不能被误判为成功，否则以为收回了，其实没收回）

**因此"唯一出口"的准确表述是**：

> **系统里不存在第四条能让副作用发生的路径。** 副作用只有正向与补偿两类，两类都从同一个状态发出，都受同一套判定与查证机制约束。

### 约束二：`UNKNOWN` 不可直通终态

- `VERIFYING` 是 `CALL_UNKNOWN` 与 `CALL_CONFLICT` 的唯一去向
- `VERIFYING` **没有任何一条边直接通向 `DONE`**（只有 `VERIFY_FOUND`，而它是查证结论不是调用结论）
- 因此"不确定"必须经过**查证**才能变成结论（I3 的结构表达）

### 约束三：不可补偿的写操作无法进入自动链路

- 数据侧：注册表中这类接口被标记为"禁止自动编排"（第 01 章 §七 M8）
- **结构侧**：它们**不被任何意图计划引用**，因此不存在一条边会走到它们
- 两道冗余是有意的：数据标记可能被改错，而"计划里没有它"无法被运行时绕过

## 七、循环与上限

**任何循环都必须有上限**，且上限必须是**具体的数字**，不能是"必要时再判断"。

| 循环 | 上限 | 达到上限时的处置 | 为什么这个值 |
|---|---|---|---|
| 理解格式重试 | **2 次**（共 3 次调用） | 如实上报"无法理解" | 3 次仍不合规，说明提示词或输入有问题，重试无用 |
| 追问轮次 | **3 轮** | 终止并列出"还缺什么" | 见第 03 章 §8.2 |
| 查证次数（**目的 = 正向写入**） | **2 次** | 落 `UNRESOLVED` | 查证两次仍不确定，说明查证路径本身不可用，再查也是同样结果 |
| **补偿重试（目的 = 补偿撤销）** | **1 次**（决策 D8） | 落 `UNRESOLVED`（`VERIFY_LIMIT`，**不再重试撤销**） | 撤销通常只有"能撤/不能撤"两种结果，重试意义有限；二审把它落进本表（此前只写在决策汇总，转移表接不住）。**与正向的"查证次数 2 次"是两个独立计数器**，各自在自己的目的下计数 |
| 降级轮次（换教室/换时段） | **3 轮** | 落 `REJECTED`（**并说明已尝试哪些方案**） | 3 轮覆盖"换时段""换邻近教室""两者都换"；再多只是穷举，用户等不起 |
| **任务总步数** | **60 步**（一次状态转移算一步，多资源任务跨运行累计；三审拍板 K1 由 40 上调） | 落 `UNRESOLVED` | 兜底防线。单资源正常链路约 15 步；双资源（决策 D7）约 30 步；**步数预算表的理论上界约 46，60 可覆盖且保留"打到上限即存在未预料环"的诊断余量** |

> **总步数上限是防死循环的最后一道防线。** 表驱动的状态机理论上不会有环（每条环都对应一次真实重试），但"理论上"不足以让人放心——**这道上限的成本极低，且它能保证系统在任何情况下都会停下来。**

> **步数预算表（二审补齐，用来判断 40 够不够）**——把每条循环的上限换算成步数（一次状态转移算一步）：
>
> | 组成 | 最坏步数 | 说明 |
> |---|---|---|
> | 起手（`START` → `UNDERSTANDING` → `RESOLVING` → `GATHERING` → `VALIDATING`） | 5 | 单资源正常链路的固定开销 |
> | 追问 3 轮 | 9 | 每轮 3 步 |
> | 降级 3 轮 | 15 | 每轮 5 步（`DEGRADING` → `GATHERING` → `VALIDATING` → `SUBMITTING` → `JUDGING`） |
> | 查证 2 次 | 6 | 每次 3 步 |
> | 第二个资源（决策 D7） | 5 | 从 `GATHERING` 起的一次完整运行 |
> | 补偿 1 项（含重试 1 次） | 6 | `COMPENSATING` → `SUBMITTING` → `JUDGING` →（未命中）`VERIFYING` → `SUBMITTING` → `JUDGING` |
> | **合计（理论上界）** | **46** | 各环同时打满 |
>
> **结论：40 不足以覆盖"所有循环同时打满"的理论上界（约 46 步）。** 正常演示远不会走到——它要求追问、降级、查证、补偿四件事同时到达各自上限。**三审已拍板（K1，2026-09-25）：采用处置 ①，上限上调至 60**——把合法路径判成 `UNRESOLVED` 会污染"系统诚实度"指标（第 07 章 §八 规格 3）；60 相对 46 仍保留"打到上限即存在未预料环"的诊断余量。

> **可行性评估点（三审已实测）**：数智楼共 5 间教室（容量 48/48/55/32/9），扣除主角后候选池**天然 ≤ 4 间**，降级 3 轮足以覆盖同楼栋候选耗尽；候选数上限 K=5（第 08 章 §8.1）。跨楼栋候选（电信楼 2 间 48 座）排在同楼栋之后。

## 八、状态与六命题的对应

这张表用来检查"是否有命题无处安放，或某个状态不服务任何命题"。

| 状态 | 服务的命题 | 说明 |
|---|---|---|
| IDLE / UNDERSTANDING / AWAIT_CLARIFY | **P1** 理解 | —— |
| RESOLVING / GATHERING / VALIDATING | **P2** 判定 | 实体消解是"判定"的前置（不解出 ID 就无从取事实） |
| SUBMITTING | **P3** 调用 | 身份选择在接触层完成 |
| JUDGING / VERIFYING | **P4** 结果判定 | 查证是判定的延伸，不是独立命题 |
| DEGRADING / COMPENSATING | **P5** 恢复 | 降级是"换个方案继续"，补偿是"收回去"，都属恢复 |
| （贯穿，不落状态） | **P6** 留痕 | 证据层是横切，不占状态——**若给它一个状态，会误导人以为"留痕"是流程中的一步** |
| DONE / REJECTED / FAILED / UNRESOLVED | —— | 终态不服务命题，它们是**结论的容器** |

**自检规则**：每个非终态必须至少服务一条命题；否则它是多余的。

## 九、重入、并发与"同一件事"

### 9.1 任务键

**决定：以"身份 + 资源 + 时段"作为跨会话的任务身份**（与第 06 章的幂等业务键一致）。

**为什么需要它**：用户可能开了两个标签页、或网络卡了点了两次、或换个说法又说了一遍。这三种情况在系统里表现为**三个独立请求**，但它们其实是**一件事**。

**它不是锁，是查证依据**：本项目**不做分布式锁**（存量系统不配合，且锁本身会带来新的失败模式）。它的用途是：提交前按这个键查一次"是不是已经有一份了"。

### 9.2 并发时的行为

| 场景 | 期望行为 | 依据 |
|---|---|---|
| 两个会话同时提交同一资源 | 一个成功，另一个收到冲突信号 → 进入查证 → 查证**命中的是别人的记录** → 落 `REJECTED`（并说明"该时段已被占用"） | I2 |
| 两个会话同时提交不同资源 | 互不影响 | —— |
| 同一会话重复提交 | 提交前的查重命中**自己的**记录 → 落 `DONE`（幂等命中；决策 C6，事件 `ALREADY_DONE`） | I2 |

**注意"查证命中的可能是别人的记录"这一情况**：这正是第 06 章要解决的"如何判断这条是不是我写的"——**仅凭业务键不够，还要比对写入者**（第 06 章 §三）。

### 9.3 挂起任务的过期

**决定：挂起态（`AWAIT_CLARIFY`）在会话内有效，不做跨会话持久化。**

- 理由：跨会话续跑需要定义"会话"的生命周期、冲突合并、超时清理，成本远大于收益
- 代价：用户关掉页面后回来要重说
- 若将来要做，须先定义会话语义（第 02 章待决 5）

## 十、超时策略

**核心口径：超时**不是**失败，它是 `UNKNOWN`。**

| 层级 | 策略 | 说明 |
|---|---|---|
| **单次调用** | 有超时，超时 → `CALL_UNKNOWN` | 超时值按接口分级（写接口给得宽一些，避免在"其实已写库"的情况下过早判定） |
| **重试** | 只有"查证确定未生效"才允许 | 见 §五.3 注 |
| **整体任务** | **不设墙钟超时**（待决 5） | 设墙钟超时会导致"任务被中断但副作用已发生"——比不设更危险。改用**总步数上限**兜底 |

> **为什么不给整体任务设墙钟超时**：任务超时被中断时，系统**不知道自己走到了哪一步**——可能刚好在写请求发出的瞬间。这个状态比"多等一会儿"糟糕得多。**用步数上限控制失控，用单次调用超时控制等待**，两者分工明确，不需要第三个机制。

> **可行性评估点**：需要你确认写接口的超时值。我判断不了的是：演示机与存量系统同机（localhost）时的正常响应时间。**建议做法**：先实测正常响应时间（预计 <100ms），写接口超时设为它的若干倍（如 3 秒），既能容忍瞬时卡顿，又不会让用户等太久。

## 十一、机器化自检规则（不写代码，写规则）

状态机是**可以被静态检查**的，这是它相对"分支脚本"的一大优势。以下是必须被检查的项：

| # | 自检项 | 判否说明 |
|---|---|---|
| 1 | **每个状态都能从初始态到达** | 有孤立状态 → 设计残留 |
| 2 | **每个非终态都有出边**（`AWAIT_CLARIFY` 有三条出边，见 §5.5；**"忽略型无边"不算"没有出边"**，见 §5.6 / §5.9） | 死状态 → 任务会卡住 |
| 3 | **每个 `(状态 × 目的 × 载荷)` 的出边事件不重复**（载荷维度见 §5.3 注三：`VERIFY_FOUND` 按"我写的/别人写的"分流） | 同一事件两种去向 → 行为不确定 |
| 4 | **终态没有任何出边**（含忽略型无边也**不**出现在终态，见 §5.9 末行） | 终态有出边 → 任务会被"复活" |
| 5 | **`SUBMITTING` 的入边恰好三条，且每条都能追溯到一次显式决策事件**（命题成立 / 查证未命中 / 补偿就绪） | 多于三条或有一条无决策来源 → 出现了绕过校验的副作用路径 |
| 6 | **`VERIFYING` 没有由 `CALL_*` 事件直通 `DONE` 的边**（`VERIFY_FOUND` 是**查证结论**而非调用结论；正向幂等命中经它落 `DONE` 是刻意的，见 §5.3 注三） | 有 → `UNKNOWN` 可以被当成功 |
| 7 | **每个终态都至少有一条入边** | 无入边的终态 → 永远到不了 |
| 8 | **被标记"禁止自动编排"的接口，不被任何计划引用** | 被引用 → 不可逆操作进入了自动链路 |

**这 8 条要能一键跑出来。** 它们检查的是"结构是否仍然符合设计"，而不是"功能是否正常"——**功能测试通不过会报错，结构被悄悄破坏不会报错**，所以必须单独检查。

> **可行性评估点**：需要你确认是否接受"8 条自检是一等公民"（即：自检不过就不允许继续开发）。我判断不了的是：你希望自检到什么频度（每次改动/每次提交/每次演示前）。**我的倾向是"每次改动后跑一次"**，因为它跑起来是瞬间的事。
