# 05 · 三值语义与结果判定方案

> 本章解决：**一次调用回来之后，系统凭什么说它成了、没成、或者不知道。**
>
> 这是本项目与"接口封装"的最大分野所在。普通封装只有两态，遇到超时只能猜；**本方案的设计前提是"猜不得"**。
>
> **本章不含代码。** §四 的判定规则表是**规格**：它在接触层被逐条执行，规则与实现不一致即为缺陷。

---

## 一、为什么必须三值：两值错在哪，四值又为什么多余

### 1.1 两值（成功/失败）在本地调用里没问题，在网络调用里有问题

两值的隐含假设是"响应到达即代表事实"。这个假设在本地函数调用里成立，在 HTTP 调用里**不成立**，因为它忽略了一个真实存在的中间状态：

> **请求已经被服务端处理并落库，但响应在返回途中丢失了。**

此时：
- 判**成功** → 撒谎。响应没到，我们不知道服务端做了什么
- 判**失败** → 更危险。用户被告知失败，于是重试；而库里**已经有了一条** → 重复数据 + 用户认知与服务端状态不一致

**两种都是错的，所以必须有第三种。**

### 1.2 为什么不是四值（如"部分成功""超时"）

| 备选 | 为什么不选 |
|---|---|
| 加"部分成功" | 本项目的写操作**没有部分**——整间教室预约是一个动作，要么有一条记录要么没有。若将来有多步写入，"部分成功"应表达为**编排层的多步状态**（第 07 章），而不是调用的第四种结果 |
| 加"超时"作为独立取值 | 超时是**信号**，不是**结论**。超时的结论就是"不知道"。把信号当结论会导致"超时"与"不知道"两条路径分叉，行为漂移 |
| 加"已提交待确认" | 这正是 `UNKNOWN` 的含义，另起名字只会让两处判定不一致 |

**三值就是最小完备集**：`SUCCESS` / `FAILURE` / `UNKNOWN`，分别对应"确定成了""确定没成""不知道"。

### 1.3 `UNKNOWN` 不是终点，是**待办**

这是最容易做错的地方：

> **`UNKNOWN` 必须被继续收敛，不得悬空。**（不变量 I3）

在第 04 章的结构里，这条被做成了拓扑性质：`UNKNOWN` 的唯一去向是**查证态**，而查证态**没有直通成功终态的边**。

**因此"把 UNKNOWN 当失败重试"和"把 UNKNOWN 当成功收工"这两条路在设计上走不通。**

## 二、判定在哪里做：一处，且只有一处

**决定：三值判定只在接触层发生，是全系统唯一的判定点。**

| 项 | 规格 |
|---|---|
| 谁判 | 接触层 |
| 输入 | ① 注册表声明的接口元信息 ② 协议级信号（§三） |
| 输出 | 一个三值结论 + 依据（**不输出原始响应给上层**） |
| 上层拿到什么 | 已归一化的结论。编排层**看不到 HTTP 状态码**，也看不到业务码 |

**为什么上层不能看到原始信号**：

一旦编排层能看到 `httpStatus`，它迟早会写 `if (httpStatus === 409)`。于是判定规则就从一处扩散成多处，而**多处的判定规则一定会漂移**——漂移之后，"同一响应在不同路径下被判定成不同结果"，系统就不可信了。

> ### 一处必须澄清的边界：接触层"不做业务判断"与"做结果判定"不矛盾
>
> 第 02 章说接触层"禁止做业务判定"。这里说它在做判定。两者不冲突，因为它们是不同的东西：
>
> | | 业务判定 | 结果判定 |
> |---|---|---|
> | 问题 | "这间教室能不能借？" | "这个响应代表成了还是没成？" |
> | 依据 | 事实 + 业务规则 | 协议信号 + 接口元信息 |
> | 是否依赖存量系统的业务语义 | **是** | **否** |
> | 归属 | 判定层 | 接触层 |
>
> **判定规则是声明式的**——它来自注册表与本章的规则表，接触层是**执行者**，不是**决定者**。等价的说法：接触层知道"这个接口是写接口，所以 5xx 要判成不确定"，但它不知道"这个接口写的是什么业务"。

## 三、判定的输入：五类信号

| # | 信号 | 取值 | 说明 |
|---|---|---|---|
| 1 | **HTTP 状态码** | 200 / 401 / 403 / 4xx / 5xx / 无 | 存量系统**只用它表达认证层的结果**，业务结果不在这里 |
| 2 | **业务码**（响应体内的 `code`） | 200 / 400 / 403 / 409 / 未登记值 / 缺失 | 存量系统的**业务结果全在这里** |
| 3 | **业务数据**（响应体内的 `data`） | 存在 / 不存在 / 形状不符 | 有的接口成功时 `data` 是本体的标识 |
| 4 | **传输层结果** | 收到 / 超时 / 连接断开 / 无法解析 | 决定"有没有响应" |
| 5 | **接口元信息** | 有副作用 / 无副作用；幂等业务键；查证路径 | 决定"同样的信号在读写两类接口上如何解释" |

**第 5 类信号常被忽略，但它决定了整张规则表的分叉。** 例如 5xx：

| 接口类型 | 5xx 的含义 |
|---|---|
| **只读** | 服务端没能给我们数据。**没有副作用发生** → 可以安全重试 |
| **写** | 服务端在返回前出错了，**但请求可能已经被处理** → 不能重试，必须查证 |

**因此"是否有副作用"必须是注册表的一等字段**，且必须传到接触层。这不是设计洁癖——**不知道它，就无法正确判定 5xx**。

## 四、判定规则表（穷举）

**读法**：自上而下匹配，命中即停。**未列出的组合一律 `UNKNOWN`**（保守兜底）。

### 4.1 有副作用的接口（写）

| # | HTTP | 业务码 | 其他条件 | 判定 | 理由 | 上层动作 |
|---|---|---|---|---|---|---|
| W1 | 200 | 200 | `data` 有值或该接口不返回 data | **SUCCESS** | 存量系统的成功语义 | 进结果确认 |
| W2 | 200 | **409** | — | **UNKNOWN**（歧义） | 无法区分"自己已成功"与"别人占了" | **禁止重试**，进查证 |
| W3 | 200 | 403 | — | **FAILURE**（身份错） | 方法层越权被拒。**绝不能当成功** | 直接失败；若身份是系统选的，登记为**系统缺陷** |
| W4 | 200 | 400 | — | **FAILURE** | 参数非法 / 资源不存在 / **业务规则拒绝**（**多种含义无法区分**，如"超过单次预约时长上限"） | 失败。**登记为疑似缺陷**——本地校验本该拦住它（M3），但归因**需人工确认**，不得自动定性为系统缺陷（一审修正：400 的语义二义，业务规则拒绝也可能走这个码） |
| W5 | 200 | 其他非 200 值 | — | **UNKNOWN** | 未登记的业务码，语义未知 | 进查证（见 §五） |
| W6 | 200 | 缺失 | — | **UNKNOWN** | 响应体不是约定形状，可能来自中间层 | 进查证 |
| W7 | **401** | — | — | **FAILURE**（凭证问题） | 未认证或凭证失效 | **不允许在写接口上"刷新凭证后直接重试"**，须先查证 |
| W8 | **403** | — | — | **FAILURE**（身份错） | 过滤器层权限不足 | 同 W3 |
| W9 | **5xx** | — | — | **UNKNOWN** | 服务端出错，**请求可能已被处理** | 进查证 |
| W10 | 4xx（非 401/403/**404**） | — | — | **UNKNOWN** | 未预期形状（404 见 W13，三审） | 进查证 |
| W11 | 无 | — | 超时 / 断连 | **UNKNOWN** | 最典型的不确定 | 进查证 |
| W12 | 有 | — | 响应体无法解析 | **UNKNOWN** | 无法得知内容 | 进查证 |
| W13 | 200 | **404** | — | **按调用类型分叉（三审实测新增，决策汇总 L1）** | 同一"资源不存在"语义在存量系统有两个码：GET 详情返 400、创建/撤销返 404 | **创建类调用** → **FAILURE**（引用资源不存在，业务拒绝，不重试；本应由前置命题拦住，登记疑似缺陷）；**补偿撤销调用** → **不判失败**，按第 06 章 §8.1 以 `recordId` 查证——列表中确无该 id 即"撤销已生效"，`recordId` 未知/查不清则 `VERIFY_INCONCLUSIVE` |

### 4.2 无副作用的接口（读）

| # | HTTP | 业务码 | 判定（三值） | 上层动作 | 与写接口的**差异** |
|---|---|---|---|---|---|
| R1 | 200 | 200 | **SUCCESS** | 使用数据 | 同 |
| R2 | 200 | 400 | **FAILURE** | 不重试；**不登记为缺陷**（读接口的参数由我们自己组装，可能确实传了它不接受的值，如"教室不存在"） | 同 |
| R3 | 200 | 403 | **FAILURE**（身份错） | 登记缺陷（根因在我们这边），不重试 | 同 |
| R4 | 200 | 409 | **FAILURE** | 不重试 | **差异**：读接口不会"冲突"，409 在只读语义下只能是异常，判失败 |
| R5 | 200 | 404 或其他 | **FAILURE** | 不重试 | **差异**：读接口拿到不认的码，重试也不会变，直接判失败 |
| R6 | **401** | — | **UNKNOWN**（凭证问题） | **刷新凭证后允许直接重试**（上限见 R10） | **关键差异**：无副作用，重试安全 |
| R7 | **403** | — | **FAILURE**（身份错） | 不重试（身份是声明式的，不会变）；登记缺陷 | 同上 |
| R8 | **5xx** | — | **UNKNOWN** | **可重试**（有限次，上限见 R10） | **关键差异**：无副作用，重试安全 |
| R9 | 无响应 | — | **UNKNOWN** | **可重试**（有限次，上限见 R10） | **关键差异**：无副作用，重试安全 |
| R10 | — | — | **重试超限后 → `FAILURE`**，并把结论标为"事实不可得" | 交命题层按"不可得"处置（第 08 章 §三） | 见第 08 章 |

> **二审修正（本表只改表达，不改语义）**：此前 R6/R8/R9 的"判定"列写的是动作（"可重试"）而非三值，R10 又缺信号列，导致"判定表"与"处置表"混成一列，实现者无法机械地对齐 W 表。现拆为"判定（三值）"+"上层动作"两列，**与 §4.1 写接口表同构**。重试次数上限沿用决策 C13（**2 次，短间隔**）；R10 是"重试超限的兜底行"，不是一条独立信号行。

> ### 这张表最重要的一行是 R6/R8/R9 与 W7/W9 的对比
>
> **同一个信号（401、5xx、超时），在读写两类接口上处置相反。**
>
> - 读：可以重试 —— 因为重试不会改变世界
> - 写：必须先查证 —— 因为重试可能造出第二条记录
>
> **这就是"写操作永不自动重试"（M4）的由来**，也是它为什么不能靠"注意一下"来落实——它必须写进规则表，且规则表必须知道接口是读还是写。

### 4.3 规则表的"未列出即未知"原则

**决定：规则表是白名单式的。任何未明确列出的组合，一律判 `UNKNOWN`。**

**为什么不设"默认判失败"**：默认失败是一个**静默的错误源**。存量系统将来若新增一个业务码（比如 `code: 422` 表示"超过每日配额"），默认失败会把它当成"技术故障"，用户收到的信息是错的，而**系统不认为自己做错了什么**。

默认 `UNKNOWN` 的代价是：遇到新码会进入查证，可能查不清而落 `UNRESOLVED`。**这个代价是可接受的**——它会促使我们去登记这个新码，而不是被悄悄吞掉。

## 五、`HTTP 200` 陷阱：为什么不能只看状态码

这是存量系统最反直觉的一处，也是**最危险的一处**。

| 现实 | 后果 |
|---|---|
| 业务错误**全部返回 HTTP 200**，语义只在响应体的 `code` 里 | 任何"看 HTTP 状态码判成败"的实现，都会把**越权被拒**（W3：`200 + code 403`）和**冲突**（W2：`200 + code 409`）判成**成功** |

**这与常规直觉相反**：多数人写 HTTP 客户端时，把"非 2xx 抛错、2xx 成功"当成本能。在这里，**这个本能会直接制造假成功**。

### 5.1 假成功的三个来源（穷举）

| # | 来源 | 表现 | 危害 |
|---|---|---|---|
| 1 | `HTTP 200 + code 403`（方法层越权） | 系统以为预约成功，实际被拒 | **静默**：用户被告知成功，库里什么都没有 |
| 2 | `HTTP 200 + code 409`（冲突） | 系统以为预约成功 | 半静默：库里可能真有一条（自己已成功），也可能是别人占的**而用户以为是自己的** |
| 3 | `HTTP 200 + code 400`（参数错） | 系统以为提交成功 | 静默：参数错了，什么都没写 |

> **第 1 种最危险**，因为它连"事后对账"都很难发现——用户拿到"成功"，走了。**唯一的防线是判定规则必须在看状态码之前先看业务码。**

### 5.2 规格要求

**决定：判定必须按固定优先级读取信号，顺序不可调整。**

```text
先判「有没有响应」 → 再判「响应体能不能解析 + 业务码是否存在」
   → 再判「业务码是不是成功码」 → 最后才看 HTTP 状态码
```

**最后才看 HTTP 状态码的理由**：HTTP 状态码在本系统里**只承载认证层信息**（401/403），业务结论它不承载。把它放到最后，是因为"它是唯一会被本能误用的信号"——**顺序本身就是一道防线**。

> **可行性评估点**：需要你确认这个优先级顺序是否值得写进规格。我判断不了的是：将来若纳管**一个协议正常的系统**（业务结果用 HTTP 状态码表达），这张表的顺序是否需要按接口可配置。**我的倾向是保留单一顺序**，因为"按接口切换判定顺序"会让判定规则出现分支，而分支会漂移。

## 六、409 歧义：本章与其他章的分界点

409 在本项目里被反复提到。这里要说清**它到底歧义在哪，以及判定层为什么解决不了它**。

| | 情况 A | 情况 B |
|---|---|---|
| 真实原因 | **你自己刚才那次其实提交成功了** | **别人抢先占用了这个时段** |
| 响应内容 | 完全相同 | 完全相同 |
| 正确应对 | 告诉用户"已办成"（附记录号） | 告诉用户"该时段被占，可换教室/时段" |
| 副作用状态 | 已发生，且应当保留 | 未发生，什么都没写 |

**判定层能给出的只有"UNKNOWN"。** 区分 A 与 B 需要**额外的事实**（去查那条记录到底是谁写的、什么时候写的），这属于**查证**，不属于判定。

**所以 409 的正确处置有一条清晰的边界**：

| 环节 | 做什么 | 不做什么 |
|---|---|---|
| **判定层（本章）** | 判为 `UNKNOWN`，并**带上"歧义"标记** | 不猜、不重试、不当成功 |
| **编排层（第 04 章）** | 转 `VERIFYING` 态 | 不直接重试 |
| **查证（第 06 章）** | 按业务键查，并比对写入者，区分 A/B | —— |

> **规格要求**：判定结果里必须携带一个**"歧义"标记**（ambiguity flag），供证据链与演示界面显示。这个标记让演示时能说清"系统知道自己不知道"——**这是最能体现设计深度的展示点之一**。

## 七、"无权限"的两种表达

同一语义（权限不足）有两种协议表达，规则表必须**两条都覆盖**：

| 来源 | 表达 | 落在哪一行 |
|---|---|---|
| **过滤器层**拒绝（未匹配到可访问路径） | `HTTP 403` | W8（写）/ R7（读） |
| **方法层**拒绝（`@PreAuthorize` 不通过） | `HTTP 200 + code 403` | W3（写）/ R3（读） |

**这两条必须都判为 FAILURE，且都必须携带"身份错"这一具体原因。**

**为什么必须区分"身份错"与普通业务失败**：身份错的根因在**我们这边**（注册表声明的所需角色写错了，或凭证池取错了身份），而普通业务失败的原因在**业务条件**上。前者是**系统缺陷**，必须被登记并修正；后者是正常路径。

**规格**：判定结果里的失败原因必须**分类到"身份错"这一具体取值**，而不是笼统的"调用失败"。否则每次越权被拒都会被当成一次业务失败，**系统自身的缺陷会被业务失败掩盖**。

> **可行性评估点**：需要你确认是否要为"身份错"设一个专门的告警/自检项。我判断不了的是：演示时若发生身份错，是希望它**安静地当成失败**（不影响演示流畅度），还是**显眼地暴露为系统缺陷**（更诚实但可能尴尬）。**我的倾向是"在证据链里显眼暴露、在用户界面上安静处理"**——用户不必知道我们的组件出了问题，但我们必须知道。

## 八、判定结论的结构

判定输出不只是三个字。它必须**可复述**（I4）。

| 字段 | 含义 | 为什么需要 |
|---|---|---|
| `verdict` | `SUCCESS` / `FAILURE` / `UNKNOWN` | 三值本身 |
| `reasonCode` | 具体原因编码（如"身份错""参数非法""业务冲突""超时"） | 决定上层动作；决定是否登记为系统缺陷 |
| `ambiguous` | 是否歧义信号 | §六；驱动查证策略与演示展示 |
| `evidence` | **判定依据**：命中的规则行号（如 W2）、关键信号（HTTP 状态、业务码）、**原始响应的片段** | 回答"凭什么这么判"；答辩时可直接展示 |
| `retryable` | 在当前语境下可否安全重试 | **注意**：这个标记只表达"技术上安全"，**不表达"业务上应该"**。写接口即使标了可重试，也仍须先查证 |
| `elapsedMs` | 耗时 | 用于定位"是慢还是错" |

**三条关于 `evidence` 的规格**：

1. **必须包含原始信号的片段**（不是摘要）。答辩时"我们有证据"这句话要有实物
2. **必须包含命中的规则行号**。它让"判定"这件事本身可被复查——规则行号一改，历史判定就能被重新解释
3. **不得包含凭证**（token、密钥）。凭证只在接触层内部流转（I5 / 第 01 章 M6）

## 九、错误分类与三值的关系

这两组概念容易混淆，必须明确定义。

| | 三值（本章） | 错误分类 |
|---|---|---|
| 回答什么 | **成没成** | **接下来怎么办** |
| 取值 | SUCCESS / FAILURE / UNKNOWN | BUSINESS / TRANSIENT / FATAL |
| 谁消费 | 状态机（决定去哪个状态） | 处置策略（决定重试/上报/转人工） |

**映射关系**（规格，须逐行落到规则表）：

| 三值 + 原因 | 错误分类 | 处置 |
|---|---|---|
| SUCCESS | —— | 进结果确认 |
| FAILURE + 业务条件不满足（如"不接受该时段"） | **BUSINESS** | 上报用户；不回滚已完成的只读步骤 |
| FAILURE + 身份错 | **FATAL** | **系统缺陷**，登记；上报"系统配置异常" |
| FAILURE + 参数非法 | **FATAL** | **疑似缺陷**（400 语义无法自动区分：参数非法 / 资源不存在 / 业务规则拒绝），登记待人工确认 |
| FAILURE + 只读重试超限 | **TRANSIENT**（已耗尽） | 把结论标为"事实不可得"，交命题层处置 |
| UNKNOWN | —— | 进查证；**分类在查证收敛后确定** |
| 查证后仍 UNKNOWN（查不清） | **FATAL** | 落 `UNRESOLVED`，转人工 |

> **注意"FATAL"用得很多**。这里 FATAL 的语义是"**需要人（我们）介入**"，不是"用户办不成"。身份错与参数非法都是**我们的缺陷**（第 02 章 M3：把不合格请求挡在存量系统之外）。把它们标成 FATAL 而不是 BUSINESS，是为了让这些缺陷**不被业务的正常失败淹没**。

## 十、明确排除的做法

| # | 排除 | 理由 |
|---|---|---|
| 1 | ~~只看 HTTP 状态码判成败~~ | §五；直接制造假成功 |
| 2 | ~~把超时/5xx 当失败~~ | §1.1；用户被误报，且会触发重复提交 |
| 3 | ~~把 409 当成功~~ | §六；可能是别人占的 |
| 4 | ~~把 409 当失败后直接重试~~ | §六；可能是自己已成功 |
| 5 | ~~让上层看到原始 HTTP 状态码~~ | §二；判定规则会扩散并漂移 |
| 6 | ~~在写接口上"刷新凭证后直接重试"~~ | §4.1 W7；凭证失效时请求可能已被处理 |
| 7 | ~~把未登记的业务码默认判失败~~ | §4.3；静默的错误源 |
| 8 | ~~把"身份错"与"业务失败"混为一类~~ | §七；会掩盖系统自身缺陷 |
| 9 | ~~给 `UNKNOWN` 设"超时后自动重试 N 次"的定时器~~ | §1.3；会自动把不确定变成重复写入 |
| 10 | ~~在判定结论里保留完整原始响应~~ | 可能含凭证；只保留片段与关键信号 |
