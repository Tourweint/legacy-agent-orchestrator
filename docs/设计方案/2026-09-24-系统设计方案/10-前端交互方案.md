# 10 · 前端交互方案

> 本章解决：**界面长什么样、展示什么、以及"可解释性"如何被人看见。**
>
> **本章不含代码。** §三 的三值表达与 §六 的数据流是**规格**。
>
> 相关：`docs/研发规范/文档驱动开发规范.md` §五（前端分层规范）；第 02 章 §七（前端不得直连存量系统）。

---

## 一、前端的职责：它不是聊天框，是**可解释性的外化**

这一句决定了整章的取向。

| 若把前端当聊天框 | 本项目的前端应当做的是 |
|---|---|
| 输入一句话、输出一段话 | 输入一句话，输出**一句话 + 一份可追溯的执行过程** |
| 只有"成功/失败"两种显示 | 显示**三值**（含"不确定，正在查证"） |
| 过程不可见 | **每一步的判定依据、用到的身份、读到的值都可见** |
| 出错就说"出错了" | 出错要说"**在哪一步、依据什么、试过什么**" |

**理由**：本项目的立论是"可解释可恢复"。而**可解释性如果只存在于日志和文档里，它在答辩现场是不存在的**。

> **这是一个判断，也是一个取舍。** 把执行过程可视化会让界面复杂、开发量增加；但**不这么做，"可解释"这条主张就只剩一张嘴**。
>
> **可行性评估点**：需要你确认这个取向。我判断不了的是：你希望答辩时评委的注意力更多在"界面的完成度"还是"过程的深度"。**若偏前者**，可以把轨迹做成可折叠的次级面板；**若偏后者**，轨迹应该是**主视图**，对话退居一侧。

## 二、三个视图

**决定：界面由三个互相联动的视图组成，不是一个大框。**

```text
┌────────────────────────┬──────────────────────────────┐
│  ① 对话视图             │  ② 执行轨迹视图                │
│                         │                              │
│  用户说什么             │  P1 理解  ✓ 意图=借教室        │
│  系统问什么             │          槽位=…（缺哪一天）     │
│  系统怎么答             │  P2 判定  ✓ 收集 4 项事实       │
│                         │          ✗ 时段已被占           │
│  （人读的）              │  P3 调用  — 已选身份：TEACHER   │
│                         │  P4 结果  ⚠ 不确定 → 查证中      │
│                         │  P5 恢复  —                    │
│                         │  P6 留痕  证据链 7 条            │
│                         │                              │
│                         │  （机器做的，人可读的形态）       │
├────────────────────────┴──────────────────────────────┤
│  ③ 结果视图                                             │
│  终态 + 唯一结论 + 用户可读的话术 + 证据链明细             │
└───────────────────────────────────────────────────────┘
```

### 2.1 ① 对话视图

| 项 | 规格 |
|---|---|
| 展示什么 | 用户的每一句话、系统的追问、系统的最终答复 |
| **不展示什么** | **不展示接口名、参数名、状态机状态名**——用户是"不懂接口的普通学生"（边界文档 §一） |
| 追问的形态 | 问题 + 可选答案（若是"选意图"或"选时段"） |
| 时间表达的展示 | 凡涉及时间，**必须展示归一化后的具体值**，并保留用户的原始说法（"您说的『下午』 → 09/30 13:00–14:30"） |

> **"保留用户的原始说法"这一条是刻意的**：如果用户说"下午"、系统显示"13:00–14:30"，用户看到的是系统的理解；**再加上原话，用户才能判断这个理解对不对**。这是 §7.3"请确认"在界面上的落地。

### 2.2 ② 执行轨迹视图

**这是本作品的展示核心，不是可选装饰。**

| 项 | 规格 |
|---|---|
| 结构 | 按 P1–P6 六段组织，与 `智能体设计.md` §7.2 同源 |
| 每步展示 | ① 做了什么 ② 依据什么（引用事实/命题标识） ③ 结论 ④ 用了哪个身份 |
| **身份必须可见** | 因为"跨权限域"是本项目的立论，**身份切换要在界面上被看见** |
| **事实来源必须可见** | 每条事实标注来源（哪个域、哪个接口的业务语义），使"跨域聚合"变成可见的事实 |
| 折叠规则 | 默认展开 P1–P4，P5/P6 折叠（它们多数时候是空的） |
| 实时性 | **边执行边出现**，不是执行完再一次性渲染（见 §六） |

**展示粒度（规格）**：

| 阶段 | 展示内容 | 禁止展示 |
|---|---|---|
| P1 理解 | 识别出的意图、槽位（原话片段）、缺口 | 模型的原始输出（非确定性，且无意义） |
| P2 判定 | 需要哪些事实、每项的来源与获取状态、每条命题的判定与依据 | 原始响应体（可折叠的"原始证据"除外） |
| P3 调用 | 接口的**业务语义名**、使用身份、参数形状 | 接口 URL、token（**禁止**） |
| P4 结果 | 三值判定、命中的规则、是否歧义、查证过程与结论 | 原始 HTTP 状态码作为**主要**信息（可作次级证据展示） |
| P5 恢复 | 是否触发补偿、补偿结果、是否登记为待处理 | —— |
| P6 留痕 | 证据链条目数 + 明细入口 | —— |

### 2.3 ③ 结果视图

| 项 | 规格 |
|---|---|
| 终态 | **4 个终态**（DONE/REJECTED/FAILED/UNRESOLVED）各有明确视觉形态；另有"查证中/已收敛"两个**过渡形态**（§三，三审计数澄清：过渡形态不是终态） |
| 唯一结论 | 一句话说清"成了 / 没成 / 不知道 / 需要人工处理" |
| 用户话术 | 来自第 08 章的命题失败话术；**必须包含"为什么"** |
| 证据链 | 可展开的明细：时间、阶段、依据、结论 |
| 待处理项 | 若落 `UNRESOLVED`，**必须显著展示**待处理事项的内容（第 07 章 §六） |

## 三、★ 三值在界面上的表达

**这是本章最需要仔细设计的一处。** 因为三值语义是本项目的核心，而**它若在界面上退化成两值，整个设计就白做了**。

| 判定 | 视觉形态 | 文案 | 可用操作（按钮） | 禁止的形态 |
|---|---|---|---|---|
| **确定成功** | 绿色系，实心标识 | "已办成" | 无（可再次发起新任务） | —— |
| **确定失败** | 红色系，实心标识 | "未能办成：{原因}" | **可**提供"换一个方案"（等价于**发起一次新任务**，候选由系统给出，不由前端编造） | 只说"失败"不给原因；**不得**提供"原样重发" |
| **不确定（查证中）** | **琥珀色，带进行中动效** | "**结果待确认，正在核对……**" | **无重试**；取消按钮按 §4.5 显隐矩阵 | **禁止**显示成失败（灰/红）或成功（绿）；**禁止**显示成静止状态 |
| **不确定 → 已收敛** | 依收敛结果变为绿或红 | 同成功/失败 | 同收敛后的对应行 | 收敛后仍停留在"不确定" |
| **需要人工处理** | 琥珀/深色，**带显著的"待处理"标记** | "操作未成功，且有一项变更需要人工处理（编号 X）" | **无**（不由前端提供"再试一次"） | 与普通失败混同；折叠在次级面板里 |

> **二审补充**：上表是"界面上有什么按钮"的**唯一来源**；§4.5 是其中"取消按钮"一列的展开。此前本表只有视觉与文案，没有按钮列，导致"失败态能否重试"没有规格。**任何按钮的出现都必须能追到本表的一行**——这是"界面不得自行推断"（§6.1）在操作层面的落点。

### 3.1 为什么"不确定"必须有专门的视觉形态

| 若把它显示成失败 | 若把它显示成成功 |
|---|---|
| 用户会去重试 → **可能造成重复提交**（这正是系统要防的，而界面在诱导它发生） | 用户以为办成了 → 库里可能什么都没有 |
| 与 I3 冲突 | 假成功，静默 |

**规格**：

1. **"不确定"必须携带"正在做什么"**（"正在核对：该时段是否已有一条相同的申请"）——**让等待有内容**
2. **"不确定"必须携带"已经查了多久 / 还要多久"的量级提示**（不是精确进度条，是"通常数秒内完成"这类预期管理；**三审 J7 口径**：最坏上界随 K1=60 约为 3 分钟，文案不得承诺更短）
3. **"不确定"不允许提供"重试"按钮**。此时重试是危险的——**界面不得提供一个会让用户犯错的操作**

> **第 3 条是本章最容易做错的一条。** 常规 UI 设计里，"加载失败 → 提供重试按钮"是标准做法。**在这里，它是个陷阱**：因为"不确定"不代表失败，此时重试等于绕过查证。

## 四、关键交互

### 4.1 追问（对应挂起态）

| 项 | 规格 |
|---|---|
| 触发 | 必填槽位缺失（第 03 章 §五 闸门三） |
| 形态 | 一个明确的问题 + **可选答案**（若有候选） |
| 上限提示 | 第 2 轮起提示"再补充 1 次我就需要您换个说法了"（诚实，且降低第 3 轮的突兀） |
| 超限 | 明确终止并给出**结构化说明**："要办这件事，我需要知道：① 哪一天 ② 哪个时段" |

### 4.2 确认（写操作之前）

**决定：对写操作，界面必须在提交前提供一次**明确的确认**。**

| 项 | 规格 |
|---|---|
| 内容 | 归一化后的完整语义（教室、日期、时段的**具体值** + 用户原话）+ 将要发生什么 |
| **不得省略** | 因为一次写操作**不可自动撤销**（第 01 章 §一） |
| 与其他确认的区别 | 这不是"礼貌确认"，是**用户纠正理解错误的最后一道机会** |

> **可行性评估点**：需要你决定确认交互是否必须（可能拖慢演示节奏）。我判断不了的是：演示时长与"现场感"的取舍。**我的倾向是必须保留**，但可以做成"在对话流内的一句内联确认"而不是弹窗——**既不打断节奏，又保留了纠正机会**。

### 4.3 拒绝的可解释

| 项 | 规格 |
|---|---|
| 必须给出原因 | 引用具体的事实与命题（第 08 章 `失败话术`） |
| 必须给出**下一步** | "可以改选：数智楼123 / 数智楼233"，或"可以换个时段" |
| **禁止** | 只给"操作失败"；给接口术语；给出系统中不存在的选项 |

### 4.4 降级的可见性

**规格**：降级发生时，界面必须展示**"试过哪些方案、为什么不行"**（第 08 章 §8.3 的尝试清单）。

**理由**：降级是本项目最像"智能体"的一幕——**它在替用户试**。不展示过程，这一幕的价值就浪费了。

### 4.5 用户取消（决策 B8，一审回填）

**取消按钮的显隐与禁用必须严格对应状态机的取消边（第 04 章 §5.9），不得由前端自行推断。**

| 任务阶段 | 取消按钮 | 点击行为 |
|---|---|---|
| 理解 / 追问 / 收集事实 / 校验 / 降级（**写请求发出前**） | **可见可点** | 任务落 `REJECTED`，提示"已按您的要求取消，未产生任何变更" |
| 提交中 / 判定中 / 查证中（**写请求已发出**） | **禁用**（灰置 + 文案"已提交，正在确认结果，暂时无法取消"） | 取消不生效——此时中断会制造不确定态；任务继续走查证收敛 |
| 补偿执行中 | **隐藏** | 补偿一旦开始不可中断（I6） |
| 终态 | 不出现 | —— |

**禁止**：在"不确定（查证中）"状态下提供任何**等价于重试或放弃写入**的操作入口——这是 §3.1 第 3 条（不确定禁止重试按钮）的延伸：换一个名字的重试仍然是重试。

## 六、数据流：边执行边推送

**决定：一次办事请求建立一条**事件流**，执行步骤实时推送；最终结果也由同一条流给出。**

| 备选 | 为什么不选 |
|---|---|
| 一次性返回（请求 → 等 → 完整结果） | 用户盯着转圈等数秒。**而"过程可见"正是本作品的展示核心** |
| 前端轮询任务状态 | 需要引入"任务"概念与存储，且轮询间隔会造成轨迹的断裂感 |
| 前端自己推断步骤 | **绝对不可**——见 §6.1 |

### 6.1 ★ 界面展示的内容必须与证据链同源

**规格**：轨迹视图里的每一条，**必须直接来自证据链**，不得由前端根据最终结果反推或补全。

| 若前端自行推断 | 后果 |
|---|---|
| 前端按"最终成功"倒推出"查证命中" | 若实际是"直接成功、未查证"，界面就会展示一个**没发生过的步骤** |
| 前端按经验估算步骤顺序 | 界面与证据链不一致 → **"界面在演戏"**，而这恰恰摧毁了"可解释"这条主张 |

**推论**：事件流的**粒度由证据链决定**，不是由界面需要决定。若界面想看某个信息而证据链没有，**要补的是证据链**。

### 6.2 事件类型（规格）

| 事件 | 触发 | 界面反应 |
|---|---|---|
| 阶段开始 / 结束 | 进入/离开某个命题阶段 | 轨迹条目出现并标记结果 |
| 事实获取 | 每项事实获得（或不可得） | 展示来源与状态 |
| 判定结论 | 每条命题判定完成 | 展示依据 |
| **需要用户输入** | 挂起态（追问 / 确认） | 对话视图出现交互 |
| 不确定 | 进入查证 | **切到"待确认"形态** |
| **取消结果**（二审新增） | 取消被接受（落 `REJECTED`）或不被接受（忽略型无边，§4.5） | 对话视图给出对应提示；轨迹追加一条审计条目 |
| 终态 | 落入 **4 个终态**之一（每个 taskId 唯一一条，§6.3 规格 2） | 结果视图出现 |
| 待处理项 | 落 `UNRESOLVED` | 显著展示 |

### 6.3 事件消息的结构（二审补齐：阶段 4 的必交付契约）

**问题**：§6.2 只规定"有哪些事件"，没有规定**消息长什么样**。事件流是阶段 4（接入层）的交付物——没有 schema 就无法实现，也无法验证"界面与证据链同源"（§6.1）。

**每条事件的最小字段**：

| 字段 | 类型 | 说明 |
|---|---|---|
| `seq` | 整数，**单调递增**、任务内唯一 | 前端据此**排序与去重**，不依赖到达顺序 |
| `taskId` | 字符串 | 一次办事请求的标识 |
| `type` | 枚举（**闭集**） | 取 §6.2 的事件类型；新增须登记 |
| `phase` | 枚举 | P1–P6，与证据链六段同源 |
| `status` | 枚举 | `进行中` / `已完成` / `失败` / `不确定` / `不可得` |
| `evidenceRef` | 字符串 | **指向证据链条目的引用**（§6.1：界面展示的内容必须来自证据链） |
| `text` | 字符串 | 人可读摘要；**不得含接口路径、参数名、状态机状态名**（§2.1） |
| `at` | 绝对时刻 | 展示时由前端单向转本地时区（第 06 章 §六） |

**五条规格**：

1. **顺序以 `seq` 为准**。前端**不得**按到达顺序推断步骤（§6.1）。
2. **终态事件唯一**：一个 `taskId` 只允许一条终态事件；重复收到时忽略后到的，并留一条前端日志。
3. **断线重连**：重连时前端携带最后收到的 `seq` 请求续传，服务端从其后重发。**若服务端无法续传，前端必须清空当前轨迹、由终态事件重建**——不得拼接两段互不衔接的轨迹。
4. **`evidenceRef` 必须可解析**：解析不到时按**缺陷上报**（而不是忽略该条），否则界面会静默漏步。
5. **对外接口清单**（端点、方法、请求/响应结构、错误码）与本节同属阶段 4 交付物，实现时必须登记到本章或第 13 章；本节只固定事件流这一条通道。

## 七、视觉规范（Stripe 风格）

**说明**：以下是**取向**，不是完整设计稿。目标是让界面显得"克制、可信、信息密度高但不吵"。

| 项 | 取向 |
|---|---|
| 底色 | 浅色为主；大面积留白 |
| 描边与阴影 | **细描边优先于重阴影**；圆角克制 |
| 色彩 | 主色克制；**颜色只用于表达状态**（三值、待处理），不做装饰性用色 |
| 字体 | 无衬线；正文与代码/标识符用不同字族区分 |
| 层级 | 用**字号与留白**建立层级，而不是用颜色与边框堆叠 |
| 动效 | **只用于表达状态变化**（轨迹条目出现、切到查证态）。不做纯装饰动效 |
| 数据展示 | 时间、状态这类关键值用等宽字体，便于扫读 |

> **一条关于主题的纪律**：界面**必须同时支持浅色与深色**。理由：答辩场地的投影环境不可控，深色在暗环境下更清晰，浅色在明亮环境下更清晰。**这不是审美选择，是风险对冲。**

> **可行性评估点**：需要你确认视觉取向。我判断不了的是：你对 Stripe 风格的具体偏好（是它的**排版克制**，还是它的**渐变与图形语言**）。这两者的实现成本差别很大——**前者靠留白与字重，成本低；后者需要设计稿**。若你只是要"看起来专业"，前者足够。

---

## 八、演示相关：界面要替评委回答什么

**界面的最终验收标准是：评委看完一遍，能自己回答下面四个问题。**

| # | 问题 | 界面靠什么回答 |
|---|---|---|
| 1 | 它真的不动那个老系统吗？ | 界面不出现任何"系统设置/数据管理"入口；**所有演示用数据的变化都通过业务动作发生** |
| 2 | 它怎么知道"不能借"？ | 轨迹视图里的事实来源（跨域）+ 命题判定依据 |
| 3 | 超时的时候它怎么不乱来？ | **"不确定 → 正在查证 → 已确认"** 这段完整过程可见 |
| 4 | 它出错的时候会瞒着我吗？ | `UNRESOLVED` 与待处理项的显著展示 |

**规格**：**这四个问题对应四个必须能被"一眼看到"的界面元素**。若某个元素需要翻三层才能找到，等于没有。

## 九、明确排除的做法

| # | 排除 | 理由 |
|---|---|---|
| 1 | ~~把"不确定"显示成失败或成功~~ | §3.1；会诱导用户犯错或造成假成功 |
| 2 | ~~在"不确定"状态下提供重试按钮~~ | §3.1；此时重试等于绕过查证 |
| 3 | ~~界面自行推断或补全执行步骤~~ | §6.1；界面在演戏会摧毁"可解释" |
| 4 | ~~展示接口 URL、参数名、状态机状态名~~ | §2.1；用户不懂接口 |
| 5 | ~~组件直接调 `fetch` 或直连存量系统~~ | §五；违反分层与"接触面收敛" |
| 6 | ~~把待处理项折叠在次级面板~~ | §2.3；它是最需要被看见的东西 |
| 7 | ~~用颜色做装饰性表达~~ | §七；颜色被占用后，状态就表达不出来了 |
| 8 | ~~只做浅色主题~~ | §七；投影环境不可控 |
| 9 | ~~做对话历史云存储 / 多用户体系~~ | 超出边界（边界文档 §四 速查表）；本项目是单用户演示场景 |
| 10 | ~~为"界面好看"给证据链加装饰性内容~~ | §6.1；证据链是判定依据，不是展示素材 |
