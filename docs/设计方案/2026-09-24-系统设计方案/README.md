# 系统设计方案 · 总纲

> **这份方案是拿来被评估的，不是拿来被执行的。**
>
> 读者：项目作者本人（评估可行性）、后续开发时的执行者、答辩评委（看设计深度）。
> 本方案**不含任何代码**，也不引用任何既有实现的结构。

---

## 一、为什么方案必须先于实现

2026-09-24 曾发生一次交付物越界：在只被要求"写方案"的情况下产出了可运行的实现，随后被降级（见 `docs/变更记录/2026-09-24-交付物越界与降级处置.md`）。

那次失误的要害不是"做多了"，而是**用"可运行"替换了"可评估"**：

| | 方案 | 已完成实现 |
|---|---|---|
| 决策权 | 在评估者手里 | 事实上转移到实现者手里 |
| 推翻成本 | 改一段文字 | 推翻一整套结构 |

所以本方案遵守一条纪律：**每条设计决定都要留下被推翻的空间**——写明它成立的条件、它的备选、它不成立时会怎样。

## 三、颗粒度标准

用户要求：**"方案的颗粒度需要细，要怎么做都去写好，方案所有的内容都要写好。"**

据此定三条硬标准：

### 标准一：写到"能照着做"为止

不出现"合理处理即可""视情况而定"这类话。凡是需要判断的地方，**把判断依据写出来**。

| ❌ 不够细 | ✅ 合格 |
|---|---|
| "调用前要校验教室是否存在" | "调用前需读取教室详情，比对 `status` 字段；判定集合为 `AVAILABLE/ENABLED/NORMAL/未标注` 四个值，其余一律视为不可用并拒绝，拒绝理由需引用实际读到的 `status` 值" |
| "超时要查证" | "超时归入 `UNKNOWN`，进入查证；查证首选跨身份可见的列表接口，且**不带 `keyword`**（该参数语义模糊），拉全量后在内存按 (教室, 时段) 做重叠比对；未命中且列表规模 ≥ 500 条时，结论降级为"查不清"而非"未生效"" |

### 标准二：每条决定必附四件套

1. **决定**：定成什么
2. **为什么**：依据哪条事实 / 哪条不变量
3. **备选与为什么不选**：至少一个被排除的做法
4. **可行性评估点**：见下

### 标准三：不留隐含前提

凡假设了"存量系统会…""用户会…""环境里已有…"，一律显式写出，并标明**这个假设若不成立会怎样**。

## 四、可行性评估点的写法

用户原话：**"方案我还要去评估可行性呢。"**

因此每章的每条关键决定，末尾附一行：

```
> **可行性评估点**：<这里需要你判断什么>。我判断不了的是：<AI 无法确认的部分>。
```

三条纪律：

- **不粉饰**：不成立的条件要写出来，不能只写好处
- **可验证**：尽量给出"怎么验证这件事成立"的具体办法
- **区分两类**：① 需要**用户决策**的（取舍、范围、优先级）② 需要**实测确认**的（技术事实）。不能混着写

## 七、提案阶段发现的一处关键修正（已回填）

撰写第 07 章时发现第 04 章的一处设计缺陷并已修正，记录在此以便追溯：

| 项 | 原设计 | 修正后 |
|---|---|---|
| 副作用的出口 | "只能从提交态发出"，**入边恰好两条**（命题通过 / 查证未命中） | **修正为三条**，增加"补偿就绪"。并明确：**补偿撤销也是副作用，必须走同一个提交态**，复用同一套三值判定与查证 |
| 原因 | —— | 补偿请求同样会超时、同样返回歧义信号。**若给它另开一条路径，它就得不到三值判定的保护**——"补偿失败被误判为成功"是最危险的假成功（以为收回了，其实没收回） |
| 连带修正 | 转移表以 `状态 × 事件` 为索引 | **索引变为 `状态 × 目的 × 事件`**（目的 = 正向写入 / 补偿撤销） |

修正详情见 [04 章 §六 约束一、§5.7](./04-任务编排与状态机方案.md) 与 [07 章 §七](./07-补偿与异常恢复方案.md)。

## 八、需要用户拍板的两件事

### 待决 1：章节以"多文件"还是"单文件"组织

**现状选择**：本方案按 13 章拆成多个文件，放在 `docs/设计方案/2026-09-24-系统设计方案/` 下。

**理由**：13 章合写会是一份数千行的文档，无法分段评审；拆章后可以**逐章评估、逐章推翻**，返工范围可控。

**代价**：与 `研发规范/文档驱动开发规范.md` 中"设计方案为 `YYYY-MM-DD-描述-设计方案.md` 单文件"的命名约定不一致。

> **可行性评估点**：需要你决定是否接受"带日期的目录 + 编号章节"这种组织方式。若你要求严格遵循原有命名约定，我就改回单文件（代价是可读性下降）。我判断不了的是：你的毕设/其他项目里是否已有既成的多章方案组织习惯，应当保持一致。

### 待决 2：可行性评估点的密度

**现状选择**：每章每条关键决定都附一条。

**代价**：文档会变长，阅读时"决定"与"待你判断"交错出现。

**备选**：把评估点集中到每章末尾的"本章待决清单"。

> **可行性评估点**：需要你决定评估点**贴着决定写**还是**集中在章末**。我判断不了的是：你评估时是逐条顺着读，还是会先扫一遍待决清单——这决定哪种更省你的时间。
