# 09 · 故障注入与混沌实验方案

> 本章解决：**凭什么说这个系统在异常下仍然可靠。**
>
> 依据：不变量 I1–I6。前八章是"设计成什么样"，本章是"怎么证明它真的是这样"。
>
> **本章不含代码。** §三 的故障清单与 §五 的实验设计是**规格**。

---

## 一、为什么必须有混沌：否则前八章都是纸面的

**不变量在没有故障的系统上自动成立。** 一句话就够说明问题：

| 不变量 | 正常链路下 | 只有注入故障才能验证 |
|---|---|---|
| I1 事实齐备方可写入 | 自然成立（事实都能取到） | 事实取不到时，系统是否仍不写 |
| I2 至多一条有效记录 | 自然成立（一次只提交一次） | **响应丢失后，系统是否会重复提交** |
| I3 结果唯一确定 | 自然成立（响应都正常） | 超时/冲突时，系统是否会猜 |
| I6 副作用可收敛 | 自然成立（没有需要回收的副作用） | 补偿失败时，系统是否静默 |

**关键判断**：

> **本项目最有价值的几个设计（三值语义、幂等查证、补偿登记）在正常链路上完全看不出来。** 正常链路下，一个只会 `try/catch` 的脚本和本系统的行为**一模一样**。
>
> **所以混沌不是"额外的测试"，它是本项目核心主张的唯一证伪方式。**

### 1.1 混沌的第二个作用：可重放的故障

"容错"这件事有个很难绕过的验证障碍：真实故障**不可控、不可重放**。

| 若靠真实故障验证 | 问题 |
|---|---|
| 拔网线 | 无法精确控制"在哪一步断" |
| 等真的超时 | 不可复现，无法回归 |
| 让服务端出错 | 做不到（我们不改它） |

**所以必须自己注入**——而且注入必须是**命令式的、确定性的、可重放的**（§六）。

## 二、注入点：在接触层的出站通道上，不动存量系统

**决定：故障注入实现在**编排引擎接触层的出站管道**中，作为一个可插拔环节。不在存量系统进程内，也不在它前面另起一个代理进程。**

| 位置候选 | 评价 |
|---|---|
| **① 接触层出站管道（采用）** | 所有请求都必须经过这里（第 02 章 §四 约束 A：唯一 HTTP 出口）。**注入点天然唯一**，与"唯一出口"这条约束同源 |
| ② 存量系统进程内 | **绝对不可**——需要改它的代码，违反零侵入；且注入会污染它的行为 |
| ③ 另起一个代理进程夹在中间 | 可行但多余：需要改配置指向代理，多一个进程与一个配置项，且"唯一出口"这条约束的检查会变模糊 |
| ④ 在存量系统前面挂 Nginx 做故障 | 它自带的 `nginx/` 目录是给前端用的；用它做故障注入需要改它的配置文件 |

> **① 的最大优点是"注入点在结构上唯一"**：只有一处能发请求，因此也只有一处能注入。**不需要额外保证"注入点不被绕过"**。

### 2.1 撤防状态必须"零差异"

**规格（这是本章最重要的一条实现纪律）**：

> **撤防时，请求与响应必须与"根本没有这套机制"完全一致——不是"差不多一致"。**

| 若做不到 | 后果 |
|---|---|
| 撤防时仍多一次拷贝/一次重写 | 可能改变请求体形状（如多出/丢失字段），导致**实验中的失败无法归因**（是注入的故障，还是撤防路径引入的差异？） |
| 撤防时仍有极小的延迟 | 演示时无法宣称"这就是真实性能" |
| 撤防与开启路径的代码不同 | 两套路径会各自演化，**实验验证的就不再是生产路径** |

**检查方式**：撤防状态下跑一遍正常链路，与"完全不带注入代码"的行为逐项对比（请求体、响应体、耗时量级）。**这个对比本身是一次实验（D0）。**

## 三、故障类型清单

**每条都必须标明：它模拟什么现实故障、它考验哪条不变量。**

| # | 故障 | 模拟的现实 | 考验的不变量 |
|---|---|---|---|
| **T1** | **超时（未到达服务端）** | 网络不通、服务端卡住、请求被丢弃 | I3 |
| **T2** | **慢响应** | 服务端负载高 | I3（是否会在未超时前就误判） |
| **T3** | **服务端错误（5xx）** | 服务端内部错误 | I3（**写接口 5xx 是否被误判为失败**） |
| **T4** | **连接断开** | 网络抖动、对端主动断开 | I3 |
| **T5** | **★ 响应丢失（半成功）** | 请求已到达并处理，响应在返回途中丢失 | **I2**（最重要的一条） |
| **T6** | **业务错误码**（`HTTP 200 + code 400/403/409`） | 参数错 / 越权 / 冲突 | I2、I3、I5 |
| **T7** | **身份凭证失效**（401） | token 过期、Redis 未启动 | I5 |
| **T8** | **慢到刚好超时**（边界） | 服务端在超时值附近返回 | I3（边界上是否会被误判） |

### 3.1 ★ T5 的注入方式：**丢弃响应**，而不是伪造响应

**这是本章技术含量最高的一条，也是最容易被做错的一条。**

| 做法 | 能不能证明我们的设计有效 |
|---|---|
| **伪造一个超时**（不发请求，直接报超时） | ❌ **不能**。它只证明了"报超时的时候我们会去查证"，**没有证明"库里真的有一条记录时我们能查到它"** |
| **转发请求 → 让它真实写库 → 响应返回时丢弃** | ✅ **能**。它完整复现了"服务端已提交、客户端没收到"这一现实，且**库里的那条记录是真实存在的**——查证能不能找到它，才是真正被测的东西 |

**规格**：

1. 请求**必须真实转发**给存量系统，让它**真实写库**
2. 响应**必须在客户端侧被丢弃**（不进入判定流程），**并且判定为超时**
3. 注入记录里必须标明"本次请求已真实到达服务端"

> **这一条决定了 D2 实验的效力。** 若用"伪造超时"，整个 D2 实验就是自欺——因为它依赖的那个前提（库里已有一条记录）根本没发生。

## 四、每类故障的预期行为（规格）

**这张表就是"如果行为不符，说明设计有洞"的判据。**

| 故障 | 接口类型 | 期望的判定 | 期望的后续 | 若不符，说明 |
|---|---|---|---|---|
| T1 超时 | 写 | `UNKNOWN` | 进查证 → 未命中 → 允许重试一次 | 把超时当失败 → 可能重复提交 |
| T1 超时 | 读 | **可安全重试**（有限次） | 重试成功则继续；超限则标"事实不可得" | 读接口也进查证 → 无谓地放大开销 |
| T2 慢响应 | 写 | 未超时则正常判定 | 超时则同 T1 | 用"耗时"判成败 → 错误的判定依据 |
| T3 5xx | 写 | `UNKNOWN` | 进查证 | 判失败 → 重复提交（**这是最常见的错误直觉**） |
| T3 5xx | 读 | 可安全重试 | —— | —— |
| T4 断连 | 写 | `UNKNOWN` | 进查证 | 同上 |
| **T5 响应丢失** | 写 | `UNKNOWN` | 查证**命中** → 判"已成功" → **不重复提交** | 直接重试 → **库里两条**（本项目要消除的头号场景） |
| T6 `code 409` | 写 | `UNKNOWN` + **歧义标记** | 查证 → 区分"我写的"/"别人占的" | 当成功或当失败 → 误报 |
| T6 `code 403`（方法层越权） | 写 | **`FAILURE`（身份错）** | 登记为**系统缺陷** | **判成功 → 假成功，静默** |
| T6 `code 400` | 写 | `FAILURE` | 登记为缺陷（本地校验本该拦住） | 判成功 → 假成功 |
| T7 401 | 写 | `FAILURE`（凭证） | **不允许刷新凭证后直接重试**，须先查证 | 直接重试 → 可能重复写入 |
| T7 401 | 读 | 可刷新凭证后重试 | —— | —— |
| T8 边界超时 | 写 | `UNKNOWN` | 同 T1 | 边界上出现不一致行为 |

> **注意 T3 那一行**。它是**"正确设计"与"直觉"分歧最大的一处**：
>
> 几乎所有人写 HTTP 客户端时都会把 5xx 当失败。**在写接口上这是错的**——5xx 意味着"服务端在返回前出错了"，而**请求可能已经被处理**。
>
> 这条在答辩时值得单独讲：**它不是常识，它是从"响应丢失"这个现实反推出来的。**

## 五、实验设计

**每个实验必须包含五要素**：假设、注入、期望、**证伪条件**、证据采集。

> **"证伪条件"是必须写的一栏。** 一个没有证伪条件的实验，只能"通过"，不能"发现问题"——它证明不了任何东西。

---

### D0 · 撤防对照（基线）

| 项 | 内容 |
|---|---|
| **假设** | 撤防状态下，系统行为与"没有故障注入机制"完全一致 |
| **注入** | 无（撤防） |
| **期望** | 正常链路走通；请求体、响应体、耗时量级与直接调用存量系统一致 |
| **证伪条件** | 撤防时请求体形状发生变化，或耗时出现量级差异 |
| **证据** | 请求/响应体快照对比；耗时分布 |

---

### D1 · 超时但未写入

| 项 | 内容 |
|---|---|
| **假设** | 请求未到达服务端时，系统不会误判为失败并重复提交 |
| **注入** | T1（**不转发**，直接判超时） |
| **期望** | 判 `UNKNOWN` → 查证 → **未命中** → 允许重试 → 重试成功 → 终态 `DONE`；**库中恰好 1 条** |
| **证伪条件** | ① 库中出现 2 条 ② 用户看到"失败"但实际成功 ③ 查证未命中却被判为"不能重试" |
| **证据** | 判定序列（含规则行号）；查证过程；**实验前后按业务键的库内计数** |

---

### D2 · 响应丢失（半成功）★ 核心实验

| 项 | 内容 |
|---|---|
| **假设** | 服务端已写入但响应丢失时，系统能通过查证发现"其实成了"，从而**不重复提交** |
| **注入** | T5：**真实转发 → 真实写库 → 丢弃响应** |
| **期望** | 判 `UNKNOWN` → 查证 → **命中**（且 Q1="是我写的"、Q2="时段重叠"）→ 终态 `DONE`（幂等命中）→ **库中恰好 1 条**；用户被告知"已办成"而非"失败" |
| **证伪条件** | ① 库中出现 2 条 ② 用户被告知失败（而库里实际有一条）③ 查证未命中（说明查证能力不足以发现真实存在的记录） |
| **证据** | **注入记录（标明请求已真实到达）**；查证命中的记录号；库内计数；用户可见的话术 |
| **为什么它是最重要的一个** | 它是**唯一能证明"幂等查证真的有用"**的实验。没有它，"我们会查证"这句话无法被验证 |

> **D2 是三值语义存在的唯一理由。** 若把超时当失败，D2 的期望结果就变成"库中 2 条"——**这正是本项目要消除的场景**。

---

### D3 · 409 歧义的两种真相

| 项 | 内容 |
|---|---|
| **假设** | 同一个 `409` 响应，系统能通过查证区分"自己已成功"与"他人已占用"，并给出**不同的**用户答复 |
| **注入** | T6（`code 409`）；分两个子场景 |
| **子场景 A**（自己已成功） | 先由本系统成功提交一次（不注入）→ 再注入 409 重复提交 → 期望：查证命中**我写的** → 终态 `DONE`（或按第 06 章待决 1 的话术），**不产生新记录** |
| **子场景 B**（他人占用） | 先用另一个身份直接占用该时段 → 本系统提交 → 注入 409 → 期望：查证命中**别人写的** → 终态 `REJECTED`，话术为"该时段已被人预约" |
| **期望（共同）** | 两种子场景的**判定相同（UNKNOWN）**，但**终态与话术不同** |
| **证伪条件** | ① 两个子场景给出相同话术（说明系统没有真正区分）② 任一子场景产生新记录 |
| **证据** | 两种子场景的完整证据链对比；结论差异 |

> **D3 的价值在于展示"系统知道自己不知道"**：判定阶段的结论是相同的（`UNKNOWN` + 歧义标记），**区分发生在查证阶段**。这个"分层"正是设计的深度所在。

---

### D4 · 权限错判（假成功防线）

| 项 | 内容 |
|---|---|
| **假设** | `HTTP 200 + code 403`（方法层越权）**不会**被误判为成功 |
| **注入** | T6（`code 403`，HTTP 200） |
| **期望** | 判 `FAILURE`，原因分类为**身份错**；**登记为系统缺陷**；用户看到"系统配置异常"而非"预约成功" |
| **证伪条件** | 判定为 `SUCCESS`（**假成功**）；或原因被归类为普通业务失败（缺陷被掩盖） |
| **证据** | 判定结论与原因分类；缺陷登记记录 |
| **附加子场景** | `HTTP 403`（过滤器层拒绝）走同一实验，验证两条表达**都被覆盖** |

> **这个实验验证的是"最容易写错的一行代码"**：把 HTTP 状态码当成功判据。它同时也是演示时最有说服力的一幕——**因为"以为自己成功了，其实没有"是所有人都有过的体验**。

---

### D5 · 补偿失败必须被登记（依赖第 07 章待决 1）

| 项 | 内容 |
|---|---|
| **假设** | 补偿失败时，系统不会静默吞掉，而是落 `UNRESOLVED` 并生成待处理事项 |
| **前置** | **需要存在一个"多步写入"场景**——若第 07 章待决 1 选 A（不做多步场景），**本实验无法执行** |
| **注入** | ① 让第二步失败 ② 让补偿（撤销）也失败 |
| **期望** | 终态 `UNRESOLVED`；生成可被人独立复现的待处理事项 |
| **证伪条件** | 落 `FAILED`（抹掉"可能有残留"）；或没有任何可见记录 |
| **证据** | 终态；待处理事项内容（是否含记录 id、业务键、失败原因、时刻） |

> **若第 07 章选 A（不做多步场景），本实验应改为"验证不可补偿写操作的禁令"**：尝试让 `logi.maintenance.create` 进入自动链路，验证它**在结构上无法被引用**（第 04 章 §六 约束三）。这同样是一个有效的实验，且不需要新场景。

---

### D6 · 只读故障不影响写路径

| 项 | 内容 |
|---|---|
| **假设** | 只读接口的故障处置（可重试）与写接口的处置（须查证）**互不干扰** |
| **注入** | 同时向只读接口注入 5xx/超时，写接口正常 |
| **期望** | 只读重试后恢复 → 链路继续 → 写入正常；**写路径的行为不因只读接口的故障而改变** |
| **证伪条件** | 只读故障导致写接口被误判；或整个任务因为只读抖动而中断（本可恢复） |
| **证据** | 两类接口的处置序列 |

---

### D7 · 实验性对照：提示词含/不含接口信息（可选）

| 项 | 内容 |
|---|---|
| **假设** | 提示词不告诉模型有哪些接口时，意图与槽位抽取的准确率**不下降**（第 03 章 §六） |
| **注入** | 无（这是模型实验，不是故障注入） |
| **方法** | 固定一组输入样本（含正常、模糊、超域、多义），分别用两版提示词各跑一遍，比对准确率 |
| **证伪条件** | 不含接口版本的准确率显著更低（说明该假设不成立，需重新论证第 03 章 §六） |
| **证据** | 样本集、两版提示词、逐条比对结果 |
| **样本量** | **需实测**（第 03 章待决 6）。**注意**：样本量太小会得出噪声结论，需先定一个最低样本数 |

> **这个实验与其他实验性质不同**：它验证的是"某个设计选择是否成立"，而不是"某个不变量是否被维护"。**但它同样需要证伪条件**——所以列在这里。

## 六、可控性与可重放

**混沌实验若不能重放，结论就不可信。三条要求：**

| # | 要求 | 做法 |
|---|---|---|
| 1 | **输入确定** | 用**结构化任务**路径（第 03 章 §十），绕开模型。这样失败必定来自注入，而非模型的随机性 |
| 2 | **注入确定** | 注入是**命令式**的：明确指定"第 N 次调用 / 哪个接口 / 注入什么故障"。**禁止使用随机故障注入**（随机无法重放，也无法归因） |
| 3 | **环境确定** | 每次实验前**复位数据**到已知状态（第 11 章）；记录实验时的环境快照（版本、配置） |

> **第 2 条要强调**：很多混沌工程实践用随机注入（"5% 的请求失败"）。**本项目不用**——理由是随机注入会让"这次失败是设计缺陷还是概率使然"无法回答。**我们要的是"可控的证明"，不是"概率的信心"。**
>
> **代价**：无法发现"罕见的偶发问题"。**这个代价可以接受**——本项目的目标不是覆盖所有故障分布，而是**证明几条具体的设计在特定故障下成立**。

### 6.1 实验的确定性检查

**规格**：同一个实验**连续跑 N 次**（N ≥ 3），结果必须**完全一致**（判定序列、终态、库内计数）。

| 若不一致 | 说明 |
|---|---|
| 判定序列不同 | 存在未受控的输入源（如模型被意外调用） |
| 库内计数不同 | 存在并发或残留数据未清理 |
| 终态不同 | 存在非确定性分支（**这是最严重的问题，说明设计里有未覆盖的分支**） |

## 七、默认撤防

**不变量：演示路径上不得存在默认开启的故障注入。**

| 项 | 规格 |
|---|---|
| 默认值 | **撤防**（关闭） |
| 开启方式 | **显式**指定实验编号与注入点；不允许"开着但没命中"的模糊状态 |
| 开启时的可见性 | 一旦有注入生效，**必须在结果与证据链中显式标注"本次运行包含注入"** |
| 演示时的纪律 | 演示路径**必须是撤防状态**；注入只在与演示分离的实验环节使用 |
| 撤防的验证 | D0 实验 |

> **"开启时必须可见"这条容易被忽略但很重要**：若某次演示中无意带着注入开启，评委看到的"失败"可能是注入造成的——**那就成了自己骗自己**。让注入在所有输出上留下痕迹，是防止这种事故的唯一办法。

## 八、每次实验必须产出的证据

**实验的产物不是"通过/不通过"，是一份可被第三人复核的记录。**

| # | 证据 | 用途 |
|---|---|---|
| 1 | **注入配置**（哪个接口、第几次调用、什么故障） | 复现 |
| 2 | **请求序列**（含每次使用的身份、参数形状） | 复现；检查身份选择是否正确 |
| 3 | **每次调用的三值判定 + 命中的规则行号** | 验证第 05 章的规则表被正确执行 |
| 4 | **查证过程与结论**（查了几条、命中哪一条、Q1/Q2 的答案） | 验证第 06 章的查证逻辑 |
| 5 | **最终终态 + 用户可见话术** | 验证 I4（用户看到的是对的） |
| 6 | **★ 实验前后按业务键的库内计数** | **唯一能证明"没有重复写入"的证据** |
| 7 | 是否发生缺陷登记（身份错/参数错的次数） | 验证 M3（把不合格请求挡在外面） |

> **第 6 项必须真的去查库。** 只看系统自己的报告是循环论证——系统说自己只提交了一次，而我们要验证的正是"系统有没有说真话"。
>
> **注意**：查库是**只读**，不违反"不直接写它的数据库"（M2）。**只读与只写的边界要写清楚。**

## 九、明确排除的做法

| # | 排除 | 理由 |
|---|---|---|
| 1 | ~~靠真实故障（拔网线、等服务端真出错）验证~~ | §1.1；不可控、不可重放 |
| 2 | ~~修改存量系统来注入故障~~ | 违反零侵入 |
| 3 | ~~另起一个代理进程做注入~~ | §二；多余，且会淡化"唯一出口"这条约束 |
| 4 | ~~伪造响应（不真正转发）来模拟响应丢失~~ | §3.1；没有真实写库，就验证不了查证能力 |
| 5 | ~~随机比例注入故障~~ | §六；无法归因，结论不可信 |
| 6 | ~~用自然语言路径做混沌实验~~ | §六 要求 1；模型的随机性会污染归因 |
| 7 | ~~把"实验通过"作为产出~~ | §八；产出应是可复核的证据 |
| 8 | ~~在演示路径上保持注入开启~~ | §七 |
| 9 | ~~注入生效时不作标注~~ | §七；会让"看到的失败"无法归因 |
| 10 | ~~只跑一次就下结论~~ | §6.1；需连续 N ≥ 3 次结果一致 |
