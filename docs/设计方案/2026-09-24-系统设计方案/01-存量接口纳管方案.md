# 01 · 存量接口纳管方案

> 本章解决：**我们的系统以什么方式接触存量系统。**
>
> 这是整个方案里风险最高的一章——因为其他章节出错只影响我们自己，这一章出错会**污染别人的数据**。
>
> 事实依据：`docs/基线文档/存量系统改造说明.md`（§七 实测记录、§八 能力探针、§九 文档与实现不一致清单）。本章不做新的实测断言，凡引用的事实均标注出处。

---

## 一、先说清楚风险

「对接存量系统」这句话听起来是技术问题，实际上是**责任问题**。我们把请求发出去之后，它产生的后果落在**不属于我们的数据库**里。

三类不可逆的后果：

| 后果 | 怎么发生 | 为什么不可逆 |
|---|---|---|
| **脏数据落库** | 我们的判定错了，把一个不该成立的申请提交上去 | 存量系统没有业务唯一约束（`存量系统改造说明.md` §七.3），错的数据会真实存在，且**它自己的使用者会看到** |
| **数据被耗尽** | 演示/测试反复提交，把演示用的时段占满 | 占用是真实的，别人（或下一场演示）就用不了了 |
| **权限被滥用** | 图省事全程用 `ADMIN` 身份 | 一旦形成习惯，最小身份原则失效；且任何一次越权读写都无法解释 |

**因此本章的立场是：默认不纳管，逐条论证后才纳管。**

---

## 二、纳管判据（四条，缺一不纳管）

| # | 判据 | 不满足时的后果 | 对应约束 |
|---|---|---|---|
| **N1** | **有明确业务用途**——服务于某个已登记意图的某个步骤 | 会攒下一堆"以后可能有用"的接口，扩大接触面 | — |
| **N2** | **结果可判定**——调用返回后能唯一确定 `SUCCESS`/`FAILURE`/`UNKNOWN` | 结论悬空，无法向用户交代 | 不变量 I3 |
| **N3** | **若产生副作用，必须可查证**——有路径能在事后确认"到底生效没有" | `UNKNOWN` 永远收敛不了，只能猜 | 不变量 I3 |
| **N4** | **若产生副作用，必须可补偿，或显式登记为不可补偿** | 半成功状态无人知晓，数据留在中间态 | 不变量 I6 |

**N3 与 N4 是硬门槛。**

> **编号域声明（二审修正）**：本表原先编号 `J1–J4`，与决策汇总 §十三 的架构一审新增项 `J1–J7` **撞号**（例如"J3"既可指本表的"必须可查证"，也可指实测项"预约记录有效状态集合"）。**本表已改为 `N1–N4`，此后 `J#` 专指决策汇总 §十三/§十四 的新增项，`N#` 专指本章的纳管判据。** 改名的原因是撞号会让"J3 需实测"这类句子无法判断指哪一条。

> 判据的依据：`智能体设计.md` §三"判定原则"。特别是其中一条——**没有查证路径的接口，不得进入可编排清单**。

## 三、接口标识规范

**决定**：每个纳管接口分配一个稳定标识，形如

```
<域>.<资源>.<动作>
```

- 域：`auth`（认证）｜`edu`（教务侧）｜`logi`（后勤侧）
- 资源：单数名词
- 动作：`detail` / `list` / `create` / `cancel` / `available` / `reservedSeats`

**为什么不用 URL 作为标识**：

| 理由 | 说明 |
|---|---|
| URL 是会变的外部事实 | 存量系统升级、反向代理改前缀（本项目已经发生过一次：文档写 `/api`，真实路径没有），标识若等于 URL，它一变全项目引用全断 |
| 编排逻辑需要引用"业务动作"而非"地址" | 状态机关心的是"我要提交一次教室预约"，不是"我要 POST 到 /reservations/classrooms" |
| 域是设计信息 | `edu` 与 `logi` 的区别不是部署区别（它们跑在同一个进程里），而是**权限域与事实域**的区别。这个信息必须进标识 |

> **可行性评估点**：需要你确认这个命名法是否够用。我判断不了的是：将来若要纳管**真正异构的第三方系统**（不同厂商、不同部署），域的划分是否还应该以"权限域"为准，还是应该引入"系统来源"这一维度。

## 四、元信息字段定义

**决定**：每个纳管接口必须声明下列字段。少一个字段，就少一道防线。

| 字段 | 含义 | 为什么必须声明 | 省略的后果 |
|---|---|---|---|
| `标识` | 见 §三 | 被编排逻辑引用 | — |
| `域` | `edu` / `logi` | 决定用哪个身份 | 用错身份 → 静默 403，被当成"业务失败" |
| `方法 + 真实路径` | HTTP 契约 | 网关据此发起调用 | 硬编码路径散落各处，改一次要全局搜索 |
| `用途` | 一句话说明它干什么 | 人读；防止纳管了却没人记得为什么 | 接口清单变成垃圾场 |
| `所需身份` | 调用它的最小角色 | **最小身份原则（I5）** | 退化到"全用 ADMIN" |
| `是否有副作用` | 是否改变存量系统的状态 | 决定它能否被自动执行、能否重试 | 把写接口当只读接口用 → 静默改数据 |
| **`是否允许自动编排`**（二审补齐） | 该接口能否被意图计划引用、进入自动执行链路 | **决定它能否进入自动链路**。它与"是否有副作用"是**两个维度**（§七 M8）：不可补偿的写操作有副作用，但必须禁止自动编排 | 不可补偿的写操作进入自动链路 → 制造无法回收的副作用 |
| `幂等业务键` | 形如 `教室 + 时段` 的业务唯一标识 | 查证时用来确认"这条是不是我写的" | 查证无从比对 |
| `查证路径` | 用哪个接口、什么口径查证 | **N3 硬门槛** | `UNKNOWN` 无法收敛 |
| `补偿动作` 或 `不可补偿登记` | 失败后如何撤销，或明确声明撤不了 | **N4 硬门槛** | 半成品留在库里 |
| `前置命题` | 调用前必须成立的业务条件 | 驱动事实收集；把不合格请求挡在存量系统之外 | 漏查条件 → 脏数据 |
| `适配器` | 用哪套响应解析规则 | 吸收协议异构 | 判定规则散落 |
| `实测注意事项` | 每一条都是实测结论 | **防止后人按直觉改** | 后人"顺手修好"，破坏判定 |

`幂等业务键` 对**补偿动作**可豁免——重复撤销的影响天然幂等（记录已不存在）。

> **可行性评估点**：这套字段能否覆盖将来可能的接口形态？我判断不了的是：若某天要纳管一个**异步接口**（提交后返回任务号，结果稍后才出），现有字段没有地方表达"轮询查证"，需要新增字段。是否现在就要为它预留？

## 五、纳管清单（共 12 条）

**写接口 4 条，自动编排资格分三档（三审核准，D2/M8）**：① **允许自动编排 2 条**——`edu.reservation.classroom.create`（主链路写入）与 `edu.reservation.cancel`（补偿动作，由补偿清单自动触发）；② **纳管但不进入自动编排 1 条**——`edu.reservation.seat.create`（决策 D2：座位预约非主链路，注册表保留完整记录但**不被任何意图计划引用**，仅用于说明粒度边界）；③ **禁止自动编排 1 条**——`logi.maintenance.create`（演示工具，仅脚本/人工触发，M8）。

### 身份分布

| 身份 | 条数 | 接口 |
|---|---|---|
| ADMIN | 3 | `logi.maintenance.list`、`logi.reservation.list`、`logi.maintenance.create` |
| TEACHER | 5 | `edu.classroom.*`、`edu.reservation.classroom.create`、`edu.reservation.mine`、`edu.reservation.cancel` |
| STUDENT | 1 | `edu.reservation.seat.create` |
| 无 | 1 | `auth.login` |

> ¹ **发起时身份**（一审更正）：`edu.reservation.mine` 只返回**当前身份**的预约（第 06 章 §五 路径②），查证时必须使用**发起写入时的同一身份**——教室预约查证为 TEACHER，座位预约查证为 STUDENT。注册表写死单一角色会在这条接口上造成身份错配。
>
> **凭证刷新（一审提出，**三审 J5 已拍板**）**：纳管清单未包含 token 刷新接口（access token 实测有效期 30 分钟）。**`auth.login` 兼作刷新路径**：读接口遇 401 按 R6 透明重登后重试；写接口遇 401 严格按 W7（先查证，不得直接重试）。不为此新增纳管项。

**这张表是本作品立论的核心证据**：判定"这间教室这个时段能不能借"，需要三份事实——教室状态（edu）、时段占用（edu）、维修窗口（**logi**）。第三份**只有 `ADMIN` 身份读得到**（实测 `TEACHER` 被拒，HTTP 403，`存量系统改造说明.md` §八.3）。

→ **一次简单的借教室，在权限维度上就不可能由单一身份完成。** 多身份编排不是设计偏好。

## 六、逐接口设计

以下按"事实查询 / 写入 / 查证与补偿 / 演示工具"四组展开。

### 6.1 事实查询（教务侧）

---

#### ① `edu.classroom.detail` — 教室详情

| 项 | 内容 |
|---|---|
| 用途 | 把人类可读的教室名（"数智楼222"）解析成系统标识；同时读取 `status` |
| 服务于 | 两个意图的第 1 步（借教室 / 可用性查询） |
| 契约 | `GET /classrooms/{id}`；身份已登录即可（TEACHER） |
| 副作用 | 无 |
| 前置事实 | 无 |

**设计要点**：`status` 是教室可用性的**三个来源之一**（另两个是时段占用、维修窗口）。三者必须**全部**检查——只查任意两个都会漏。

**判定口径**（写成规格，避免各处分头判断）：

- `status` ∈ {`AVAILABLE`, `ENABLED`, `NORMAL`, 未标注} → 视为启用
- 其余值 → 视为不可用，**拒绝理由必须引用实际读到的值**

为什么把"未标注"算作可用：它的可用性由另外两个来源兜底；若此处也拦截，会造成"三处都不放行"的死锁。这是**保守与可用的取舍**——宁可让另外两个来源拦截，也不让一个空字段变成否决权。

> **可行性评估点**：需要你确认"`status` 为 `null` 视为可用"这个取舍。我判断不了的是：存量系统里 `status` 为空的实际语义是"未设置"还是"未知"——这需要查它的数据分布。若实测发现空值占比很高，说明该字段不可靠，那就应该改为"空值 → 不放行"（宁可多拦）。

---

#### ② `edu.classroom.available` — 按条件筛选教室

| 项 | 内容 |
|---|---|
| 用途 | **降级换教室时**，按楼栋与容量挑候选 |
| 服务于 | 降级策略（目标教室被占时自动换一间） |
| 契约 | `GET /classrooms/available_list`；参数 `building`、`min_capacity` |
| 副作用 | 无 |

**实测约束**（三审补为五条，每条都会导致错误，必须写进规格）：

| 约束 | 实测事实 | 规格要求 |
|---|---|---|
| **没有时间参数** | 它的参数只有楼栋与容量，**答不了"这个时段是否可用"** | **禁止**用它做时段冲突判定。它的输出只是**候选池**，候选池的每一项仍须逐项走完整的时段校验 |
| **`min_capacity` 必填** | 缺失时返回**业务码 500**（三审复测一致） | 调用方**必须**显式传值；不限容量时传 `0` |
| **`building` 事实必填**（三审新增） | **不传 `building` 返空列表**（SQL `building = NULL` 比较恒假），并非返全量 | 必须以原教室楼栋为参数（第 08 章 §8.1 同楼栋基准）；空结果只表示"无候选" |
| **它会返回已被占用的教室** | 它不考虑时段占用 | 同上：结果**不可当真**，只是候选 |
| **候选池规模（三审实测 C2）** | 数智楼 5 间（容量 48/48/55/32/9）：≥48 仅 111/123/222，≥55 仅 222；全系统 7 间 | 候选上限 **K=5**；**222 是全栋最大容量，不能作为降级起点**（三审演示口径：主角 123/48 座，见第 12 章） |

> ⚠️ 第 1、4 条与 `存量系统改造说明.md` §六 N5 同源。**这条"缺陷"是我们的立论支点**：正因为这个接口答不了"现在能不能用"，才逼出了跨接口聚合。**不要试图绕过它，也不要试图修好它。**

> **三审已实测**：候选池规模见上表——数智楼扣除主角后候选天然 ≤ 4，K=5 已留余量，逐项校验不会造成可感知等待（与只读调用 avg 14ms 的样本相称，决策汇总 §10.1 B3）。

---

#### ③ `edu.classroom.seats` — 座位布局

| 项 | 内容 |
|---|---|
| 用途 | 读取座位的 `id` / `seatNumber` / `status` |
| 服务于 | 目前**服务于座位粒度的对照场景**，不在主链路上 |
| 契约 | `GET /classrooms/{id}/seats` |

**设计决定**：**主链路（教室级借用）不依赖它。**

为什么：主业务是整间教室粒度，座位布局对"能不能借"没有贡献；纳管它只是为了在演示"粒度差异"时有据可依。

> **可行性评估点**：需要你决定它是否保留在纳管清单里。我判断不了的是：答辩时"粒度差异"这条是否需要单独展示——若不需要，它可以从清单里去掉，进一步缩小接触面。

---

#### ④ `edu.classroom.reservedSeats` — 时段占用

| 项 | 内容 |
|---|---|
| 用途 | 判断"该时段该教室是否被占" |
| 服务于 | 借教室意图的事实收集；可用性查询意图 |
| 契约 | `GET /classrooms/{id}/reserved_seats`，入参 `start_time`/`end_time`（**带 `Z` 的偏移时间**） |
| 副作用 | 无 |

**这是整个项目最重要的一处陷阱，必须逐条写清：**

**陷阱一：读写粒度不一致。** 它返回的是**座位 ID 数组**，而写操作是**整间教室粒度**。中间需要有一步"推导"。

**推导口径**（统一在此规定，禁止别处另行判断）：

| 返回情况 | 推导结论 |
|---|---|
| 占用座位数 > 0，且 ≥ 教室容量 | 视为**整间不可用** |
| 占用座位数 > 0，但 < 教室容量 | 视为**部分占用** → 仍判定为不可用（写操作没有"部分"这个概念） |
| 占用座位数 = 0 | 座位层面空闲 → **继续核对整间教室预约**（见下一步） |

**陷阱二（★ 最要紧）：返回全量座位时，原因不可区分。**

已核实到源码层（`存量系统改造说明.md` §八，`ReservationServiceImpl` 的判定分支）：**「整间教室已被预约」与「教室正在维修中」被合并成同一个返回值。**

```
若 (整间教室预约冲突 或 维修窗口冲突) → 返回该教室的全部座位
```

也就是说：调用方看到"返回了全部座位"，**无法判断是哪种原因**。而两者的应对方式完全不同：

| 真实原因 | 正确应对 |
|---|---|
| 整间被预约 | 换时段，或换一间教室 |
| 正在维修 | 该教室在这段时间内都不可用 —— 换教室更合适，且应当告知用户原因 |

**要区分，只能换 `ADMIN` 身份去后勤域查维修窗口。**

→ **这就是"跨权限域聚合"成为技术必然、而非设计选择的那一行代码。** 这是本作品最硬的一条证据，答辩时应直接引用它。

**规格要求**：命中"全量座位"时，判定理由中**必须**包含"此信号可能是整间预约，也可能是维修中，需交叉判定"的说明，且必须携带一个 `signalIsAmbiguous` 标记进入证据链。

> **可行性评估点**：需要你确认——当判定为"整间不可用"但**后勤域事实取不到**时（例如 ADMIN 身份失效），应当**保守拒绝**还是**按"被占"处理并降级换教室**。我判断不了的是：哪种更符合你演示时的期望。**我的倾向是保守拒绝**（判定原则：事实不齐不得假设其成立），代价是可用性下降。

#### ⑤ `logi.maintenance.list` — 维修窗口

| 项 | 内容 |
|---|---|
| 用途 | 判断"该教室该时段是否在维修窗口内" |
| 服务于 | 借教室意图；可用性查询意图 |
| 契约 | `GET /admin/maintenance`，可用 `classroomId` 过滤 |
| 身份 | **ADMIN**（实测 `TEACHER` / `STUDENT` → HTTP 403，过滤器层拒绝） |
| 副作用 | 无 |

**判定口径**（写成规格；三审 C4/C8 实测后定稿）：

- **生效中 = `status='ACTIVE'`**：三审实测枚举只有 `ACTIVE/CANCELLED` 两态（无定时过期作业），admin 列表默认含 CANCELLED、冲突 SQL 只计 ACTIVE
- 失效集合在**实现常量**中仍按排除法写：`CANCELLED/CANCELED/FINISHED/EXPIRED/CLOSED`（实测命中的是 CANCELLED；其余为向前兼容的防御性扩展——存量系统若新增状态，未登记即拦，代价对称）
- 生效中 **且** 时段与申请时段**严格重叠**（`start < 对方end AND end > 对方start`，**不含边界**，第 06 章 §6.4）→ 判定不可用

**为什么用排除法而不是白名单**：这是**保守优先**的取舍。

- 漏放一个"其实在维修"的教室 → 会向存量系统写入脏数据，**后果不可逆**
- 多拦一次 → 用户只是被提示换个时段，**后果可逆**

两者代价不对称，所以选择"宁可错拦"。

**命名异构注意**：出参是 camelCase（`resourceType`/`resourceId`/`startTime`），与入参的 snake_case 不一致。适配层处理，**不要**下沉到判定逻辑。

**演示数据现状**：种子数据里两条维护窗口**均为 `CANCELLED`**——即"当前没有教室在检修"。想演示"教室在检修"，**必须现场创建**（见 §6.4）。

> **可行性评估点**：需要你确认排除法这个口径。我判断不了的是：存量系统是否有其他**表示失效但不在上述集合里**的状态值。这需要查它的状态枚举定义或数据分布；若发现遗漏，应补进失效集合。

### 6.2 事实查询（后勤侧，跨权限域）

#### ⑥ `logi.reservation.list` — 管理端预约列表（**查证支点**）

| 项 | 内容 |
|---|---|
| 用途 | ① 查证"某次写入是否已生效" ② 收集跨身份的场所占用事实 |
| 身份 | **ADMIN** |
| 副作用 | 无 |

**为什么它是整个幂等机制的支点**：它**跨身份可见**——Agent 提交时用 `TEACHER`，查证时用 `ADMIN`，靠这个切换才能确认"别人（或我自己）是不是已经占用了"。

**五条实测约束**（第五条为架构一审新增，故本节标题由"四条"更正为"五条"）：

| 约束 | 事实 | 规格要求 |
|---|---|---|
| **`keyword` 不可信** | `keyword=4` 实测命中 16 条——`user_id/resource_id/reason` 三字段 CAST 模糊匹配（三审核准） | **禁止**使用 `keyword` 做精确过滤；**查证时一律不带该参数** |
| **不带参数返回全量** | 纯数组，非分页对象；复位基线 **86 条**（旧载 87 = 86 + 当次撤销留存的测试记录） | 这是**唯一可靠**的用法 |
| **没有分页参数** | 数据量增大后无法保证全量 | 设**安全阈值**：条目数 ≥ 500 时，**仍做比对，仅"未命中"时降级为查不清**，**不得**降级为"未生效"（第 06 章 §五.4） |
| **需要 ADMIN** | `TEACHER`/`STUDENT` 被拒 | 查证必须切换身份，且该切换只发生在网关内部 |
| **记录口径（三审 J3 已实测）** | 列表含**全部状态**（ACTIVE/CANCELLED/EXPIRED）与**两种类型**（CLASSROOM 23 + SEAT 63）；已撤销记录**留存**；签到 20/用量 15 在**独立表**、不混入（旧载"混入"已更正） | 比对前过滤：仅计 `status=ACTIVE`；CLASSROOM 按 resource_id、SEAT 按 classroom_id 归并（C9）；严格不等号判重叠（不含边界，第 06 章 §6.4）。详见第 08 章 §2.2 |

> **为什么安全阈值必须存在**：如果列表被截断而我们不知道，"没找到"就会被误判成"没生效"，进而触发重试 → **重复提交**。这是"不报错的错误"，比报错危险得多。**二审澄清**：阈值是**性能护栏**（防止无界比对），不等于"已实测到截断点"——存量系统实测无分页参数，因此"会不会截断"本身是未知的，这正是要保守的原因。

> **可行性评估点（三审已核）**：复位基线 86 条且全部为非 ACTIVE，演示当日参与比对的主要是新产生的少数 ACTIVE 行，距阈值 500 有 5 倍以上余量；超阈行为维持第 06 章 §五.4 规格（仍比对、未命中才判查不清、转人工）。

### 6.3 写入接口

#### ⑦ `edu.reservation.classroom.create` — 提交整间教室预约（**主轴**）

| 项 | 内容 |
|---|---|
| 用途 | 完成"借一间教室"这个动作 |
| 身份 | **TEACHER** |
| 副作用 | **有** |
| 幂等业务键 | `教室 + 时段` |
| 查证路径 | `logi.reservation.list` |
| 补偿动作 | `edu.reservation.cancel` |
| 前置命题 | 教室存在 / 教室启用 / **本人未重复提交** / 时段未被占 / 不在维修窗口 |

**实测结论（三条，都反直觉）**：

| # | 事实 | 规格要求 |
|---|---|---|
| 1 | **它有时间重叠冲突检测**——重复提交返回 `HTTP 200 + code 409`；6 路并发仍只落库 1 条 | 因此"幂等"要解决的问题**不是防重复写入**，而是**消解歧义**（见下） |
| 2 | **`409` 是歧义信号**——两种情况响应完全相同：① 你自己刚才那次其实成功了 ② 别人抢先占了 | **既不能当成功，也不能当失败**，必须查证。查证前**禁止重试** |
| 3 | **`ADMIN` 身份调用返回 `HTTP 200 + code 403`**（方法层拒绝），而过滤器层的拒绝是 `HTTP 403` | 判定规则必须**两条都覆盖**；只看 HTTP 状态码会把"越权被拒"当成"成功" |

**这条更正很重要，来源是实测**：早期设计曾假设"重复提交会产生两条记录"。实测证明**不成立**（`存量系统改造说明.md` §七.3）。修正后的命题更准确——问题不在"会写脏"，而在**"看不出到底成没成"**。

**前置命题的顺序有讲究**：

```
先查「是不是我自己提交的」 → 再查「是不是别人占的」
```

为什么这个顺序：若顺序反了，用户重复提交时会被提示"教室不可用"——而占用者其实是**用户自己**，这个提示会误导他去换教室。先查本人，才能给出**准确**的提示（"您此前已提交过，预约号 X"）。

> **可行性评估点**：需要你确认"本人重复提交"应当算**失败**还是**幂等成功**。我判断不了的是：业务语义上，用户第二次说"帮我借这间教室"时，期望得到"已帮你借好了（此前那次）"还是"你重复了"。**我的倾向是前者**（按幂等成功处理，返回已有记录），因为它更符合"代办"的语义；当前设计给的是明确拒绝，这在演示里更醒目但语义上略保守。

### 6.4 查证与补偿

#### ⑨ `edu.reservation.mine` — 我的预约

| 项 | 内容 |
|---|---|
| 用途 | ① 判断"本人是否已重复提交" ② 查证的降级路径 |

**关键约束**：**身份决定可见范围**——它只返回**当前身份**的预约。因此用它查证时，**必须使用发起写入时的同一身份**。

#### ⑩ `edu.reservation.cancel` — 撤销预约（补偿动作）

| 项 | 内容 |
|---|---|
| 用途 | 撤销此前已生效的写入 |
| 身份 | TEACHER |
| 副作用 | 有（但它是补偿动作） |
| 补偿动作 | **无** —— 显式登记为**不可补偿** |

**设计决定**：它自身标记为"不可补偿"，因为**不存在"撤销补偿"这回事**。

**关键约束：补偿不保证成功。** 若记录已进入不可撤销状态，撤销会失败。失败时**必须**落到"需人工介入"的终态并如实上报——**禁止静默吞掉**（不变量 I6）。

**撤销返回码（三审 D10 实测，2026-09-25）**：

| 我们的请求 | 存量系统的行为（实测） |
|---|---|
| 撤销有效且未到结束时间的预约 | 成功 `200+200`（SQL 条件：`status='ACTIVE' AND end_time >= UTC_TIMESTAMP()`） |
| 撤销**已取消**的预约 | **`200+400`**"该预约已取消" |
| 撤销**结束时间已过**的预约 | **`200+400`**"历史预约不能取消"（EXPIRED 记录同理） |
| 撤销**不存在**的 id | **`200+404`**（资源不存在码分叉，第 05 章 W13） |
| 并发竞争状态已变化 | `200+409` |
| 撤销别人的记录 | 按 id+userId 查无此记录 → `200+404` |

> 上述 400/404 在补偿语境下**不判"撤销失败"**：按第 06 章 §8.1 的 `recordId` 谓词查证，CANCELLED/EXPIRED/查无此 id 均判"撤销已生效"；仅查不清或 id 未知落三级处置。

**幂等业务键豁免**：它不需要业务键，因为重复撤销的影响天然幂等（记录已不存在）。

> **可行性评估点**：需要你确认——补偿失败时的"人工介入"在 demo 里**怎么表现**。我判断不了的是：是弹出提示、写入日志、还是在界面上显示一条"待处理"记录。这属于演示设计，我在第 12 章再展开，现在需要你给个方向。

## 七、不影响存量系统的八条措施

这一节回答用户的要求："**为了不去影响引用的系统，我们要好好考虑这些接口的。**"

### M1 · 零源码改动

不改、不新增、不删除 `mock-legacy/` 里的任何文件，包括看起来"必须"的配置文件。

运行配置走**环境变量注入**（借用它自己 `docker-compose` 里已有的变量名，不是我们发明的旁路）。复核方式见 `存量系统改造说明.md` §十一。

### M2 · 不直接写它的数据库

**所有业务数据变更只能经由它的 HTTP 接口。** 不建表、不加唯一约束、不建触发器、不加中间表。

**为什么这条排得很前**：一旦直连它的库，就产生了**第二个写入方**，它的业务校验（冲突检测、权限、状态流转）会被整个绕过。而且这种破坏是**静默的**——存量系统自己都不知道数据被谁改了。

> ⚠️ **唯一的例外是"复位"**：演示前把数据恢复到初始状态，走它自己的初始化脚本（该脚本每张表都有 `DROP TABLE IF EXISTS`，可重复执行）。这不算"业务写入"，它是把系统恢复到**它自己定义的初始状态**。这个例外的边界要写清楚。

### M3 · 把不合格的请求挡在它之外

所有**能在本地判定**的不成立条件，都在调用前拦掉，不让它产生错误响应。

**理由不只是"省一次调用"**：它的错误响应语义是混乱的——`400` 既表示参数非法、也表示资源不存在（`存量系统改造说明.md` §八.2）。**我们的正确性不应该建立在解读它的错误码上。** 少依赖一次它的错误路径，就少一处隐患。

### M4 · 写操作永不自动重试

写操作只有在**确定"未生效"**之后，才允许再次提交。"确定"的唯一来源是**查证命中/未命中**，不是超时、不是 5xx、不是 409。

**为什么**：它的写接口**没有幂等键**。任何"先重试再说"的写法，都会在"服务端已写库、响应丢失"时制造重复数据。

### M5 · 只读调用有规模上限

| 约束 | 要求 |
|---|---|
| 全量列表 | 设安全阈值；超阈值时查证结论降级为"查不清"，**不得**降级为"未生效" |
| 同类只读并发 | 不做无界并发（降级换教室时的候选校验要串行或有上限） |
| 不做轮询 | 不用轮询代替查证 |

**理由**：它的列表接口**没有分页参数**，无界调用会放大成"每次办事都扫全表"。

### M6 · 身份按需最小化取用

每个接口用它声明的**最小身份**。**不因为省事而全用 `ADMIN`。**

凭证由网关统一持有与刷新，**只在网关内部流转**——不进入编排逻辑，不进入日志，不进入前端。

### M7 · 不假设它的行为，也不"顺手修好它"

| 半句 | 含义 |
|---|---|
| 不假设 | 所有判定依据以**实测**为准。它的自述文档已被证明有错（`存量系统改造说明.md` §九，6 条不一致，包括账号密码） |
| 不"修好" | 它的不一致**不是缺陷，是本作品存在的前提**。把 HTTP 状态码语义统一了、把时间格式统一了，防腐层就失去了存在理由 |

**这一条要抵抗的是一种很自然的冲动**：看到 `HTTP 200 + code 403` 会觉得"这不是 bug 吗，顺手改了吧"。**不改。** 理由见 `存量系统改造说明.md` §六的六条逐项说明。

### M8 · 不可补偿的写操作禁止自动编排

**唯一名单**：`logi.maintenance.create`。

**规格**：注册表里有"是否有副作用"，但**不足以**表达这条禁令——必须另有"是否允许自动编排"这一维度。任何新增的不可补偿写接口，默认落在禁止侧。

## 八、明确不纳管的接口及理由

| 不纳管 | 理由 |
|---|---|
| 涉及**金钱/额度**的接口（如信用等级扣减） | 后果不可逆且影响真实权益，超出"代办"的合理范围 |
| **用户管理**类接口（增删改用户） | 与业务意图无关，且风险与收益严重不对称 |
| **签到 / 用量上报**类接口 | 属于"用户本人在场行为"，代办无意义 |
| 任何**无查证路径的写接口** | 违反硬门槛 **N3** |
| 任何**不可补偿且无法避免**的写接口 | 违反硬门槛 **N4**（演示工具按"禁止自动编排"另行处理） |

**原则**：**接触面越小，主张越硬。** 纳管 12 条能讲清楚，纳管 39 条只能讲"我们全都支持"——后者听起来更弱。

> **可行性评估点**：需要你确认这个"小而深"的取舍。我判断不了的是：比赛的评分维度里，"接口覆盖面"是否是一个加分项。若是，可能需要适度扩大纳管清单（代价是本章需要同等力度地论证每一条）。
