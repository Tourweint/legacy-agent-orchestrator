# 11 · 部署与运行方案

> 本章解决：**从一台干净的机器到"可以演示"，中间的每一步是什么。**
>
> 依据：`docs/基线文档/存量系统改造说明.md` §四（三道防线）、§五（运行配置注入清单）、§十（已知风险与对策）、§十一（复核方式）。
>
> **本章不含代码。** 脚本的**职责边界**是规格，脚本内容不属于方案。

---

## 一、环境要求

| 组件 | 版本要求 | 说明 |
|---|---|---|
| **JDK** | **必须 17** | 存量系统的编译目标。本机 PATH 上的默认 Java 是 24，**不可用**（与 Lombok 版本不兼容） |
| **MariaDB / MySQL** | MariaDB 12.1 及以上（已实测） | 承接 MySQL 5.7 导出的初始化脚本，零改动 |
| **Redis** | 7 及以上（已实测 8.10） | **存量系统强依赖**：未启动时，登录后的所有接口一律返回 401 |
| **Node.js** | 20 及以上 | 编排引擎与前端构建。需要原生 `fetch` 与顶层 `await` |
| **浏览器** | 近两年的现代浏览器 | 需支持事件流（SSE） |
| **邮件服务** | **不需要** | 演示链路使用口令登录，不触发邮件。相关配置填占位值即可 |

> **"不需要邮件"这一条要写清楚**：存量系统在**缺少邮件配置时会启动失败**（`MailService` 的 Bean 依赖 `spring.mail.host` 存在），但这**不等于**需要真的能发邮件。**填占位值即可**——这是一个很容易被误判的坑：看到"需要邮件配置"就去找 SMTP 账号，白花时间。

## 二、三个进程与端口

| 进程 | 端口 | 是否必须 | 说明 |
|---|---|---|---|
| 存量系统后端 | **8080** | 必须 | **不改**——改端口会改变它的配置语义 |
| MariaDB | 3306 | 必须 | —— |
| Redis | 6379 | 必须 | —— |
| **编排引擎** | **8090**（决策 A2，三审确认） | 必须 | 必须避开 8080 |
| 对话前端（开发期） | 5173 | 演示时必须 | 生产形态为 **Vite 预览独立进程**（决策 A8），不由编排引擎托管 |

**端口冲突的处理原则**：

| 冲突对象 | 处理方式 |
|---|---|
| 存量系统 8080 被占 | **让占用者让路**，不改存量系统端口 |
| 编排引擎端口被占 | 改**我们自己的**端口（它是我们的东西） |
| Redis 6379 被占 | 先确认占用者是不是我们要用的那个 Redis（常见于机器上已有多个实例） |

> **这个原则体现的是"谁的东西谁改"**：存量系统的端口是**它的配置语义的一部分**，改它等于在思想上也改了它。**这条纪律在演示前的慌乱时刻最容易被破坏**——脚本里要写死，不要留给现场判断。

## 三、配置注入

### 3.1 存量系统的配置（必需，12 项）

全部通过**环境变量**注入，**不写配置文件**（`存量系统改造说明.md` §四 防线一）。

| 类别 | 项 | 缺失后果 |
|---|---|---|
| 数据源 | URL / 用户名 / 密码 | **启动失败** |
| Redis | 主机 / 端口 | 登录后所有接口 **401** |
| JWT | 密钥 / 访问有效期 / 刷新有效期 | **启动失败**（其中有效期两项在源码中无默认值） |
| 邮件 | 主机（**占位值即可**） | **启动失败**（Bean 装配依赖） |
| 认证策略 | 验证码有效期 / 重发冷却 / 设备会话上限 | 相关功能异常 |

**两条必须写进脚本的规格**：

| # | 规格 | 理由 |
|---|---|---|
| 1 | **启动前显式清除可能被环境注入的端口变量**（如 `SERVER__PORT`） | 宽松绑定会把它解析成 `server.port`，导致 Tomcat 绑到意料之外的端口（**已实测踩到**，报的是"端口被占"，极具误导性） |
| 2 | **显式使用 JDK 17 的绝对路径**，不依赖 PATH | PATH 上的默认 Java 版本会随机器变化 |

> **第 1 条是本章最值得单列的一条经验。** 它的危险在于**报错信息指向完全错误的方向**——你会去查"8080 被谁占了"，而真正的问题是"它压根没打算用 8080"。**这类"报错指向错误方向"的问题，必须在脚本里一次性解决，不能靠现场排查。**

### 3.2 编排引擎的配置

| 类别 | 内容 | 注入方式 |
|---|---|---|
| 存量系统地址 | 基址（**注意：真实路径没有 `/api` 前缀**） | 环境变量 |
| 身份凭证 | 各身份的账号口令（ADMIN / TEACHER / STUDENT） | 环境变量 |
| 大模型 | 密钥、模型名、接口地址 | 环境变量 |
| 自身端口 | 见 §二 | 环境变量 |
| 超时 | 读写分级超时（第 04 章待决 3） | 配置文件（非敏感） |
| 混沌 | **默认撤防**（第 09 章 §七） | 配置文件 |

**三条纪律**：

1. **密钥一律走环境变量**，不写进仓库里的任何文件（含示例文件与文档）
2. **示例配置文件里只放占位值**，并在注释里写明"这里需要真实值"
3. **禁止在日志、证据链、界面中输出凭证**（I5；第 01 章 M6）

## 四、启动顺序与脚本职责

**顺序不可颠倒**（每一步都有前置依赖）：

```text
① 数据库（MariaDB 已在运行）
      ↓
② Redis
      ↓
③ 复位存量系统数据到已知初始状态      ← 见 §五
      ↓
④ 启动存量系统（→ 8080）
      ↓
⑤ 探活：三个身份各登录一次           ← 见 §四.1
      ↓
⑥ 编排引擎（→ 8090）
      ↓
⑦ 前端（→ 5173）
```

### 4.1 ★ 第 ⑤ 步"探活"不能省

**规格**：启动存量系统后，**必须**逐个验证三个身份都能登录成功，再往下走。

| 若不探活 | 后果 |
|---|---|
| Redis 没起好 | 登录后的所有接口 401。**表现是"系统能启动但什么都不能办"**，而你会以为是编排引擎的问题 |
| 某个账号口令不对 | 直到演示中途才发现（**上游文档里的账号密码有错，已实测**） |
| 数据库连接到了空库 | 一切正常但没有数据 |

**探活必须覆盖三个身份**，因为它们分别对应三个权限域——只验 ADMIN 会漏掉 TEACHER 侧的问题。

### 4.2 脚本职责（三个，职责必须单一）

| 脚本 | 职责 | 允许做 | **禁止做** |
|---|---|---|---|
| **环境准备** | 启动 Redis（若未运行） | 探测端口、启动、探测存活 | 改存量系统任何文件 |
| **数据复位** | 把数据恢复到已知初始状态 | 删库建库、导入初始化脚本、清空 Redis 键 | **直接插业务数据**（见 §五） |
| **启动存量系统** | 注入环境变量并启动 | 清除干扰变量、指定 JDK 17、探测端口、**探活三个身份** | 修改它的配置文件或 `pom.xml` |

## 五、数据复位与"演示数据怎么来"

### 5.1 复位

| 项 | 规格 |
|---|---|
| 方式 | 走**它自己的初始化脚本**（该脚本每张表都有 `DROP TABLE IF EXISTS`，可重复执行） |
| 范围 | 删库 → 建库 → 导入 → 清空 Redis 中的会话键 |
| 时机 | **每次演示前必跑**；连续演示之间也要跑 |
| 为什么可以在库这一层动手 | 它**不是业务写入**，而是把系统恢复到**它自己定义的初始状态**。这个例外的边界必须写清楚（第 01 章 M2） |

### 5.2 ★ 演示用的"额外场景"必须走接口，不能插库

**这条容易被图省事破坏，必须写死。**

| 场景 | 怎么做 | **不能怎么做** |
|---|---|---|
| "某间教室正在检修" | **用 ADMIN 接口在线创建一条生效中的维护窗口** | ❌ 直接 `INSERT` 到维护窗口表 |
| "某间教室已被预约" | 用 TEACHER 接口正常提交一次教室预约 | ❌ 直接插预约表 |

**理由**（`存量系统改造说明.md` §四 防线三）：

> 走接口创建，才能证明**"这是存量系统里本来就有的业务数据"**，而不是我们伪造的。直接插库会让"零侵入"与"数据真实"两条主张**同时受损**。
>
> 而且——**"用 ADMIN 接口创建维护窗口"这个动作本身，就是 ADMIN 身份编排的展示机会**（第 01 章 §6.5）。

**推论**：复位脚本**只做复位**，不负责构造演示场景。场景构造是**演示脚本**的事，且**必须走业务接口**。

## 六、演示前检查清单

**这份清单的作用是"把慌乱从现场移到准备阶段"。** 每一项都必须能被机械地检查，不允许"我觉得应该没问题"。

| # | 检查项 | 通过标准 |
|---|---|---|
| 1 | 数据已复位 | 复位脚本执行成功；按业务键统计与初始状态一致 |
| 2 | Redis 存活 | 探测通过 |
| 3 | 三个身份都能登录 | 探活脚本输出三个成功 |
| 4 | 存量系统监听在 8080 | 端口探测 |
| 5 | 编排引擎存活 | 存活探测通过 |
| 6 | **混沌处于撤防** | 显式检查开关状态（第 09 章 §七） |
| 7 | 大模型可达 | 用**结构化任务**做一次探活（第 03 章 §十）；**这一步失败不影响演示**，因为可切到预置任务 |
| 8 | 前端可访问 | 页面打开 + 一次结构化任务走通 |
| 9 | 演示脚本里提到的教室**确实存在** | 对照存量系统实际教室清单（**注意：没有"302 教室"**；三审定稿主演示教室=数智楼 **123**，id=5） |
| 10 | 演示脚本里的时段**当前确实可用** | 逐条核对；**被占用的时段要换掉** |
| 11 | 深色/浅色主题都能看清 | 在投影环境或等效环境目视 |
| 12 | **证据链导出可用** | 一次完整链路后能拿到证据链明细 |
| 13 | **时间链路复验**（一审补入，第 06 章 §6.3 的要求） | 在当前环境构造一个"两种时区解释下结论不同"的用例，出参按 UTC 解释的链路结论正确；另核对归一化三段（8–12/13–17/18–22）落在系统可预约时段 07:00–22:30 内（三审 K2/C19） |
| 14 | **降级演示的候选存在**（一审补入；三审按实测改写） | 第 4 幕口径：主角 **123=48 座（id=5）被占 → 候选 222=55 座（id=4）**。复位后逐项核对：123 与 222 当时均无 ACTIVE 预约、222 无生效维修窗口。**数智楼容量实测：111/123=48、222=55、233=32、431=9——222 为全栋最大，不可作为降级起点** |

> **第 9、10 两项是最容易翻车的地方**：演示脚本里写的"数智楼 123 周三下午"，若恰好已有预约，演示第一句就失败。
>
> **处理方式**：把演示脚本里用到的资源**在复位后逐一核验**，而不是在台上撞运气。复位基线中 86 条预约全部为 CANCELLED/EXPIRED（无 ACTIVE），但当台之前各幕/前一场演练产生的记录必须重新核对或重新复位。

## 七、故障排查表

**按"症状 → 最可能的原因 → 处置"组织。** 顺序按发生概率从高到低。

| 症状 | 最可能的原因 | 处置 |
|---|---|---|
| 存量系统启动报"端口 50520 被占"（或任何非 8080 的端口） | 运行环境注入了端口变量，被宽松绑定解析 | 启动脚本显式清除该变量（§3.1 规格 1） |
| 存量系统启动失败，报配置占位符无法解析 | 缺少无默认值的配置项（JWT 有效期等） | 补齐环境变量（§3.1） |
| 存量系统启动失败，报 `MailService` 相关 Bean 装配错误 | 缺少 `SPRING_MAIL_HOST` | 填**占位值**即可，不需要真实 SMTP |
| **能启动，但登录后所有接口返回 401** | **Redis 未启动** | 启动 Redis（§四 步骤 ②） |
| 登录成功，但某个操作返回 403 | **身份不对**（该接口需要更高角色） | 对照第 01 章的纳管清单核对所需身份 |
| 调用返回 `HTTP 200` 但业务码是 403/409 | 正常——**存量系统的业务错误走 200** | **不是故障**。检查判定规则（第 05 章）是否正确执行 |
| 时段重叠判定总是"不重叠" | **时间按本地时区解析了**（第 06 章 §六） | 改为按 UTC 解释出参时间 |
| 查证总是查不到已存在的记录 | ① 用了 `keyword` 过滤 ② 时间时区错 ③ 用错了身份 | 改为拉全量 + 内存比对；检查身份；检查时区 |
| 查证结果不稳定（时而命中时而没有） | 列表可能被截断/数据量变化 | 检查安全阈值（第 06 章 §五.4） |
| 降级时等待很久 | 候选池逐项校验且无上限 | 加候选上限（第 01 章待决 2） |
| 界面显示"成功"但库里没有 | **假成功**：只看 HTTP 状态码判成败 | 检查判定规则是否先看业务码（第 05 章 §五） |
| 演示中出现"不确定"且很久不收敛 | 查证路径不可用（ADMIN 身份失效 / 数据量超阈值） | 检查 ADMIN 凭证；检查查证的身份切换 |
| 前端拿不到执行步骤 | 事件流未建立或被中断 | 检查接口层的流式通道；检查是否有中间层缓冲 |

> **第 6 行值得单列**：**"HTTP 200 + 业务错误码"不是故障，是存量系统的正常行为。** 排查时最容易在这里浪费时间——看到 200 以为成功，看到 403/409 以为网络出问题。

## 八、零改动的复核方式

**任何人都能独立复核"我们没碰过它"**（`存量系统改造说明.md` §十一）。

| # | 复核项 | 期望结果 |
|---|---|---|
| 1 | 存量系统源码无改动 | 版本管理状态为空（除构建产物）；**无新增文件** |
| 2 | 运行配置不在其仓库内 | 其资源目录下**没有** `application-local.yaml` 之类的文件 |
| 3 | 启动脚本与配置都在其仓库之外 | 脚本与示例配置位于 `deploy/` 下 |
| 4 | 完整启动与验证 | 按 §四 顺序走一遍，探活全部通过 |

**这项复核要能在答辩时当场做。** 它是"零侵入"这条主张的唯一实物证据——**比任何解释都有效**。

## 九、明确排除的做法

| # | 排除 | 理由 |
|---|---|---|
| 1 | ~~改存量系统的端口~~ | 端口是它配置语义的一部分；"谁的东西谁改" |
| 2 | ~~往存量系统仓库里补配置文件~~ | 违反零侵入（`存量系统改造说明.md` §四 防线一） |
| 3 | ~~改它的 `pom.xml` 或初始化脚本~~ | 同上 |
| 4 | ~~直接插库构造演示数据~~ | §5.2；会让"数据真实"这条主张作废 |
| 5 | ~~靠 PATH 上的 `java` / `mvn`~~ | 默认版本可能是 24，不可用 |
| 6 | ~~跳过三身份探活~~ | §4.1；Redis 问题会伪装成"其他一切问题" |
| 7 | ~~在示例配置或文档里写真实密钥~~ | 凭据纪律 |
| 8 | ~~为演示临时打开混沌~~ | 第 09 章 §七；会让"看到的失败"无法归因 |
| 9 | ~~用容器化包装存量系统（改它的 compose）~~ | 它自带 `docker-compose`，但**改它 = 碰它**。是否**原样**使用需要单独实测 |
| 10 | ~~把编排引擎拆成多个进程部署~~ | 第 02 章 §七 |

## 十、本章待决清单

| # | 待决 | 类型 | 我的倾向 |
|---|---|---|---|
| 1 | 编排引擎端口取值 | **需决策** | 8090（避开 8080，且不常见） |
| 2 | 前端在生产形态下由谁托管（Vite 预览 vs 由编排引擎托管静态资源） | **需决策** | 演示用一个额外进程更简单；若要求"两个进程"，则由引擎托管 |
| 3 | 是否原样使用存量系统自带的 `docker-compose` | **需实测** | 目前是本机直跑（MariaDB/Redis 各自独立），更可控 |
| 4 | 数据库连接是否用独立只读账户做"库内计数校验"（第 09 章证据 6） | **需实测** | 用管理员只读查询即可，不必新建账户 |
| 5 | 复位是否需要清空 Redis 中的会话键（会不会导致已登录凭证失效） | **需实测** | 需要；且必须在探活**之前**清，顺序不能反 |
| 6 | 演示前检查清单是否固化为可一键执行的脚本 | **需决策** | 需要；这是"把慌乱移到准备阶段"的唯一手段 |
| 7 | 是否需要一份"演示机环境快照"（版本、路径、端口） | **需决策** | 需要；换机器时能快速重建 |
