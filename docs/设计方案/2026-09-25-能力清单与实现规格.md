## 一、14 项能力总表

**计数口径（重要）**：
- **"能力"与"意图"不是一回事**：一项能力可以由**两个意图**承载（例如"管理我的预约"含"查"与"退"两个意图，因为只读与写入在状态机里是两条不同的路径）；也有能力不挂意图（C11 的"全部已读"是界面按钮 + 引擎专用端点，三审拍板，见 C11 行）。
- 合计（**三审口径**）：**14 项能力 → 13 条意图计划**（其中 **11 条新增**、2 条既有）；**新增纳管 12 个接口**（一审补 1 条：管理员撤销任意预约，见 §2.6 #12；注册后纳管合计 24/39）；**新增 4 条事实、7 条命题**。
- 逐项对应：C1–C6 复用既有 2 条意图；C7 两条意图（查/退）；C8、C9、C10、C12、C14 各一条；C11 仅"查询"为意图（"全部已读"端点化，不计意图）；C13 三条（排队/查位次/取消）＝ **11 条新增**。

## 二、通用规格（14 项共用，只写一次）

### 2.1 终态与三值（复用既有，不新增口径）

| 情形 | 终态 | 界面 | 话术纪律 |
|---|---|---|---|
| 办成 | `DONE` | 绿 | 说清了什么、什么时候 |
| 幂等命中（此前已办成） | `DONE` | 绿 | "未重复提交" |
| 有依据地拒绝 | `REJECTED` | 红 | 必须引用**真实事实/规则** |
| 试过所有办法仍办不成 | `REJECTED` | 红 | 给出下一步可选（换教室/改时段） |
| 结果查不清 | `UNRESOLVED` | 琥珀 | 如实说"没能确认"，**不猜** |
| 人工介入 | `UNRESOLVED` | 琥珀 | 说明已登记、需要谁处理 |

**新增要求（本次）**：**每一类拒绝都必须能指到"哪条规则/哪条事实"**——这是 C9 的落地方式。

### 2.2 槽位与追问（新增一条能力）

- 既有：缺失槽位 → 挂起追问（最多 3 轮）→ 恢复或超限拒绝。
- **新增：列表选择式追问**（C7 撤销定位、C14 受影响预约确认）——当系统**知道有多个候选**时，追问必须给出**可点的选项**（复用已有的"候选意图按钮"机制），而不是让用户重说一遍。
  例：用户说"把周三那个退了"，而周三本人有 2 条预约 → 追问："您周三有两条：数智楼123（14:00–17:00）、数智楼222（18:00–21:00），退哪条？"

### 2.3 身份（按最小权限，逐项在 §三 标注）

| 身份 | 用途 | 备注 |
|---|---|---|
| TEACHER | 教室预约的提交/撤销/我的预约 | 主链路 |
| STUDENT | 座位预约、候补排队（C12/C13） | **本次首次进入自动链路** |
| ADMIN | 跨域事实（全量预约、维修窗口）、配置查询、维修窗口创建/取消 | |

### 2.4 证据与话术纪律（复用既有，全部新能力适用）

- 每一步（收集/判定/调用/决策）都要落证据链，**界面内容与证据链同源**。
- 界面上**不出现**接口 URL、参数名、状态机状态名；接口在界面上用**业务语义名 + 使用身份**表示。
- "不确定"不得退化成"失败"，也不得给"重试"按钮。

### 2.5 新增事实与命题（本次新增的基础设施）

**新增事实**：

| 编号 | 事实 | 来源接口（新纳管） | 用途 |
|---|---|---|---|
| F7 | 我的候补队列 | 我的候补查询 | C13 |
| F8 | 教室规则上限（单次时长、单日上限、可预约时段） | **两部分**：① 登录后的**本人资料**（openapi 确认 `UserInfoVO` 自带 `creditLevel`（A/B/C 档）、`maxSingleReservationMinutes`、`dailyReservationLimitMinutes`、`seatReservationAdvanceHours`——**读本人上限不需要借任何身份**）；② **全局规则**（可预约时段等）走配置查询（借管理只读身份） | C9 解释、提交前预校验 |

> **二审补（F8 采集路径）**：本人资料不是一个独立的接口调用——它来自**登录响应**（`LoginVO.userInfo`），登录后缓存在引擎会话中。事实收集层取 F8 时：① 先从会话缓存读本人资料（零调用）；② 需要全局规则时才调 `GET /admin/configs`（管理只读身份）。因此 F8 的"采集路径"是"会话缓存 + 可选配置查询"，不是传统的"调一个接口拿一个事实"。实现时 fact-collectors 需要支持"从会话上下文取事实"的采集方式（本次新增），而不是所有事实都走接口注册表。 |
| F9 | 楼栋与偏好楼栋 | 楼栋列表、偏好楼栋 | C10 |
| F10 | 我的通知 | 通知列表、未读数 | C11 |

**新增命题**：

| 命题 | 问什么 | 依赖 | 用于 |
|---|---|---|---|
| `P-IS-MINE` | 目标记录确实属于本人 | F4/F5 | C7 撤销定位（**不得撤销别人的记录**） |
| `P-SLOT-FREE-EXCLUDING-SELF` | 目标时段可办，且**排除本人这条待改期的记录** | F3/F4 | C8 改期（否则会被自己的记录判成"被占"）★ |
| `P-WITHIN-CONFIG-LIMITS` | 申请落在系统规则内（时长上限、可预约时段、不跨天） | F8 | C9 + 提交前预校验 |
| `P-NOT-ALREADY-WAITLISTED` | 本人未重复排队同一教室同一时段 | F7 | C13（重复排队 → 幂等命中，不落拒绝） |
| `P-WAITLIST-TARGET-VALID` | 候选补的对象确实已满（满才需要排） | F3/F4 | C13 |
| `P-NO-ACTIVE-RESERVATION` | 目标时段已无生效预约 | F4 | C14 报修的收尾条件 |
| `P-MAINTENANCE-NOT-DUPLICATE` | 同一教室同一时段未重复建维修窗口 | F6 | C14 幂等 |

（既有 `P-SEAT-EXISTS` / `P-SEAT-SLOT-FREE` 已存在，C12 直接复用。）

### 2.6 新增纳管接口清单（12 条，含门槛体检；计数经一/三审两度订正）

> 门槛（白话）：**有副作用的接口必须①能事后查证、②能撤销（撤不了就要明确登记为撤不了）**。

| # | 接口（白话） | 方法 / 路径 | 身份 | 副作用 | 允许自动编排 | 查证路径 | 撤销方式 |
|---|---|---|---|---|---|---|---|
| 1 | 配置查询 | `GET /admin/configs` | ADMIN | 否 | ✅ | — | — |
| 2 | 楼栋列表 | `GET /classrooms/buildings` | 已登录 | 否 | ✅ | — | — |
| 3 | 我常去的楼栋 | `GET /classrooms/preferred_buildings` | 已登录 | 否 | ✅ | — | — |
| 4 | 通知列表 | `GET /notifications` | 已登录 | 否 | ✅ | — | — |
| 5 | 未读通知数 | `GET /notifications/unread-count` | 已登录 | 否 | ✅ | — | — |
| 6 | 全部标为已读 | `PATCH /notifications/read-all` | 已登录 | **是** | ⚠️ **人工触发**（不可逆，且没有"标未读"接口 → 明确登记为不可撤销） | 未读数复核 | **无**（登记） |
| 7 | 加入候补 | `POST /waitlist` | STUDENT | 是 | ✅ | 我的候补 | 取消候补 |
| 8 | 我的候补 | `GET /waitlist/my` | STUDENT | 否 | ✅ | — | — |
| 9 | 取消候补 | `DELETE /waitlist/{id}` | STUDENT | 是 | ✅ | 我的候补 | 重新排队 |
| 10 | **建维修窗口** | `POST /admin/maintenance` | ADMIN | 是 | ✅ **本次放行**（原禁令解除，理由：撤销接口存在） | 维修窗口列表 | 取消维修窗口 |
| 11 | 取消维修窗口 | `DELETE /admin/maintenance/{id}` | ADMIN | 是 | ✅ | 维修窗口列表 | 重新创建 |
| 12 | **管理员撤销任意预约**（撤**别人**的预约只能走它） | `DELETE /admin/reservations/{id}` | ADMIN | 是 | ✅（仅 C14，且必须两段式确认） | 全量预约列表 | 无（撤销不可逆；失败落人工介入）——同"撤销即目的"口径 |

> **一审补（2026-09-25）**：#12 是 openapi 里已确认存在的接口（"Cancel a reservation as administrator"，仅 ADMIN，可能返回 409）。C14 要撤的是**受影响预约本人**（并不在场）的记录，用户侧撤销接口只能撤"当前登录者自己的"，**没有这条就没有 C14**。它的真实返回码表仍需实测（§六 #1）。
>
> **二审补（2026-09-25）**：#12 的请求体是**可选**的 `AdminReservationCancelDTO`（仅含 `reason` 字段，maxLength 255）。C14 场景下建议传 `reason="设备维修"`（或类似业务原因）——该字段可能影响存量系统发给被撤人的通知内容；不传也能调用，但通知里可能缺少原因。是否传、传什么值待实测确认（§六 #1 增补）。
> **二审补**：#10 建维修窗口的请求体 `MaintenanceCreateDTO` 必填 `resourceType`（枚举 `SEAT`/`CLASSROOM`）+ `resourceId` + 起止时间。C14 场景固定传 `resourceType=CLASSROOM`，`resourceId`=目标教室 id。实现时适配器须按此组装，不得漏 `resourceType`（openapi 确认必填）。

> **原禁令为什么可以解除（说人话）**：当初禁止"维修工单自动下发"的理由是"发出去就撤不回来"。但实测确认**撤销接口是存在的**（把窗口置为已取消，不是物理删除）。既然撤得回来，它就可以进入自动流程。

### 2.7 角色与权限（2026-09-25 21:16 新需求，详见《登录、身份与权限方案》）

**两条规矩**：① **写操作只认登录者本人身份**；② **读事实可以借一个只读的服务身份**（并在界面明示）。

| 能力 | 写操作的角色要求 | 读事实 | 越权时的表现 |
|---|---|---|---|
| C1 借教室 | **教师** | 借只读服务身份读维修安排 | 学生申请 → **拒绝** + 给替代（查空闲 / 排座位候补） |
| C2 查可用性 | —（只读） | 同上 | 任何已登录角色可查 |
| C3 多资源 | 同 C1 | 同上 | 同 C1 |
| C4 降级换教室 | 同 C1 | 同上 | 同 C1 |
| C5 追问 | 无权限语义 | — | — |
| C6 取消 | 本人 | — | 非本人任务不可取消 |
| C7 我的预约（查/退） | **本人**（只能撤自己的） | 本人的记录 | 试图撤别人的 → 拒绝 |
| C8 改期 | **本人** | 同上 | 同上 |
| C9 拒绝解释 | —（只读） | 配置需管理只读身份 | 任何已登录角色可问 |
| C10 教室发现 | —（只读） | 已登录 | 任何已登录角色 |
| C11 通知回执 | 本人（"全部已读"仅人工触发：**界面按钮 → 引擎专用端点 `POST /api/notifications/read-all`，三审拍板，不做意图、不进状态机**） | 本人的通知 | 只能读自己的；自然语言说"都标已读"→ 不调接口，回复引导点按钮 |
| C12 学生占座 | **学生** | 座位布局 | 教师若要求座位预约 → 说明边界（座位预约是学生能力） |
| C13 候补排队 | **学生** | 该时段占用 | 非学生 → 拒绝 + 说明 |
| C14 报修联动 | **发起角色：仅教师（三审拍板）**；报修+撤销：**本人**；建维修窗口与撤他人预约：**管理身份**（openapi 确认这两类动作存量系统只允许管理员做；需用户确认影响面） | 跨域事实 | **学生报修 → 有依据拒绝**（"设备报修联动仅向教师开放"）+ 替代（帮查该教室当前状态）；管理员账号仅作服务身份，不在前台发起业务 |

> **评审要点**：C14 里"建维修窗口用管理身份"**不是**借只读身份，而是一次**写**操作——所以它必须有"用户确认影响面"这道闸，这也是本清单里唯一需要**两段式确认**的能力。

## 三、逐项实现规格

> 每项固定七段：**话术 → 意图与槽位 → 事实与命题 → 步骤链 → 判定/查证/补偿 → 失败话术 → 界面与验收**。

### C1 借教室（现成，演示重排）

| 项 | 内容 |
|---|---|
| 话术正例 | "帮我借周三下午数智楼123" |
| 意图 | `borrow-classroom`（写、多资源） |
| 槽位 | 必填：教室、日期说法、时段说法；可选：理由 |
| 事实/命题 | F1/F3/F4/F5/F6；教室存在、教室启用、本人未重复、时段空闲、非维修中 |
| 步骤链 | 教室详情 → 时段座位占用 → 全量预约（管理身份）→ 我的预约 → 维修窗口（管理身份）→ 提交（教师） |
| 判定 | 提交返回按既有规则表判三值；不确定 → 走查证；重复提交 → 幂等命中 |
| 失败话术 | 引用真实事实（如"该教室在这段时间已被预约"） |
| 界面/验收 | 轨迹 P1–P6 逐步出现，每步有依据、身份；终态卡给结论；**验收：真实提交一条 ACTIVE 记录并清理干净** |

### C2 查教室可用性（现成）

同上，但**只读**：不进入提交，终态直接给"能 / 不能 / 不确定"，不产生任何写入。

### C3 一次借两间（现成）

`borrow-classroom` 的 `multiResource: true`：按资源顺序各自跑一遍完整生命周期；**第二个失败时，撤销第一个**（撤销动作在轨迹里可见）。验收：造一次"第二间被占"的真实场景，检查残留为 0。

### C4 自动换同楼栋更大的（现成）

被占后的降级：从候选池里挑**同楼栋、容量不降**的教室，**最多 3 轮**；用户没指定具体教室时**不降级**（没有比较基准）。验收：候选池消费顺序与"不换更小的"可查。

### C5 信息不全时追问（现成）

缺失槽位由**配置机械计算**（不采信模型）；最多追问 3 轮；超限 → 拒绝并说明缺什么。

### C6 写入前可取消（现成）

写请求发出前取消 → 直接终止；发出后取消不生效（避免制造不确定态），转为查证。

### C7 管理我的预约（新增：查 + 退）

| 项 | 内容 |
|---|---|
| 话术 | "我订了哪些教室" / "把周三那个退了" / "退掉数智楼123那间" |
| 意图 | `query-my-reservations`（只读）、`cancel-my-reservation`（写） |
| 槽位 | 撤销：教室名（可选）、日期说法（可选）、时段说法（可选）——**全部可缺**，因为可以从"我的预约"里反查 |
| 事实/命题 | F5（我的 ACTIVE 预约）+ F1（解析教室名）；`P-IS-MINE` |
| 步骤链 | 我的预约 → （若多命中）追问选哪条 → **判定** `P-IS-MINE` → 撤销（教师身份）→ 复验（我的预约里该条消失） |
| 判定/查证 | 撤销按既有撤销返回码规则判三值（重复撤销/已过期/不存在都有明确语义）；**不确定 → 复验** |
| 补偿 | **不需要**：撤销是用户的目的，不是副作用。若撤销**失败**，如实报失败，不做"重新订回来" |
| 失败话术 | "您周三只有一条：数智楼123（14:00–17:00）；它当前状态不允许撤销（已过期）" |

### C8 改期（新增，本清单里设计最讲究的一项）

| 项 | 内容 |
|---|---|
| 话术 | "把周三下午那间改到周四下午" |
| 意图 | `reschedule-my-reservation`（写） |
| 槽位 | 原记录定位（教室名/日期/时段，可缺 → 从我的预约反查）+ 目标时间（日期说法 + 时段说法）|
| 事实/命题 | F1/F3/F4/F5；**`P-SLOT-FREE-EXCLUDING-SELF`（关键）**、教室存在、教室启用、非维修中 |
| **执行顺序（决策）** | **先建新、后撤旧**（不是"先撤后建"） |
| **为什么不选"先撤后建"（备选与排除）** | 先撤后建会出现"旧已撤、新没建成"的**空窗**，而且此时"恢复旧预约"要面对"时段可能已被别人抢走"——补偿会失败，只能落人工介入。先建后撤最坏情况是"新的建成了、旧的没撤掉"，**用户仍有两个时段可用**，且可重试撤销，风险单向。 |
| **`P-SLOT-FREE-EXCLUDING-SELF` 的实现机制（二审补）** | 现有 `P-SLOT-FREE` 是"任何重叠都不成立"，没有"排除指定记录"的谓词。本命题的实现方式是：**在事实收集阶段对 F4（全量预约列表）做内存过滤**——先从 F5（我的预约）定位到待改期的 recordId，再在 F4 比对时**排除该 recordId**，其余重叠仍判不成立。这不需要改 predicates.js 的算子库，而是在 fact-collectors 层对 C8 意图的 F4 做"带排除条件的采集"。代价：F4 采集逻辑需要感知"当前意图是否有排除记录"——实现时在 intent-plans.yaml 的 C8 条目加 `excludeSelfReservation: true` 标记，fact-collectors 读到该标记时从任务上下文取待改期 recordId 并过滤。**这是本次唯一需要动采集层代码的命题**（其余新增命题纯数据）。 |
| 判定/查证 | 新建走既有三值判定；撤销走撤销返回码规则（含 W13 分叉：400/404 进 recordId 查证，不判失败）；**两步都要各自查证收敛** |
| 补偿 | ① 新建失败 → **什么都不用撤**（旧记录未动）；② 新建成功、撤销失败 → **重试撤销**（compensateRetries=1，最多 1 次；重试前若上一次是 W13 分叉则先查证再决定是否重试）；仍失败 → 落"人工介入"，并**如实告知"您现在两个时段都有预约"**（不隐瞒、不猜测） |
| 失败话术 | "新时段没能订上（周四下午数智楼123 已被预约），您原来的周三预约**未受影响**。" |
| 界面/验收 | 轨迹里能看到"两次写入 + 一次撤销"，并显示为什么是这个顺序；验收：造一次"新时段被占"的真实场景，检查旧记录完好 |

### C13 候补排队（新增，**诚实性**最突出的一项）

| 项 | 内容 |
|---|---|
| 话术 | "数智楼123 明天下午满了，帮我排个候补" / "我排第几了" / "取消我的候补" |
| 意图 | `join-waitlist`、`query-my-waitlist`、`cancel-waitlist`（学生身份） |
| **槽位（一审改）** | **候补是座位级的**：openapi 明确 `POST /waitlist` = "Join **seat** waitlist"，请求体必填 `seatId` + 起止时间，仅 STUDENT。因此用户说"某教室满了帮我排候补"时，系统必须**先落到一个具体座位**——从座位布局里挑一个（或用列表选择式追问让学生挑），再排候补；**不得在话术里暗示"排上了整间教室的队"**。 |
| **座位选择逻辑（二审补）** | 教室"满了"指该时段所有座位都被占（F3 返回全量座位），但候补是排**单个座位**的队。系统选择座位的规则：① 优先取座位布局中**第一个座位**（按座位 id 升序）——演示时确定性可复现；② 若用户指定了座位（"帮我排 A3 的候补"），则用指定座位；③ 若座位布局接口不可得，挂起追问"请选一个座位"。**不做"智能推荐座位"**（无依据）。候补的 `seatId` 必须是该教室真实存在的座位（复用 `P-SEAT-EXISTS` 命题）。 |
| 事实/命题 | 新增 F7；`P-NOT-ALREADY-WAITLISTED`（重复排队 → 幂等命中）、`P-WAITLIST-TARGET-VALID` |
| 步骤链 | 该时段占用判定（确认确实满了）→ 加入候补 → 查证（我的候补里出现该条） |
| 查证/补偿 | 查证＝我的候补列表可见；补偿＝取消候补 |
| **话术纪律（关键）** | **转正由存量系统自己触发**，我们只是替用户排上队。必须如实说："已替您在这个座位上排上候补（当前第 N 位）；名额空出时由系统通知您（触发条件以实测为准，见 §六 #5），我这边不占用那个时段。" ——**不得暗示"我会自动帮你抢"** |
| 界面/验收 | 候补状态卡（排队中 / 已取消 / 已转正[由外部变化]）；验收：真实排队 + 真实取消，且界面不谎报 |

### C14 报修联动（新增，最强叙事，也是**唯一会动到别人数据**的一项）

| 项 | 内容 |
|---|---|
| 话术 | "数智楼123 的投影坏了，明天下午的课没法上，帮我处理一下" |
| 意图 | `report-fault`（写、多身份） |
| **发起角色（三审拍板）** | **仅教师可发起（requiredRole=TEACHER）**。学生发起 → 在任何调用发生前有依据拒绝（"设备报修联动仅向教师开放，您可以让老师来发起；我也可以先帮您查这间教室的当前状态"）；管理员账号仅作引擎持有的服务身份，不在前台发起业务。 |
| 身份链 | 用户（教师）→ 管理身份建维修窗口 → **管理身份**撤销受影响预约（走 §2.6 #12 管理员撤销接口——受影响预约的本人并不在场，不可能"用各自的账号"撤）→ 通知 |
| 事实/命题 | F4/F5/F6；`P-MAINTENANCE-NOT-DUPLICATE`、`P-NO-ACTIVE-RESERVATION` |
| 步骤链 | ① 收集该教室未来该时段的预约 → ② **先向用户确认**："这会撤销这 2 条预约，确认？"（复用挂起/确认机制）→ ③ 建维修窗口（管理身份）→ ④ 逐条撤销 → ⑤ 复核该时段已无生效预约 |
| 查证 | 维修窗口：窗口列表可见；撤销：撤销返回码规则 + 复核（每条撤销后立即查全量列表确认该 recordId 已非 ACTIVE） |
| 补偿 | ① 维修窗口的撤销＝取消维修窗口（`DELETE /admin/maintenance/{id}`）；② 被撤销的预约**无法真正恢复**（时段可能已被别人抢走）→ 若复核不通过，落**人工介入**并如实上报，**不静默** |
| **部分成功的补偿链（二审补）** | C14 要撤销 N 条受影响预约，可能出现部分成功（M 条成功、N−M 条失败）。处置口径：**① 逐条撤销、逐条查证**（不批量），每条失败独立记录；② 全部成功 → 复核该时段无 ACTIVE 预约 → DONE；③ 部分失败 → **先撤销已建的维修窗口**（恢复该时段可用性，避免"窗口建了但预约没撤干净"的混乱态），然后落人工介入；④ 已成功撤销的 M 条**无法恢复**，终态话术必须如实列出："已撤销 X 条、Y 条撤销失败（已登记人工介入）、维修窗口已取消；被撤销的预约无法自动恢复，请联系受影响人。"——**不隐瞒、不猜测、不静默** |
| 责任口径（必须写死） | 只能**用户显式确认后**才动别人的预约；确认话术要列清"将被撤销的是哪几条" |
| **两段式确认的挂起语义（二审补）** | 复用现有挂起/恢复机制（`input-required` 事件 + `/api/tasks/{id}/reply`），但语义与"槽位追问"不同：① 挂起点在**事实收集之后、写入之前**（不是理解层之前）；② 挂起时任务上下文须保存"待撤销预约列表 + 已收集的 F4/F6 快照"；③ 恢复时**不重新走理解层**——用户回复"确认"直接进入写入阶段，"取消"直接终止任务（终态 REJECTED，话术"已取消，未做任何改动"）；④ 实现时在 intent-plans.yaml 的 C14 条目加 `confirmBeforeWrite: true` 标记，编排层在收集完事实后、第一个写入步之前检查该标记并挂起。这是本次唯一需要动编排层挂起逻辑的能力（其余挂起都是槽位缺失）。 |
| 通知口径（一审补） | 总纲里"通知相关人"的落点：**通知由存量系统在预约被撤销时自行发出（待实测确认）**；我们只如实呈现"受影响的是哪几条"，**不承诺、也不代发"已通知"**——与候补的话术纪律同源（只承诺我做了什么）。 |
| 需实测 | 管理员撤销接口的真实返回码表与行为（openapi 已确认接口存在且仅 ADMIN，可能 409；返回码语义要对齐既有撤销口径）；**撤销时存量系统是否自动通知被撤人**；维修创建/取消的完整返回码表 |
| 界面/验收 | 轨迹里出现**两个身份**与一次"影响面确认"；验收：在测试数据上走通"建窗口 → 撤 2 条 → 复核无生效" |
