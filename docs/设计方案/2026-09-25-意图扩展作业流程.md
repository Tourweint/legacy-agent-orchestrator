# 2026-09-25 意图扩展作业流程（harness）

> **文档性质：设计期过程文档，带日期。状态：三轮评审已完成（2026-09-25，三审通过）。**
> **用途**：规定"**给这个系统加一项新的可办事能力**"的标准做法。`2026-09-25-能力清单与实现规格.md` 里的 8 项新增能力（C7–C14），每一项都要走本文的流程。
> **一句话**：**加能力主要不是写代码，而是改数据 + 过五道关 + 补验收；但有三处必须写代码，还有一批"难确定"的东西要显式登记。**

---

## 一、为什么需要这套流程

| # | 事实 | 后果 |
|---|---|---|
| 1 | **加一个意图要同步改 7 处**（意图计划、接口注册表、命题、判定规则、常量、事件/界面、演示脚本） | 漏一处就是隐患。**本项目真实发生过**：新加的两条接口（追问回复、取消任务）漏登记在对外接口清单里；引擎入口的一处笔误让进程根本起不来（测试与自检都不覆盖入口） |
| 2 | **现有引擎已经是"数据驱动"的** | 意图计划是 YAML、命题是 YAML、判定规则是表数据；**新增一条只依赖已有事实的命题，代码零改动**（这是既有的验收标准）——所以"加能力"大部分是**配置工作** |
| 3 | **但有些东西现在真的定不下来** | 例如自然语言的时间表达、候补转正由谁触发、多资源部分失败怎么交代。**必须显式登记为"未定"，不能假装已经定了**（本项目的纪律：不许留隐含前提） |

## 二、五道关（每关：动作 → 产物 → 自动检查 → 常见坑）

| 关 | 动作 | 产物 | 自动检查 | 常见坑 |
|---|---|---|---|---|
| **1 意图计划** | 起意图 id；写槽位（必填/可选，**槽位存用户原话片段，不做时间换算**）；写步骤链（每步引用**允许自动编排**的接口）；写所需命题；写降级策略 | `intent-plans.yaml` 新增一节 | 结构自检第 8 条（被禁自动编排的接口不得被任何计划引用） | 槽位写成了换算后的时间；步骤链引用了禁用接口 |
| **2 接口注册表** | 每个用到的接口补齐 §4.2 模板的**全部字段**（15 个键，与既有注册表一致）：身份 / 有无副作用 / **是否允许自动编排** / 幂等业务键 / **查证路径** / **补偿动作或"不可撤销"登记** / 前置命题 / 适配器 / 实测注意事项 | `interface-registry.yaml` 新增或补充条目 | 结构自检第 8 条；约束检查（出站写法只在网关） | **把"有副作用"当成"可自动编排"**——这是两个维度；有副作用但撤不回来的，必须禁自动编排 |
| **3 事实与命题** | 需要新事实就加一条（并补它的采集路径）；命题用"谓词表达式"写成立条件，**不得出现接口路径/字段名** | `propositions.yaml` 新增一节 + 事实采集说明 | 命题声明的依赖能驱动事实收集（`dependsOn`） | 把"事实拿不到"当成"命题不成立" |
| **4 判定规则** | 新接口的返回码/返回体是否落在既有规则行内；落不进就**加行**（写规则表 + 加测试） | 判定规则表新增行 | 规则表测试（每条规则有对应用例） | 只看 HTTP 状态码判成败（已有的坑：无权限返回"200 + 业务码 403"） |
| **5 对外表现** | 事件类型（**闭集，新增要先登记**）；界面呈现（业务语义名 + 身份，不出现接口术语）；话术；演示动线 | 对外接口清单 + 前端 + `docs/演示/` | 事件与证据链逐条一致 | 界面里出现接口名/参数名；"不确定"被画成"失败" |

> **关卡的分量不一样**：关 2 与关 4 最容易被忽略，也最容易出事（一个决定"能不能安全地自动执行"，一个决定"结果判得对不对"）。

## 三、标准作业流程（12 步，含命令）

```text
 1. 定能力与话术          → 写进《能力清单与实现规格》，固定用户会怎么说、系统怎么答
 2. 接口体检              → 每个新接口过两条硬门槛：能查证？能撤销（或明确登记撤不了）？
 3. 真实调用实测          → 用真实系统跑一遍，把结论写进注册表的"实测注意事项"
 4. 写意图计划            → intent-plans.yaml 加一节（槽位/步骤链/命题/降级）
 5. 写事实与命题          → propositions.yaml 加节（缺事实先加事实）
 6. 补判定规则行          → 新返回码没覆盖就加行 + 加用例
 7. 补常量                → 上限/超时/轮次一律进 constants.yaml，不写死在逻辑里
 8. 跑门禁                → cd orchestrator && npm run check     ← 8 条结构自检 + 4 条约束检查
 9. 写测试                → 单元 + 一条真实链路（含失败与边界）
10. 接界面与事件          → 事件登记 + 前端展示（业务语义名 + 身份）
11. 更新演示脚本          → 这项能力在视频里出现在哪一秒、看什么
12. 文档回填 + 变更记录   → 改过的文档同步；较大改动落变更记录
```

**每一步的"不合格"长什么样**（自查用）：

| 步 | 不合格的典型症状 |
|---|---|
| 2 | 说"应该能撤"但没找到撤销接口 → 必须改成"禁自动编排"并登记 |
| 3 | 注册表里的注意事项是**推断**的，不是实测的 |
| 4 | 步骤链里出现"由模型决定下一步"——本项目禁止自主规划 |
| 8 | 只看测试全绿，**没有真的把进程起一次**（本项目真实踩过） |
| 9 | 只测成功路径，边界（超时/冲突/已过期）不测 |
| 12 | 代码改了、文档没改 → 口径立刻开始漂移 |

## 四、模板（可直接抄）

### 4.1 意图计划条目

```yaml
  - id: <意图-短横线命名>
    name: <用户看得懂的名字>
    readOnly: true|false          # 决定终态是"直接给结论"还是"进入提交"
    multiResource: false
    slots:
      required: [<槽位名>…]        # 缺了就要追问
      optional: [<槽位名>…]
      slotHints:                  # 给理解层的槽位释义（从本文件生成，不手抄）
        <槽位名>: <一句人话说明 + 正例>
    facts: [F1, F3, …]
    propositions: [P-XXX, …]
    steps:                        # 每步只引用"允许自动编排"的接口
      - { step: <步骤名>, interface: <接口 id>, serves: <服务哪条事实/命题> }
      - { step: <写入步>, interface: <接口 id>, serves: 提交, role: submit }
    verification:                 # 有写入才需要：首选路径 + 降级路径 + 判定谓词
      primary:  { interface: <查证接口>, identity: <身份> }
      fallback: { interface: <查证接口>, identity: <身份> }
      predicate: { forward: <什么算命中>, compensate: <什么算撤销已生效> }
    compensation:
      action: <撤销接口>
      recordIdRequired: true      # 拿不到记录 id 时不许猜 → 如实报"查不清"
    degrade: null | { candidatesFrom: <候选来源>, note: <什么时候不降级> }
```

### 4.2 接口注册表条目（15 字段，一审核准：与既有注册表逐键一致）

```yaml
  - id: <域.资源.动作>
    domain: edu|logi
    method: GET|POST|DELETE|PATCH
    path: <真实路径>              # 注意：没有 /api 前缀
    timeoutClass: read|write
    purpose: <它服务于哪项能力的哪一步>
    requiredIdentity: <最小身份>   # 一个业务身份只绑一个账号
    sideEffect: true|false
    autoOrchestration: true|false # 与"有无副作用"是两个维度
    idempotentBusinessKey: <身份+资源+时段>
    verification: { via: <接口>, note: <什么算命中> }   # 有副作用则必填
    compensation: { action: <接口> } | null            # 撤不了就显式登记
    preconditions: [P-XXX…]
    adapter: <适配器名>           # 协议差异在这里吸收，不下沉到业务层
    legacyNotes: [ <实测结论，一条一句> ]
```

### 4.3 命题条目

```yaml
  - id: P-<大写下划线>
    semantics: <这条命题在问什么（人话）>
    dependsOn: [F#…]              # 驱动事实收集；事实拿不到时的挂载点
    skipWhen: <什么时候整条跳过（不适用）>
    when: <成立条件（谓词表达式）>
    violatedMessage: <不成立时对用户说什么——必须能指到事实>
    degradable: true|false        # 不成立时能否换方案继续
    disposition: { unconfirmable: conservative-reject | exempt-continue }
    invariants: [I1…]
```

### 4.4 能力登记行（写进能力清单）

```text
| C## | <用户会说的一句话> | 档位 | <意图 id> | <用到的接口> | <展示价值> |
|     | 验收：<怎么算做完> | 需实测：<留空则写"无"> |
```

## 五、"难确定"的东西（显式登记 + 我们的处置策略）

**这一节是本文最该被评审的部分**。以下都是**现在无法完全定死**的问题——登记，而不是假装已定。

| # | 难确定的问题 | 为什么难 | 现在的处置 | 什么时候能定 |
|---|---|---|---|---|
| 1 | 自然语言的时间表达（"下周三之前任意一天下午"） | 用户表达空间无限，而系统只认闭集槽位 | 槽位存**原话片段**；只识别"相对日 + 时段段"这一类表达；识别不了就**追问**，不猜 | 第 3 期做"条件搜索"时 |
| 2 | "降级换教室" 与 "偏好搜索" 的边界 | 前者是"指定教室办不到时换一间"，后者是"一开始就没指定、让我挑" | 现在只做前者（同楼栋、容量不降）；后者列为第 3 期 | 演示视频定型前 |
| 3 | 多资源部分失败怎么交代（订 3 间成 2 间） | 用户预期与系统能力有落差 | 逐条如实列出"成了哪几间、哪间为什么没成"；**不自动降级**到更小的教室 | 批量能力开发时 |
| 4 | 任务步数上限（现在 60 步）够不够 | 是按"一次借一间"标定的 | 多资源/周期能力实做时实测，再调整并回填文档 | 批量能力开发时 |
| 5 | **外部世界会变**（候补转正、别人取消我的预约） | 我们只负责自己发出的动作，管不了后续 | 话术纪律：**只承诺"我做了什么"，不承诺"世界会怎样"**；终态区分"我完成的"与"由系统后续触发的" | 候补能力开发时 |
| 6 | 身份权限的真实边界（能不能撤别人的预约） | 只能实测 | **openapi 已部分回答**：管理员撤销任意预约的接口存在（仅 ADMIN）；余下实测其返回码表与行为（能力清单 §六 #1） | 报修能力开发前 |
| 7 | 用户口语的歧义（"周三"是本周还是下周、节假日） | 语义歧义无法穷举 | 按"最近的那一个"并**在结论里显式标注我们的理解**（例："今天是周五，「周三」= 最近的周三 → 9 月 30 日"） | 已定（现状即可） |
| 8 | 界面上"能力入口"怎么排 | 属于产品设计 | 交界面方案（总纲 §五 方案 C） | 界面方案定稿时 |
| 9 | 事件类型的增长（每加能力可能加事件） | 闭集要登记，容易漏 | 每加一项能力，先问"现有事件类型够不够"；不够**先登记再实现** | 每项能力实现前 |

## 六、评审关卡（说好了 2–3 轮评审，每轮看什么）

| 轮次 | 评审对象 | 通过条件（产物） |
|---|---|---|
| **第 1 轮** | **做什么**：能力清单（14 项）、优先级、档位划分 | 每项能力有"用户话术 + 步骤链轮廓 + 展示价值"；无遗漏、无越界 |
| **第 2 轮** | **怎么做**：实现规格（本文 + 能力规格的 §三）、风险与责任口径 | 每个写操作都有查证路径与撤销方式；每个"需实测"项都有明确的验证方法；身份与责任边界写清 |
| **第 3 轮** | **怎么证明**：演示脚本改版、验收表、话术 | 14 项能力逐项有验收方式；视频分镜能覆盖"能办的事"且不演极小概率异常；话术不含接口术语 |

**每轮都要问的三个问题**（评审自查）：

1. 这一项**能不能被看见**？（看不见就不做，或降级为"留档 + 一句口播"）
2. 这项能力**失败时**用户看到什么？会不会让人以为系统坏了？
3. 有没有"**没写下来的前提**"？（有 → 补写，不许留）

## 七、本轮不做什么

- 不写实现、不改配置、不改代码；本文与配套方案先过评审，评审通过后才进入执行期。
- 不在本文里替你拍板 §五 的 9 项"难确定"——它们要么等实测，要么在评审时定。
