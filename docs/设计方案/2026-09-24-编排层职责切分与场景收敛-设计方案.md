## 1. 背景与业务事实

**业务事实（均已实测确认，非文档推断）**：

1. 学生/教师面对的是**无权修改**的存量校园系统（Spring Boot 3.5 + JWT + MySQL/Redis，39 个接口 / 12 张表）。
2. 一次"借教室"的判定需要跨 ≥3 个接口、跨 ≥2 个权限域聚合，且**读的粒度（座位）与写的粒度（整间教室）不一致**。
3. 业务错误**全部返回 HTTP 200**；"无权限"存在 `HTTP 403` 与 `HTTP 200+code=403` 两种表达。
4. 冲突检测有效，但 **409 是歧义信号**（无法区分"你自己已成功"与"别人占了"）。
5. 没有任何幂等键、唯一约束或"按教室+时段"的查证接口。

**项目约束**：校赛（华北五省计算机应用大赛）赛道一「大模型与智能体应用」；
强调原创性声明；**架构文档先于实现**。

## 2. 为什么"让 LLM 直接调接口"是错的

最省事的路径是给 LLM 挂上 function calling，让它自己决定调哪个接口、传什么参数。
这条路径在本项目里同时踩中三件事：

1. **不可解释**。LLM 为什么调这个接口？依据是什么事实？无法回答——
   直接破坏 `智能体设计.md` 的不变量 I4（可解释性）。而 I4 是"智能体"与"脚本"的分野。
2. **不可复现**。同样的输入可能得到不同的调用序列，故障无法稳定重放，
   混沌测试也就无法做——**没有确定性，就没有可验证的容错**。
3. **幻觉直落副作用**。一旦 LLM 决定调用写接口，参数幻觉的后果是往存量系统里写脏数据，
   且因为 §1 事实 5（无幂等），**写错了只能靠补偿，不能靠回滚**。

**结论：LLM 的能力必须被限制在"理解"环节，且其输出必须过 Schema 校验后才允许进入执行链。**

## 3. 建模判断：切分点画在哪

三种可能的切分方式：

| 方案 | LLM 职责 | 状态机职责 | 判定 |
| --- | --- | --- | --- |
| A | 理解 + 决策 + 调用 | 无 | ❌ 不可解释、不可复现、幻觉直落副作用 |
| B | 理解 + 决策 | 仅执行 LLM 给的调用序列 | ⚠️ 仍不可复现（序列由 LLM 决定），容错无法验证 |
| **C** | **仅理解**（意图 + 槽位） | **决策 + 执行**（由注册表映射接口序列） | ✅ 采用 |

**为什么 C 是对的**：把"不确定的部分"和"必须确定的部分"分到两个组件里，
并且让它们之间只有一个**受 Schema 约束的数据接口**。

```text
自然语言  ──LLM──▶  { intent, slots, missing[], confidence }
                          │
                     Schema 校验（不过则重试解析）
                          │
                          ▼
                    状态机（确定性）
                          │  查接口注册表
                          ▼
                    确定性接口序列 ──▶ 执行
```

**推论（已写入基线文档 §7.3，此处登记为设计决定）**：

- LLM **无权**决定调用哪个接口——接口序列由注册表按 `intent` 确定性映射；
- LLM 输出**不进入证据链**（非确定性，不可作依据），单独留档；
- **无 LLM 也能跑完整链路**——结构化任务可直接喂状态机。

最后一条不只是可测试性，还是一个**演示保险**：外部 LLM 限流或网络异常时，
可切换到预置任务继续演示，演示链路不因外部依赖中断。

## 4. 处置决定（2026-09-24）

| # | 决定 | 内容 |
| --- | --- | --- |
| 1 | **场景收敛到"教室借用"** | 一个主场景贯穿始终：借教室（含占用冲突降级 + 报修联动）。不铺开做"校园全场景"，场景数量换不来分数，讲解深度可以 |
| 2 | **不做第二个后端系统** | 单存量系统 + 双权限域已足够支撑"跨域聚合"叙事；理由与排除项见 `业务边界与责任域.md` §三 P1 |
| 3 | **状态机自研，不引工作流引擎** | 状态机是核心自研对象，引入 Flowable/Temporal 等于把创新点外包；需求规模（十余状态）也未到需要引擎的量级 |
| 4 | **调用结果采用三值语义** | `SUCCESS / FAILURE / UNKNOWN`；`UNKNOWN` 强制进入查证流程，不得悬空。这是本项目与普通接口封装最大的分野 |
| 5 | **幂等由编排层实现** | 以 `(身份, 资源, 时段)` 为业务键；重试前先查证。存量系统不提供幂等（已实测），**不得假设其存在** |
| 6 | **补偿采用编排式 Saga** | 由接口注册表为每个写接口声明补偿动作；**不假设补偿一定成功**，失败须显式登记 |
| 7 | **存量系统改动量为 0** | 运行配置走环境变量（借用其 `docker-compose` 变量名）、数据走外部脚本、故障注入走网关代理。详见 `存量系统改造说明.md` |
| 8 | **术语口径** | 不使用"遗留系统"（该代码是现代栈，会被问穿），统一称**"存量系统 / 存量业务系统"**，主张"我们无权修改它的代码" |
| 9 | **演示数据口径** | 主角教室为**数智楼 222（id=4）**；系统内无"302 教室"；两条既有维护窗口均为 `CANCELLED`，"教室在检修"须现场用 ADMIN 接口创建 |

## 5. 被明确排除的做法

1. ~~LLM 直接 function calling~~：不可解释、不可复现、幻觉直落副作用（§2）。
2. ~~引入 Flowable / Temporal 等工作流引擎~~：外包核心创新点；量级不匹配。
3. ~~自建两个独立后端服务伪造"多系统"~~：只增加跨进程一致性问题，不增加真实业务复杂度。
4. ~~为省事复用 ADMIN 单账号打通所有接口~~：技术上不成立（ADMIN 建不了整间预约，实测 200+code403）。
5. ~~保留两态（成功/失败）返回语义~~：无法表达"响应丢失但已写库"，与 I3 冲突。
6. ~~"顺手修好"存量系统的命名混用与错误语义~~：这些不一致是本系统存在的前提，
   修好等于拆掉自己的立论基础。见 `业务边界与责任域.md` §五 判定原则 6。
