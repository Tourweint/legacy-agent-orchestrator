# 2026-09-25 登录、身份与权限方案

> **文档性质：设计期过程文档，带日期。状态：三轮评审已完成（2026-09-25，三审通过，§六 待拍板全部销项）。三审结论见 [`../变更记录/2026-09-25-拓展方案三审-验收标准与拍板销项.md`](../变更记录/2026-09-25-拓展方案三审-验收标准与拍板销项.md)。**
> **来源**：作者 2026-09-25 追加要求——"需要做账号登录，不做肯定是不行。因为账号登录要记录是哪个同学约了教室……被观测的系统也有涉及到，**主要还是跟他对齐一下**"；"要区分一下，如果有些意图明显是滥用这些权利，肯定是要拒绝的"。
> **本文解决**：谁来登录、登录后以什么身份办事、哪些能力对哪些角色开放、越权怎么处理、以及**这一切怎么在视频里被看见**。
> **一句话**：**沿用存量系统自己的账号，登录在引擎里发生，读事实可以借"服务只读身份"，写操作只认本人身份，越权就明确拒绝。**

---

## 一、为什么必须改（现状与目标的差距）

| 项 | 现状（本方案之前） | 作者要求 |
|---|---|---|
| 谁在用 | 没有登录；前端直接以"TEACHER"身份发起 | **要有账号登录**，要能回答"是哪个同学约的教室" |
| 凭证 | 引擎内置三个固定账号的凭证池（管理员/教师/学生），从环境变量注入 | **与存量系统的账号体系对齐**（用同一套账号） |
| 身份选择 | 由意图计划写死"这一步用哪个身份" | **按登录用户的角色**决定能做哪些事 |
| 越权 | 未处理（因为没有登录，谈不上越权） | **明显滥用的意图必须拒绝** |

**为什么以前没有登录也说得通**：设计里把"使用者"抽象成"没有权限、也不懂接口的人"，身份由引擎按最小权限选。但作者指出的是**真实业务问题**：预约记录必须记到具体的人头上——这一条现有设计确实缺。

---

## 二、六条决定（每条附：为什么 / 备选与为什么排除 / 评估点）

### 决定 1：登录发生在引擎里，前端只拿引擎自己的会话

| 项 | 内容 |
|---|---|
| **决定** | 前端调引擎的登录接口 → 引擎用同一套凭据去调存量系统登录 → 存量系统的令牌**只留在引擎内** → 引擎给前端一个**自己的会话令牌** |
| **为什么** | ① 保住"唯一 HTTP 出口"这条结构约束（前端不直连存量系统）；② 凭证不出引擎（既有的凭证纪律）；③ 前端不需要知道存量系统的地址与协议（防腐层不泄漏） |
| **备选与排除** | ~~前端直接调存量系统登录~~：暴露其 URL、绕开出口纪律、把协议异构带进前端；~~前端保存存量 token 并回传~~：等于把凭证放到浏览器里 |
| **可行性评估点** | 需要你确认：**演示时是否接受"用户先在引擎页面登录，而不是先登录存量系统再打开我们的界面"**。我判断不了的是：评委是否会期待"我先在老的校园系统里登录过，然后打开你的界面免登录"。 |

### 决定 2：用户身份＝存量系统的账号（不建第二套用户体系）

| 项 | 内容 |
|---|---|
| **决定** | 用户用**存量系统的账号**登录（例如某个学生的账号）；引擎就用**这个人的令牌**去办事 |
| **为什么** | ① 作者要求"跟他对齐"；② 边界文档早就定了"用户体系与细粒度权限**不建模**"——不建第二套账号；③ 直接满足"记录是哪个同学约的"：写入者就是登录者本人；④ 强化最小身份原则（不再需要引擎替用户挑身份） |
| **备选与排除** | ~~引擎自建账号体系并映射到存量账号~~：要建库、要维护映射、还要处理密码安全，违反"零侵入 + 不建第二套体系" |
| **可行性评估点** | 需要你确认：**演示用哪几个账号**（本机可用的有 管理员 / 教师 233 / 学生 abc，其自带文档里的学生账号是错的）。我判断不了的是：比赛提交材料里是否需要说明"账号由评测方提供"。 |

### 决定 3：**读事实可以借"服务只读身份"，写操作只认本人**

> 这是本方案最关键的一条，也是直接回应作者"关联权限给 A，让 A 去查这些东西没问题"。

| 项 | 内容 |
|---|---|
| **决定** | ① **业务写操作**（提交预约、撤销自己的记录、排队）**只能用登录者本人的身份**；② **只读的事实收集**（如查维修窗口必须管理权限）允许引擎用**一个服务只读身份**去读；③ **唯一例外（一审修订）**：C14 报修联动中"建维修窗口"与"撤销受影响预约"用**服务管理身份**执行——openapi 确认存量系统只允许管理员做这两类动作（`POST /admin/maintenance`、`DELETE /admin/reservations/{id}` 均仅 ADMIN），受影响预约的本人并不在场，不存在"用各自的账号"的可能；作为交换，这两步**必须先经用户两段式确认**（本系统唯一的例外通道）；④ 无论哪种，**每次调用都记入证据链**（用了哪个身份、读/写、为什么） |
| **为什么** | ① 如果不允许借只读身份，**教师登录后将无法判定"能不能借"**——查维修窗口要管理权限，教师读会被拒（实测 403），于是系统只能保守拒绝一切，产品不可用；② 只借用**读**权限，不借用**写**权限，越权风险为零；③ 用户知情：界面上明示"本次判定用了管理只读身份读取维修安排"（这正是可解释性的展示点） |
| **备选与排除** | ~~全部只用本人身份~~：如上，功能会不可用；~~全部用管理员身份~~：技术上管理员建不了教室预约，且彻底破坏最小身份原则 |
| **可行性评估点** | 需要你确认：**"服务只读身份"是否需要在界面上明示**（我的建议：明示，且是加分项）。我判断不了的是：评委是否会把"借只读身份"误解成"提权"。 |

### 决定 4：角色决定可用的能力（意图 × 角色矩阵）

| 角色 | 能做的事（写） | 能查（读） |
|---|---|---|
| **学生** | 座位预约、候补排队、撤销自己的记录 | 教室可用性、教室发现、自己的预约与候补、通知 |
| **教师** | 教室预约、撤销/改期自己的记录、报修联动 | 同上 + 跨域事实判定（借只读身份） |
| **管理员** | 维修窗口创建/取消、"服务只读身份"的持有者 | 全量预约、维修窗口、配置、统计 |

**不在表里的意图 → 拒绝**（不是"试试看"）。

### 决定 5：越权一律明确拒绝并解释（不降级、不猜测）

| 项 | 内容 |
|---|---|
| **决定** | 登录用户的角色**不允许**某意图时：立刻拒绝，并说明"为什么不行 + 谁能办"；**不得**改用高权限身份代办 |
| **为什么** | ① 不变量 I5：无权限时不重试、不降级猜测；② 作者要求"明显滥用的意图要拒绝"；③ **这本身是展示点**——"有依据的拒绝"体现系统懂规则 |
| **话术示例** | 学生说"帮我借周三下午数智楼123" → "整间教室的预约只能由教师提交，你的账号是学生身份。我可以帮你排这个时段的座位候补，或帮你查这间教室的空闲情况。" |
| **可行性评估点** | 需要你确认：被拒绝时**是否要推荐替代动作**（我建议要，因为"给下一步"是既有的话术纪律）。 |

### 决定 6：登录态的生命周期与"多设备"陷阱

| 项 | 内容 |
|---|---|
| **决定** | 引擎维护会话（内存即可，重启即失效）；空闲超时后要求重新登录；登出立即失效；存量令牌过期由引擎**自动重新登录一次**（拿不到就如实告诉用户"登录已失效"） |
| **为什么** | 演示要稳：不能中途弹"未登录"；也不能假装还登录着 |
| **⚠️ 隐含前提显式化（一审补）** | ~~"自动重新登录"意味着引擎要在**会话内存里保存用户的密码**（存量系统没有刷新令牌接口）~~ → **2026-09-26 实测推翻并改实现**：存量系统**有**刷新令牌接口（`POST /auth/refresh`，且刷新令牌轮换、旧的一次性作废）。因此**不保存密码**，续期走刷新令牌（单飞，避免并发刷新用废轮换令牌）；续期失败则如实提示"登录已失效，请重新登录"。实测与实现见[登录会话与权限实现登记](../变更记录/2026-09-26-登录会话与权限实现登记.md) §二/§三 |
| **⚠️ 已发现的坑** | 存量系统限制**同一账号最多 3 个设备会话**（常量 `APP_AUTH_MAX_DEVICE_SESSIONS=3`）。我们平时会用同一个账号在多个窗口/多次录屏里登录 → **会把先登录的踢下线**（表现为"刚才还能用，突然 401"）。这是**录制视频时最容易翻车的一条**。**一审补**：`deploy/scripts/` 的预置/复位/检查脚本**自己也会登录存量系统**（同样占会话名额）——录制顺序必须写死：**先跑预置脚本 → 再引擎登录 → 再浏览器登录**；脚本用完即退，或预置用独立账号 |
| **应对** | ① 录制前统一账号与窗口数量；② 登录失败/被踢时给明确话术；③ 把这条写进"录制前检查"（含脚本占用的会话） |
| **需实测** | 踢下线的确切表现与响应码；重复登录是否计入会话数 |

## 三、要改哪些地方（影响面清单）

| # | 位置 | 改什么 |
|---|---|---|
| 1 | 引擎对外接口 | 新增 `登录 / 登出 / 我是谁` 三个端点；其余接口要求携带会话令牌；未登录返回明确错误码 |
| 2 | 会话与身份 | 新增"会话 → 用户 → 角色 → 存量令牌"的映射；身份选择从"意图计划写死"改为"会话驱动（写）＋ 服务只读（读）" |
| 3 | 意图计划 | 每条意图加"**所需角色**"与"**是否含写操作**" |
| 4 | 意图鉴权 | 入口处按"意图 × 角色"判权限，不通过即拒绝（在**任何调用发生之前**） |
| 5 | 证据链 | 每条记录带**发起人**（登录用户）与**本次使用的身份**（本人/服务只读）——这是"记录是哪个同学约的"的落地 |
| 6 | 前端 | 登录页、角色标识、会话失效提示、按角色展示可用的能力入口 |
| 7 | 演示脚本 | 新增"登录"镜头；新增"越权被拒绝"镜头（短，≤20 秒，与演示改版方案第 8 幕对齐） |
| 8 | 边界文档 | §四 速查表补"登录与身份"一行；"用户体系不建模"改为"**不建第二套体系，但承接登录态**" |
| 9 | 对外接口清单 | 三个新端点 + 会话相关错误码登记（该文档是闭集登记件，**必须先登记**） |
| 10 | **事件流（SSE）鉴权（一审补）** | 前端用 `EventSource` 订阅事件流，**无法带自定义请求头**——会话鉴权方式要专门定：**倾向 = 引擎会话令牌走 Cookie**（前端经 `/api` 同源代理，Cookie 自然携带、不暴露在 URL）；备选 = 查询参数带令牌（会进访问日志，不倾向）。登记进对外接口清单 |
| 11 | **identity-pool.js 重构（二审补）** | 现有身份池是"按意图计划的 requiredIdentity 从固定账号池选身份"。登录后改为：**写操作 = 会话中登录者本人的令牌**；**读操作 = 服务只读身份（管理员账号，仍从环境变量注入）**。身份池不再持有教师/学生账号，只保留管理员服务身份。这是接触层的核心改动，影响所有调用的身份选择逻辑。 |
| 12 | **task-store.js 增加 owner 字段（二审补）** | 现有任务存储没有"所属用户"概念。登录后每个任务须记录 `owner`（登录用户 id/username），用于：① 取消任务时校验"只能取消自己的"；② 任务列表/快照时过滤本人任务。任务仍不跨会话（A6 不变），但同一会话内的任务归属要可查。 |
| 13 | **evidence-chain.js 增加 initiator 字段（二审补）** | 现有证据链条目没有发起人。登录后每条证据须带 `initiator`（登录用户）与 `actingIdentity`（本次调用实际使用的身份：本人/服务只读/服务管理）——这是"记录是哪个同学约的"的落地，也是可解释性的展示点。证据导出（`/evidence`）须同步输出这两个字段，且凭证字段仍须脱敏。 |
| 14 | **现有接口 identity 参数废弃（二审补；三审拍板保留 deprecated）** | `POST /api/tasks` 与 `POST /api/chat` 现都有 `identity` 参数（TEACHER/STUDENT/ADMIN，现状为必填，不填报 4004）。**三审口径**：登录会话上线后该参数 **deprecated 但保留**——身份一律从会话派生，请求里**传了也忽略**，不传不再报 4004（4004 随会话鉴权上线退役）；对外接口清单已登记 deprecated。现有 140 个测试批量迁移为"先登录再调用"（本轮最大测试改动面）。**移除时机＝全部调用方迁移完成后，本轮不删、不双轨**（会话与参数冲突时永远以会话为准，不做合并语义）。 |
| 15 | **http-server.js 会话中间件（二审补）** | 新增会话解析中间件：从 Cookie（或 Authorization 头）解析引擎会话令牌，挂载 `req.session`（含 userInfo + 存量令牌）。未登录访问受保护端点返回新错误码 `4010`（未登录）。SSE 端点同样受中间件保护。 |
