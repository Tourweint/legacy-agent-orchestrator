## 一、一句话结论

**对 `mock-legacy/` 源码的改动量为 0 个文件**——没有修改、没有新增、没有删除任何源码文件。

所有为了「在本机跑起来」而做的事情（装 Redis、建库导数据、注入运行配置、编译产物）**全部落在它之外**，不在它的仓库树里留文件。故障注入（含"半成功"）由我们自己的**网关故障代理**实现，同样不进入它的进程。

因此：**本作品主张的"零侵入对接存量系统"不是营销话术，是可以被 diff 验证的事实。** 验证方式见 §七。

本作品的核心主张是「**不改动存量系统，也能让它长出自然语言接口**」。这个主张一旦被质疑，整个作品的价值就塌了。最常见的三种质疑是：

| 质疑 | 本说明的回答位置 |
|---|---|

| "脏数据是不是你人为造出来演的？" | §八（全部异构点均来自代码客观现状，附源码位置） |

## 四、三道防线：为什么可以做到零侵入

### 防线一：运行配置走环境变量，不写配置文件

该项目 `application.yaml` 中声明了 `spring.profiles.active: local`，指向 `application-local.yaml`——但**该文件不存在**，因为它被项目的 `.gitignore` 明确排除了：

```gitignore
# 摘自 mock-legacy/.gitignore
backend/src/main/resources/application-local.yaml
```

也就是说：原作者本地的这份配置从未提交，仓库是"缺配置"状态。常规做法是补一个 `application-local.yaml` 进去——**但那就在第三方仓库里新增了一个文件**。

我们改用**环境变量注入**。Spring Boot 的宽松绑定会把形如 `SPRING_DATASOURCE_URL` 的环境变量映射到 `spring.datasource.url`，效果与写在配置文件里完全一致。而且该项目自带的 `docker-compose.yaml` 用的正是同一套变量名——**这是我们借用它自己已有的机制，不是我们发明的旁路**。

### 防线二：故障注入走网关代理，不进它的进程

"半成功"（服务端已提交、响应在返回途中丢失）这类故障，必须在**服务端真实写库之后**发生，因此不能只在"请求发出前"拦截。

我们的做法是在编排引擎的**接触层出站管道**上放一层**故障代理**（它就在编排引擎进程内，但逻辑上处于引擎与存量系统之间）：

```text
编排引擎 → 故障代理（可注入故障） → 存量系统（真实写库）
```

代理转发请求 → 等待后端完成并提交事务 → **丢弃响应**。此时存量系统里已经真实落库，而调用方只看到超时。故障由此产生，且**存量系统一行代码都没碰**。

> **为什么放在"唯一 HTTP 出口"上而不是另起一个代理进程**：编排引擎里只有接触层能发起对存量系统的请求（设计方案第 02 章 约束 A），因此**注入点在结构上天然唯一**，不需要额外保证"注入点不被绕过"。另起一个独立代理进程会多一个进程、一个配置项，并让"唯一出口"这条约束的检查变得模糊。
>
> 详细规格见 `docs/设计方案/2026-09-24-系统设计方案/09-故障注入与混沌实验方案.md`。

> 注：这与"改被测后端加故障开关"的方案相比，除了零侵入，还有个额外好处——它复现的是**真实的网络层故障**（响应丢失），而不是一个被后端主动抛出的假异常。

### 防线三：数据准备与复位走外部 SQL，不改它的初始化脚本

`classroom.sql` 中每张表都有 `DROP TABLE IF EXISTS`，可重复导入。演示数据准备与复位全部通过 `deploy/scripts/reset-legacy-data.sh` 在库这一层完成，不改它的初始化脚本。

**需要特别注意**：演示场景所需的额外数据（例如"某间教室正在检修"）应通过 **ADMIN 接口在线创建**，而不是直接插库。理由：走接口创建才能证明"这是存量系统里本来就有的业务数据"，而不是我们伪造的。

## 五、运行配置注入清单

以下变量是**必需**的。缺任意一项都会导致启动失败或功能异常（已在实测中踩到，见 §七）。

| 环境变量 | 对应配置项 | 本机取值 | 缺省后果 |
|---|---|---|---|
| `SPRING_DATASOURCE_URL` | `spring.datasource.url` | `jdbc:mysql://localhost:3306/classroom?...` | 启动失败：无法创建数据源 |
| `SPRING_DATASOURCE_USERNAME` | `spring.datasource.username` | `root` | 同上 |
| `SPRING_DATASOURCE_PASSWORD` | `spring.datasource.password` | `123456` | 同上 |
| `SPRING_DATA_REDIS_HOST` | `spring.data.redis.host` | `localhost` | 登录后所有接口 401 |
| `SPRING_DATA_REDIS_PORT` | `spring.data.redis.port` | `6379` | 同上 |
| `SPRING_MAIL_HOST` | `spring.mail.host` | 占位值 | **启动失败**：`MailService` 依赖 `JavaMailSender` Bean，而该 Bean 仅在 `spring.mail.host` 存在时才创建 |

## 六、明确排除的改造项（**坚决不做**）

以下六项技术上"改了会更好用"，但我们**明确选择不改**。这一节是答辩时"你为什么不顺手把它修好"的标准答案。

| 编号 | 存量系统的现状 | 改掉之后的后果 | 决策 |
|---|---|---|---|
| N1 | **业务错误几乎全部返回 HTTP 200**，错误语义只写在 `body.code` 里（如冲突返回 `HTTP 200 + {"code":409}`） | 协议立刻变干净，**防腐网关的"响应归一化"就没有了存在理由** | **不改**。异构是网关的存在前提 |
| N2 | 同一个"无权限"有**两种表达**：过滤器层拒绝给 `HTTP 403`，方法层 `@PreAuthorize` 拒绝给 `HTTP 200 + {"code":403}` | 语义统一了，"统一鉴权与错误归一"的价值消失 | **不改** |
| N3 | **JSON 字段命名混用**：部分 DTO 用 snake_case（`classroom_id`、`start_time`），部分用 camelCase（`roomNumber`、`seatRows`、`resourceType`），`MaintenanceCreateDTO` **同一个请求体内两种混用** | 命名统一后，网关的"字段映射"退化为机械转换 | **不改** |
| N4 | **请求与响应的时间语义不对称**：请求用 `OffsetDateTime`（需带 `Z`），响应用 `LocalDateTime`（**丢掉时区**，返回 `2026-09-25T02:00:00`） | 时间语义统一后，跨系统事实比对不再需要网关兜底 | **不改** |
| N5 | **`GET /classrooms/available_list` 完全没有时间参数**，只按楼栋/容量筛，返回结果**忽略了该时段是否已被占用** | 补上时间过滤后，"跨接口聚合才能回答'这间教室现在能不能用'"这个核心命题就不成立了 | **不改**。这是本作品立论的支点 |
| N6 | **没有按"教室 + 时段"查询预约的接口**。查证只能走 `GET /admin/reservations?keyword=`，而 keyword 只匹配 `user_id`/`resource_id`/`reason`，**不匹配教室名**，且**没有时间过滤** | 补一个精确查询接口后，引擎的"查证"就变成一次简单调用，失去工程含量 | **不改**。这是幂等查证路径的难点来源 |

**一句话原则**：这些不一致是**存量系统的客观属性**，不是我们的 bug。我们的工作是在**不触碰它**的前提下消化这些不一致——这恰好就是防腐层的定义。

### 7.3 一处必须更正的早期假设

> **更正**：本作品早期设计文档中曾假设"重复提交会产生两条记录，数据库无唯一约束"。**实测证明该结论不成立。**

实测结论是：两种预约接口**都有时间重叠冲突检测**，重复提交返回 409，且在 6 路并发下仍只落库 1 条。数据库层面确实只建了 `PRIMARY KEY(id)`、没有任何业务唯一约束（`SHOW INDEX` 确认），但冲突检测在应用层生效，实测未观察到脏数据。

**这不但没有削弱本作品，反而让"幂等"的命题更准确**：真正的问题不是"会产生重复"，而是——

> **409 是一个歧义信号。** 它既可能是"你自己刚才那次其实提交成功了"，也可能是"别人抢先占用了这个时段"。系统**无法区分**（两种情况的响应完全相同）。
> 因此引擎**既不能把 409 当成功，也不能当失败**，必须走查证路径来消解歧义。
> 而在"响应丢失"场景下，这个歧义会导致**用户被误报为失败、而系统里实际已存在占用**——状态不一致。

这条更正已同步进接口注册表与状态机设计。

## 八、存量系统能力探针结果

以下全部为**实测所得**，是接口注册表（编排引擎的**配置数据**，见设计方案第 02 章 §八）的输入素材。均为该系统源码的客观现状，附源码位置以便复核。

### 8.1 接口前缀：文档是错的

| 项 | 说明 |
|---|---|
| **真实 API 前缀** | `http://localhost:8080`，**没有 `/api` 前缀**。控制器映射为 `/auth`、`/classrooms`、`/reservations`、`/admin/...` |
| `/api` 从哪来 | 前端 `frontend/vite.config.js` 中 Vite 代理的 `rewrite: path => path.replace(/^\/api/, '')` 把它剥掉了 |
| 后果 | `curl http://localhost:8080/api/auth/login` → `401 未登录或令牌无效`（因为不存在该映射，落到安全过滤器） |

`backend/src/main/resources/static/openapi.yaml`（OpenAPI **3.0.3**，39 个 path，`servers: http://localhost:8080`）**是正确的**，可直接作为接口注册表的自动导入源。而 `mock-legacy/接口文档.md` 的"Base URL `/api`"一节是错误的——**同一份仓库里，机器可读的文档对、人读的文档错**。

### 8.2 协议异构点清单（网关必须吸收）

| 类别 | 具体表现 | 源码位置 |
|---|---|---|
| **HTTP 状态码语义** | 业务错误一律 `HTTP 200`，语义只在 `body.code`：冲突=`code 409`、参数非法=`code 400`。**"资源不存在"按接口分叉（三审实测更正）**：`GET /classrooms/{id}` 不存在 → `code 400`；创建预约时教室不存在、撤销时记录不存在 → `code 404`（同一语义两个码） | `exception/GlobalExceptionHandler.java`、`enums/ResultCode.java`（三审实测，见 §7.4） |
| **认证/授权例外** | 未认证 → `HTTP 401`；过滤器层权限不足 → `HTTP 403`；**方法层 `@PreAuthorize` 权限不足 → `HTTP 200 + code 403`** | `config/SecurityConfiguration.java`、`security/JwtAuthenticationFilter.java` |
| **字段命名** | 请求侧部分 snake（`classroom_id`/`seat_id`/`start_time`）、部分 camel（`roomNumber`/`seatRows`/`resourceType`）；**`MaintenanceCreateDTO` 同一请求体内两种混用**；响应侧全部 camel | `dto/*.java` |
| **时间语义** | 请求 `OffsetDateTime`（需 `Z`）；响应 `LocalDateTime`（**丢时区**，返回 `2026-09-25T02:00:00`） | `dto/ClassroomReservationCreateDTO.java` vs `vo/ReservationVO.java` |
| **查询参数命名** | `min_capacity`（snake）与 `classroomId`、`resourceType`（camel）并存 | `controller/ClassroomController.java`、`AdminMaintenanceController.java` |
| **校验消息口径** | 消息里用的是 **Java 字段名**而非 JSON 字段名（如字段声明 `@JsonProperty("classroom_id")`，但报错文案是 `"classroomId 教室ID不能为空"`） | `dto/ClassroomReservationCreateDTO.java` |

### 8.3 权限鸿沟（多身份编排的依据）

| 接口 | 所需角色 |
|---|---|
| `GET /classrooms/*`（查询类） | 已登录 |
| `GET /classrooms/{id}/reserved_seats` | `STUDENT` / `TEACHER` |
| `POST /reservations/seats` | `STUDENT` |
| `POST /reservations/classrooms` | `TEACHER` |
| `GET /admin/maintenance`（查维修） | `ADMIN` |

**同一条业务链路横跨 TEACHER 与 ADMIN 两个身份域**——这就是"多身份凭证池"必须存在的理由，不是设计上的过度包装。

### 8.4 能力缺口（编排层要补的洞）

| 缺口 | 实测证据 | 编排层的应对 |
|---|---|---|
| 无法按"教室 + 时段"判断可用 | `available_list` 无时间参数，且返回了已被占用的教室 | 跨接口聚合：`reserved_seats` + `admin/maintenance` + `classrooms/{id}.status` |
| 占用信息是**座位粒度** | `reserved_seats` 返回 `[309,310,...]` | 需要把座位集合**推导**为教室级占用判定 |
| 查证无法精确过滤 | `keyword` 只匹配 `user_id`/`resource_id`/`reason`，**不匹配教室名**，**无时间过滤** | 取回列表后在内存做时间重叠判定 |
| 查证需要 ADMIN 身份 | `/admin/reservations` 仅 ADMIN | 查证也走身份池 |

### 8.5 演示数据现状

| 项 | 现状（三审 2026-09-25 复核） |
|---|---|
| 教室 | **共 7 间，全部 `ENABLED`，无空 status**，无"302"。数智楼 5 间：**111=48 座（8×6，id=10）、123=48 座（id=5）、222=55 座（11×5，id=4）、233=32 座（id=7）、431=9 座（id=6）**；电信楼 111/112 各 48 座（id=8/9） |
| 维护窗口 | 2 条，**均为 `CANCELLED`**（该表只有 `ACTIVE/CANCELLED` 两态，不存在"正在检修"的教室） |
| 预约 | 86 条种子数据：**全部是预约记录**（CLASSROOM 23：12 取消/11 过期；SEAT 63：50 取消/13 过期；**无一条 ACTIVE**）。**三审更正**：签到 20 条、用量 15 条在**独立表**（`reservation_attendance`/`reservation_usage`），**不在预约表中、不混入任何列表接口**——此前"预约含签到/用量记录"的说法错误 |
| 系统配置 | 23 条：单次预约时长上限 A/B/C=360/180/120 分钟、单日 720/540/480（**TEACHER 豁免，见 §7.4**）、可预约时段 07:00–22:30 |

**对演示的影响**：
1. 演示台词里的"302 教室"必须换成真实教室。**三审已定：主演示教室用数智楼 123（48 座，id=5）**——数智楼 222 容量 55 为全栋最大，一旦它被占，同楼栋找不到"不降容量"的降级候选；第 4 幕设计为 **123 被占 → 降级改订 222（55 ≥ 48，候选合法）**。
2. "教室正在检修"不能假设，**必须在演示前用 ADMIN 接口现场创建一条 `ACTIVE` 的维护窗口**（三审已走通：`POST /admin/maintenance` 创建后，`reserved_seats` 对该时段返回全量座位）——这样"旧系统里本来就有的维修单"才站得住，且该动作本身就是 ADMIN 身份编排的展示机会。

## 十、已知风险与对策

| 风险 | 触发条件 | 对策 |
|---|---|---|
| 演示前忘记启动 Redis | 忘了开 | `start-legacy.sh` 启动时会探测 6379 并告警 |
