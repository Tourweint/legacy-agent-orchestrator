# 引擎入口缺陷修复与一键启动脚本

> **文档性质：变更记录（带日期，追加不改写）。时点：阶段 8 与参数标定收尾之后，交付收口轮。**
> 触发：复核"项目是否已完成"时要求补一个 Windows 一键启动脚本；准备脚本时发现**引擎入口根本起不来**——`npm start` 自阶段 8 起即为崩溃状态。
> 结论：**阶段 8 的"验证"存在盲区**（`npm test` 与 `npm run check` 都不加载入口文件），该缺陷未被任何现有验证捕获。

## 一、缺陷：`npm start` 崩溃（阶段 8 引入）

**现象**：`node src/access/main.js`（即 `npm start`）立即抛 `ReferenceError: pool is not defined`，进程退出，8090 不监听。

**原因**：阶段 8 为把 `ChaosController` 接到出站管道上（第 09 章 §七），改写了 `orchestrator/src/access/main.js` 的装配代码，其中

```js
const identityPool = new IdentityPool({ ... })            // 第 40 行：变量名是 identityPool
createAccessServer({ ..., identityPool: pool, ... })      // 第 42 行：却引用了不存在的 pool
```

即**一次纯笔误**：`identityPool` 被写成了 `pool`。引入提交 `22a1d21`（阶段 8 交付）。

**为什么没有被发现**（三个验证都没覆盖入口）：

| 验证 | 为什么不覆盖 |
|---|---|
| `npm test`（140 个用例） | 全部走 `createAccessServer` / 各层模块的直接装配，**从不 import `src/access/main.js`** |
| `npm run check`（8+4） | 静态结构检查：状态机表、配置数据、三条结构性约束的 grep 式判否，不执行入口 |
| `deploy/scripts/demo-checklist.sh` | 它是**在引擎已运行之后**做探活（8080/8090/5173 存活），不负责启动引擎；且当时用的是一个更早启动的进程 |

**影响范围**：引擎无法启动 → 前端（5173 需 8090）、演示第 5 幕（注入经引擎重启布防）、`smoke-contact.mjs` 之外的端到端路径全部不可用。**因此文档中阶段 8 之后"`npm start` 可运行于 8090"一类表述，在当时并不成立。**

**连带更正**：本仓库 2026-09-25 各变更记录里"验证：npm test 140/140、check 8/8+4/4"是**真**的，但它**不足以支撑"可运行"的结论**——这一点此前没有写明，本记录予以明确。

## 二、修复

```js
const { server } = createAccessServer({ configStore: store, transport, identityPool, adapters })
```

一行改动，恢复为装配处定义的变量名。未改任何设计口径、未触碰其余模块。

## 三、新增：`start-all.bat`（仓库根，Windows 一键启动）

| 项 | 说明 |
|---|---|
| 用法 | 双击运行＝`all`；也可 `start-all.bat [all\|legacy\|engine\|web\|deps\|dry]` |
| 启动对象 | 存量系统 `8080`（JDK 17 + 环境变量注入）、编排引擎 `8090`、前端 `5173`；各自开一个独立窗口（`cmd /k`，Ctrl+C 或关窗即停） |
| 前置检查 | Node、Maven、JDK 17 路径、Redis 6379、MariaDB 3306、三个端口占用情况；**端口被占用则跳过该项**而不是重复启动 |
| 就绪等待 | 8080 最多 90s、8090/5173 各 30s；8090 另做 `GET /api/health` 探活。睡眠用 `ping -n 4 127.0.0.1` 而非 `timeout`（后者在 stdin 被重定向时立即报错退出，会让等待循环空转——见 §四.6） |
| 配置来源 | `deploy/config/legacy.env`（存量系统，模板见 `legacy.env.example`）与 `deploy/config/orchestrator.env`（引擎凭证）；**存在即载入，缺失则用内置默认值**（与 `start-legacy.sh` 的默认值保持一致） |
| 零侵入 | 不向 `mock-legacy/` 写入任何文件；**不设置 `ORCH_CHAOS_INJECT`**（混沌默认撤防，与第 09 章 §七 一致） |
| `deps` / `dry` | 前者只做检查不启动；后者只打印将执行的命令，便于核对与排障 |

**未纳入**：`--stop` 之类的收尾能力——杀进程属于破坏性操作，交给人手动关窗更安全。

| 6 | `start-all.bat engine` | ✅ 单组件模式路由正确：未误启存量系统与前端，健康探活命中既有 8090 进程返回 200 |
| 7 | 窗口派生语法 | ✅ 同形式 `start "标题" /D "目录" cmd /c "命令"` 实测成功派生 |
| 8 | **`start-all.bat all` 完整启动（端口全空的真机）** | ✅ 旧进程停掉后三端口全空：脚本拉起三个窗口，**8080 / 8090 / 5173 全部就绪**，`GET /api/health → 200`（新进程，含入口修复与阶段 8 混沌接线） |
| 9 | 停止旧进程的方式 | ✅ 逐棵树 `taskkill /F /T`（`sh.exe`→maven→存量系统 java、`npm start`→cmd→引擎 node、`npm run dev`→cmd→vite）；Redis/MariaDB 未受影响、保持在线 |

**同一轮里修掉并复验的脚本缺陷**：首跑 `all` 时，就绪等待的 `timeout /t 3` 在 **stdin 被重定向**（`< nul`，以及计划任务/CI 场景）下立即报 `Input redirection is not supported` 并退出，导致等待循环空转、把 8080/5173 误判为"未就绪"。已改用 `ping -n 4 127.0.0.1 >nul`，复验无报错。**这条说明"跳过/等待"这类逻辑必须在非交互调用下也验一遍。**

**未验证项（如实登记）**：
- 8080 与 5173 的"就绪"是在 `all` 首次运行之后的补充观测中确认的（首跑时被上述 `timeout` 缺陷误判）；修复后的等待逻辑本身只在非交互下单独验过睡眠，**未重跑一次完整的 `all`（端口已被本次启动占用）**。
- 未重跑 `npm run experiment`（需存量系统在线）与七幕演示；本轮只修复入口，未触碰编排行为。

## 五、给后续会话的提醒

1. **"测试全绿"不等于"能启动"。** 单测与静态自检都不加载进程入口；改动装配代码（尤其是新增/重命名变量、接线新模块）后，**必须真的把进程起一次**。建议后续在 `orchestrator/scripts/` 下补一个"入口冒烟"（用 `ORCH_PORT=0` 起一个临时端口再退出）并纳入 `npm run check`。
2. **端口被占用时的"跳过"是刻意设计**：它避免了"以为重启了、其实跑的还是旧进程"——这正是本次发现的场景（旧进程仍在服务，健康检查照样返 200）。

## 六、回滚建议

- 入口修复是一行、无副作用，**不建议回滚**（回滚即引擎不可启动）。
- `start-all.bat` 为纯新增件，删除即回滚，对引擎与存量系统无依赖。
