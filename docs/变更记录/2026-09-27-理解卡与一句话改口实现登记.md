## 一、做了什么

### 引擎侧（3 处，已全部验证）

1. `orchestrator/src/orchestration/chat-bridge.js`
   - 新增 `#decideUnderstand(taskContext, understanding, mergedSlots)`：打包理解结论事件（`decide:understand`），**ok 路径**在槽位合并（`taskContext.slots = {...}`）之后调用，附 `conclusion.structured`（intentId/intentName/slots/confidence）；
   - 澄清（置信不达标）与 out-of-domain 路径在进入各自处理前调用 `#decideUnderstand(..., null)`——**不带结构化载荷**（追问不渲染理解卡）；
   - 新增 `#understandPayload`：生成 `text` 与结构化载荷，槽位 label 取自 `getGlossary().slots`、value 是原话片段，**text 与 slots 用同一份格式化逻辑**（取代原 `#understandSummary`，不再长第二份格式化）。

2. `orchestrator/src/access/event-stream.js`
   - `decide:` 分支把 `conclusion.structured` 的 intentId/intentName/slots/confidence 透传到事件帧（不带则不加字段）；
   - **新增 `isWrite`**：`contact:*` 调用事件按接口注册表 `sideEffect=true` 判定（新增 `buildWriteInterfaceIds`）——只读查证调用不算"写请求已发出"。这是改口/取消窗口的权威判据。

3. `orchestrator/test/access.test.mjs`（+3 测试，200 → 203）
   - ok 理解：decision 事件带结构化载荷（intentId/intentName/slots 中文 label/confidence/text 同源）断言；
   - 置信不达标（intent-choice 追问）：decision 不带结构化载荷断言（挂起任务事件流不关闭，改从证据链断言）；
   - call 事件 `isWrite`：写调用 true、只读查证 false 断言。

### 前端侧

1. **新组件 `frontend/src/components/UnderstandingCard.vue`**：理解卡——意图名 + 槽位 chips + "改一下"按钮。数据源=该轮最新一条带 intentName 的 P1 decision 事件（追问补槽位后引擎会再发一条，取最新的合并后理解）；`readonly`（历史轮）不渲染按钮，纯展示。

2. **`frontend/src/components/ChatPane.vue`**：
   - 每轮在用户消息之后渲染理解卡；
   - **send() 守卫**（顺带修洞：此前运行中回车可并发第二个任务）：`pending && !writeIssued` → 这句话是**改口**——`cancel()` 取消原任务，**等终态事件**（settleCancelledTurn 收口）后自动 `startChat` 新轮；`pending && writeIssued` → 输入框已禁用兜底忽略；`suspended` → 追问回复（**绝不当改口**，B2）；`terminal` → 正常续话；
   - "改一下"按钮：聚焦输入框 + 占位提示"直接说正确说法，比如：不是周三，是周四"；写请求已发出（isWrite）时置灰，title 说明"已经开始办理，改的话会自动退旧办新"；
   - 改口中显示"正在按你的新说法重新理解……"。

3. **`frontend/src/composables/useThinking.js`**：移除 P1 decision 的强制 `focus`（`:124-125`）——理解展示由理解卡承接，办成/办不成时思考过程不再重复"识别为…"（避免同一句理解出现两份）。`failCount` 语义不受影响。

4. **`frontend/src/stores/task.js`**：`writeIssued` 从"存在 P3/P4/P5 事件"改为 `call 事件且 isWrite === true`——与引擎 CANCELABLE_STATES 同口径（查证阶段仍可改口/取消，只有真正有副作用的写请求才锁住）。

5. **`frontend/src/components/Composer.vue`**：新增 `hint` prop（"改一下"的占位提示，覆盖默认 placeholder）。

6. **测试与文档**：`frontend/test/use-thinking.test.mjs` 两处断言同步（办成时 focus 集合为空、办不成时理解行仍在 L2 但不 focus）；`docs/基线文档/对外接口清单.md` §四 登记 call 的 `isWrite` 与 decision 的结构化载荷。

## 三、实测撞出的相邻缺陷（不在本方案范围，另立任务）

1. **reply 理解漂移**：挂起追问回复"下午三点到四点"被真实 LLM 理解成「查询教室可用性」（新意图）而非"补 timeSegment 槽位继续借教室"。回复文本重新走理解层时缺少"继续上一轮意图"的强约束——需在理解层 prompt / chat-bridge resume 分支补约束。
2. **B5 记忆槽位恒空 + 被取消轮也入记忆**：`task-runner.js:151 #chatSummary` 读 `tc.chat?.slots` 但全仓无写入点（slots 恒 `{}`）；取消轮以 REJECTED 记入会话记忆。后果：改口新轮"改成周五下午"接不上上一轮的教室槽位（追问"哪间教室"）。要"取消轮不进下一轮记忆 / slots 真实注入"需引擎改动。
3. **会话记忆端到端断言假绿**（`access.test.mjs` 原 618 行）：断言 assistant 消息含"数智楼123"实际命中 few-shot 例子（注入记忆实为 `{"intent":"borrow-classroom","slots":{},"outcome":"DONE"}`）。

## 四、演示口径提醒

写入前改口窗口约 2–3 秒（全自动借教室），录制靠手速；更稳的演示话术是**在理解卡出现后立刻说纠正句**（此时任务在查证阶段，isWrite=false，仍可改口），或直接演示"改一下"按钮聚焦输入框的引导。改口话术建议带全信息（"不是下周三，改成下周五下午数智楼222"），不依赖槽位记忆。
