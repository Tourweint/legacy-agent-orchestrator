# 2026-09-26 时间表达解析扩展（"几点到几点"不再被拒）

> **文档性质：变更记录（带日期）**。记录一次**体验缺陷修复**：用户说得出"明天下午两点到四点"，系统却回"我没看懂"。
> **依据**：[08-事实收集与命题校验方案](../设计方案/2026-09-24-系统设计方案/08-事实收集与命题校验方案.md) §7.1（三类归一化，第二类示例**明列**"一点到三点"）、§7.2（五条纪律）、§7.3（"请确认"）。
> **性质说明**：本次**不是放宽权限，也不是新增能力**——是**实现追平早已写下的规格**。规格里承诺过、提示词里承诺过、只差代码没做。

---

## 一、根因：系统"说得出、听不懂"

| # | 现象 | 根因（代码位置） | 性质 |
|---|---|---|---|
| 1 | 说"明天14点到16点" → 被追问"我没看懂" | `canonical/time.js` 的时段解析只认 `上午/下午/晚上` 三段词，精确区间一律抛"规则外表达" | **提示词与规格承诺 > 实现**：`intent-plans.yaml` 的槽位提示早就写着"如'上午八点到十点'"，08 章 §7.1 表格第二类也明列"一点到三点" |
| 2 | 用户原话里带冒号（"14:00到16:00"）→ 格式重试若干次后仍失败 | `understanding/schema.js` 的形态校验只看**长相**（`HH:mm` 即判"模型自己算的"），不问**这是不是用户说的** | **判据错**：原话片段被当成模型换算值 |
| 3 | 说"10月1日" → 被追问 | `resolveDatePhrase` 只支持 `今天/明天/后天/周X/下周三/YYYY-MM-DD`，中文显式日期不支持 | 同 #1：提示词里写着"10月1日" |
| 4 | 被追问时只有一句"请换个说法" | `chat-bridge.js` 追问话术 | 体验缺陷：把"猜系统能懂什么"的成本推给了用户 |

**一句话**：这三处都不是"权限太严"，而是**解析器的覆盖面小于它对用户承诺的覆盖面**。

---

## 二、改了什么

### 1. 时间解析：补齐精确钟点（`orchestrator/src/canonical/time.js`）

新增 `resolveTimePhrase(phrase, dateYmd, options)`，作为时段槽位的统一入口（`resolveRelativeRange` 改用它）。支持三类说法：

| 类别 | 例 | 结果 |
|---|---|---|
| 三段词（含口语同义词） | "下午" "早上" "傍晚" "夜里" | 取常量三段区间（8–12 / 13–17 / 18–22） |
| 精确区间 | "14点到16点" "下午两点到四点" "上午8点到10点" "两点半到四点" "14:00-16:00" "从14点至16点" | 该日的起止绝对时刻 |
| 单点（只说了开始） | "下午两点" "14:00" | **抛 `kind='range-incomplete'` → 追问用到几点**，不猜默认时长 |

钟点写法覆盖：阿拉伯/中文数字（含"两""十""十五""二十三"）、`点/时/:/：` 分隔符、`半` 与分钟（"4点半""14点30分"）。

**唯一的一条推断，且它本身是一条能写下来的规则**（第 08 章 §7.2 纪律 5 要求"写死口径"，故此处明写）：

> 钟点没带"上午/下午/晚上"时（"两点到四点"），**取唯一落在存量系统可预约窗口（常量 `time.legacyBookableWindow`，实测 07:00–22:30）内的解释**；两个解释都不在窗口内、或结束点不晚于开始点（跨自然日）→ 不猜，追问。

例："两点到四点" → 14:00–16:00（凌晨两点不在窗口）；"八点到十点" → 08:00–10:00（已在窗口内，不动）；"六点到八点" → 18:00–20:00（开始点消歧后结束点随之后移）；"22点到2点" → 拒绝（跨自然日，J4）。

**纪律未松**：仍是纯函数、不查网络、不猜；推算成功一律 `needsConfirm` 并给出推算依据（§7.3）；可行域（不跨自然日、开始在未来、落在窗口内）仍由 `checkLegacyTimeConstraints` 兜底。

### 2. 显式中文日期（同文件 `resolveDatePhrase`）

- 新增 `10月1日 / 9月30号 / 10月1`：**没说年份 → 取最近的一个将来**（今年该日期已过则取明年），因属推断故 `needsConfirm: true` 并在依据里写明；
- 新增"大后天"；
- 周几的说法扩展为 `周/星期/礼拜`（"下星期天"）。

### 3. 契约判据修正（`orchestrator/src/understanding/schema.js`）

时间形态的违规判据由"**形态命中**"改为"**形态命中 且 该片段不出现在用户原话里**"：

- 用户说"帮我订明天14:00到16:00" → 槽位里的 `14:00` 是**原话片段**，放行；
- 用户只说"明天下午"、槽位却变成 `14:00` → 那是**模型自己算的**，照旧拒绝。

调用方（`understanding.js`）把用户原话传入校验函数。**验收③的语义不变**（模型输出 ISO 时间仍被拒），只是不再误伤原话。

### 4. 追问话术（`orchestrator/src/orchestration/chat-bridge.js`）

- 听不懂时**列出系统真正支持的说法**（而不是"请换个说法"）：日期今天/明天/后天/周三/下周三/10月1日；时间上午/下午/晚上或"14点到16点"；
- 只说了开始时间 → 单独追问"要从几点用到几点"，并给例子；
- 缺时间槽位时的追问同步升级（"什么时间（'下午'或'14点到16点'都行）？"）。

### 5. 提示词与计划（让模型稳定地照抄，而不是自己拆解）

- `config/intent-plans.yaml`：6 个意图的时间槽位提示统一为"**照抄不要换算**：可以是'下午'，也可以是'14点到16点'这样的起止钟点"；
- `src/understanding/prompt.js`：新增纪律 2（起止时间整段原样写进一个槽位，❌ 不拆成两个槽位、❌ 不换算成 `14:00-16:00`），并加一组少样本示例；
- `config/glossary.yaml`：槽位短名 `时段` → `时间`（界面显示"时间=14点到16点"，比"时段=…"更贴切）。

## 四、仍然不支持的（如实登记，避免"提示词又超出实现"）

| 说法 | 现状 | 说明 |
|---|---|---|
| "中午" / "凌晨" | 追问 | 三段常量里没有这两段（C19 实测存量系统无节次表，三段是自有口径）；**不擅自新增口径**，要加须走变更记录 |
| "周末" "月底" "下周"（不带周几） | 追问 | 语义不唯一（周末=周六还是周日？），按纪律不猜 |
| "用两小时"（只说时长） | 追问 | 需要"开始时刻 + 时长"的合成规则，未定义；提示词已要求模型按原话存，落到追问 |
