# 2026-09-27 登录失败提示分流：别把后台故障说成"账号或密码不正确"

> **文档性质：变更记录。** 承接同日 [启动脚本自动拉起 Redis](2026-09-27-启动脚本自动拉起Redis.md)：那一条修掉了"登录不进去"的真因（Redis 缺席），这一条修掉它的**次生问题**——引擎把所有登录失败都翻译成"账号或密码不正确"，会把人引向错误的排查方向。

## 一、问题

`orchestrator/src/access/auth-endpoints.js` 原实现：

```js
const message = /被拒/.test(err.message) ? '账号或密码不正确' : `登录失败：${err.message}`
```

`/被拒/` 同时覆盖「存量系统明确说用户或密码错误」与「存量系统自身故障（依赖挂掉、响应超时）」两种毫不相干的情况——**底层是服务端故障，界面却指着正确密码说"你输错了"**。本次报障就是这样被误判成"账号密码不对"的。

## 二、实测依据（分流靠什么判别）

| 场景 | 存量系统真实响应 | 引擎侧表现 |
|---|---|---|
| 密码错 | `HTTP 200` + 业务码 **401**（`用户或密码错误`） | 业务码 401 |
| Redis 缺席（存量系统卡在自己的依赖上） | 请求**挂住不返回** | `transportKind = timeout`（实测，**不是**业务码 500） |

两条结论都来自真实链路实测，不是推断：① 用错密码直调 `8080/auth/login`，拿到 `{"code":401,...}`；② 停掉 Redis 后用**正确密码**走引擎登录，拿到传输超时。**判别依据因此是「业务码是否为 401」与「传输层 kind」，不是 HTTP 状态码**（这两种情况 HTTP 状态都是 200 或超时，分不出来）。

## 三、改动

| 文件 | 改动 |
|---|---|
| `src/contact/user-token-store.js` | `#callLegacy` 抛错时附带**结构化标记**：被拒→`err.httpStatus` / `err.businessCode`；传输失败→`err.transportKind`。错误消息文本不变（原有解析依赖不受影响） |
| `src/access/auth-endpoints.js` | 新增 `describeLoginFailure(err)`：业务码 401 → `账号或密码不正确`；业务码非 200 → `登录失败：存量系统返回异常（业务码 N）——这不是账号密码问题，请检查存量系统及其依赖（Redis / 数据库）是否正常`；`timeout` / `disconnect` / `unparseable` → 各自的如实说法；兜底才回落到原始消息 |
| `test/helpers/fake-legacy.js` | `makeGateway` 新增可选 `auth` 钩子（覆盖登录原始响应）；新增导出 `loginRejected(businessCode)` |
| `test/access.test.mjs` | 新增用例「登录失败分流」：业务码 401 说密码错、业务码 500 与传输超时**都不得**说成密码错 |

**为什么不解析错误消息文本**：文本改一个字就失效，是脆的；结构化标记由抛出方直接给出，判别与文案解耦。

**对外契约不变**：三种失败仍统一是 `401 + 4013`（不区分"账号不存在/密码错"，不给枚举探测的口子，见 [对外接口清单](../基线文档/对外接口清单.md) §10）——变的只有 `message`：契约管"能不能拿到信息"，文案管"人能不能看懂"。

## 六、未验证 / 回滚

- **未验证**：`disconnect`（连接被拒）与 `unparseable`（响应不可解析）两条分支只有单测覆盖，未做真实链路复现（构造条件成本高、收益低）；前端在长文案下的换行观感需人眼过一遍（文案变长是本改动的唯一界面影响）。
- **回滚**：把 `describeLoginFailure` 换回原一行即可；`user-token-store` 附带的结构化字段是纯增量，留着无副作用。
