# 文档驱动开发规范

> 核心思想：**架构是钢筋，代码是混凝土。钢筋先定好，混凝土随便浇。**
> 本规范适用于本仓库全部文档与代码的写作、AI 协作与验收。

---

## 一、文档体系

| 目录 | 用途 | 命名规则 |
|---|---|---|
| `docs/基线文档/` | 长期维护的重要文档，**不带日期** | `系统架构.md`、`接口文档.md`、`存量系统改造说明.md` |
| `docs/设计方案/` | 设计期过程文档，**带日期** | `YYYY-MM-DD-描述-设计方案.md` |
| `docs/变更记录/` | 落地期过程文档，**带日期** | `YYYY-MM-DD-变更描述.md` |
| `docs/实验/` | 验证层：实验设计与实测数据 | `实验设计与结果.md` |
| `docs/测试/` | 验收与演示：用例、演示脚本 | `系统测试用例.md` |
| `docs/研发规范/` | 协作规范，长期维护 | `项目开发规范.md`、`文档驱动开发规范.md` |

维护规则：

- 修改架构或流程时，**优先更新 `基线文档/`**
- 大型改造必须新增一条 `变更记录/`
- 避免在根目录直接堆放零散文档

## 二、五步闭环

```text
需求澄清 → 文档先行 → 代码实现 → 验证与回写 → 变更沉淀
```

1. **需求澄清**：明确目标、边界、影响范围
2. **文档先行**：先更新架构/接口/部署文档，确认路径、参数、返回结构
3. **代码实现**：按文档实现，保持结构一致
4. **验证与回写**：编译、测试、联调后回写文档结论（含"未能验证"的部分）
5. **变更沉淀**：大改动写入 `docs/变更记录/`

### 大改动判定标准（满足任一即写变更记录）

- 目录结构或模块边界调整
- 接口路径或返回结构变化
- 认证/权限模型变化
- 数据结构或存储变化
- 端口、部署流程、运行方式变化
- **对 `mock-legacy/` 的任何触碰**

### 变更记录最小内容

变更背景（为什么改）→ 核心设计决策（方案怎么选、用户确认了什么）→ 变更内容 → 影响范围 → 验证结果（含未验证项）→ 回滚建议。

## 三、总体设计原则

1. 高内聚、低耦合
2. 分层隔离、单向依赖
3. 单一职责：一个文件/模块只做一件事
4. 上层易变、下层稳定；越抽象越稳定，越具体越灵活
5. 能抽象绝不具体，能复用绝不重复
6. 变动频繁的层尽量薄，核心稳定的层尽量厚且在纯
7. 单文件行数 ≤ 500，接近 400 行开始拆，超 500 直接打回

## 四、编排引擎规范（Node.js / ESM）—— 以第 02 章为准

> **本节当前状态：已定规的实现规格。**
>
> 分层、依赖方向与各层职责由 `docs/设计方案/2026-09-24-系统设计方案/02-总体架构与分层方案.md` 给出；主方案 13 章已经架构一审、二审、**三审（2026-09-25）定稿，开工 Gate 全部关闭**，本节与各章同属实现依据。实现以第 13 章 9 阶段（0–8）为序。
>
> **两处不一致时的处理**：以方案各章为准，并立即回写本节。

### 4.1 分层与依赖方向（以第 02 章为权威）

```text
L1 接入层  →  L2 编排层  →  L4 判定层（事实聚合 + 命题校验）  →  L3 接触层  →  存量系统
                    └─→  L5 理解层（旁路，一件事至多问一次）
横切：证据层（可解释性）、配置数据、规范口径
```

**依赖方向强制单向**，禁止反向。第 02 章 §四 给出**三条结构性约束**，它们是本节最重要的内容：

| # | 约束 | 检查方式 |
|---|---|---|
| A | **唯一 HTTP 出口**：只有接触层能发起对存量系统的请求 | 全仓库搜索请求发起位置 |
| B | **唯一副作用出口**：有副作用的调用只能由编排层在提交态发出 | 提交态的入边是否恰好三条且各可追溯 |
| C | **唯一非确定性入口**：只有理解层能调用大模型 | 全仓库搜索模型客户端用法 |

> **这三条与"是否使用第三方库"无关**——约束约束的是**位置**，不是**工具**。

### 4.2 各层职责边界

| 层 | 允许做 | 禁止做 |
|---|---|---|
| **L1 接入层** | 接收请求、参数形状校验、调用编排层、统一响应、步骤事件推送 | 直接调用存量系统、写业务判断、自行推断执行步骤 |
| **L2 编排层** | 状态推进、分支、重试决策、降级决策、补偿决策 | 直接发 HTTP、直接调大模型、直接读配置数据文件 |
| **L3 接触层** | 协议适配、身份注入、调用、响应归一化、**三值判定**、故障注入点 | 承载业务语义判断（"能不能借"不归它）、决定是否重试 |
| **L4 判定层** | 驱动事实收集、命题判定、返回结论与依据 | 发起 HTTP（含只读）、把"事实不可得"当作"命题不成立" |
| **L5 理解层** | 文本 → 结构化意图、原话槽位摘取、置信度 | 决定调哪个接口、做时间换算、做实体消解、做业务判定、提示词含接口信息 |
| **横切 · 证据层** | 记录每步的输入、依据、结论；可导出、可复核 | 记录凭证；把模型原始输出写进证据链 |
| **横切 · 配置数据** | 注册表 / 意图计划 / 身份声明（**数据，不是逻辑**） | 在业务逻辑里硬编码接口路径、字段名、身份名、状态值 |

### 4.3 命名规范

| 类型 | 规范 | 示例 |
|---|---|---|
| 目录与文件 | 小写连字符 | `state-machine/`、`task-executor.js` |
| 构造函数/类 | PascalCase | `TaskExecutor` |
| 函数与变量 | camelCase | `resolveClassroomAvailability` |
| 常量 | `UPPER_SNAKE_CASE` | `TASK_STATUS` |
| 对外接口路径 | 小写连字符，`/api` 前缀 | `/api/chat` |

### 4.4 接口与错误

- 对外统一返回 `{ code, message, data }`
- **错误必须三分类**，不得一律当异常抛出：

| 类别 | 含义 | 处置 |
|---|---|---|
| `BUSINESS` | 业务失败（如时段被占） | 上报用户，不回滚已完成的只读步骤 |
| `TRANSIENT` | 可重试（超时、5xx、连接失败） | 按策略重试；**写操作重试前必须先查证** |
| `FATAL` | 需人工介入（补偿也失败） | 落到明确终态并如实上报，禁止静默吞掉 |

> **注意**：错误三分类与判定三值（`SUCCESS`/`FAILURE`/`UNKNOWN`）是**两组不同概念**——前者回答"接下来怎么办"，后者回答"成没成"。两者的映射见第 05 章 §九。

- 禁止硬编码接口地址、路径、字段名；一律从**配置数据**（接口注册表 / 意图计划 / 身份声明，见第 02 章 §八）读取。

## 五、前端规范（Vue 3 + Vite）

```text
frontend/src/
├── api/         # 接口封装（按模块分文件）
├── components/  # 通用组件
├── stores/      # 跨页面状态（Pinia）
├── views/       # 页面
├── styles/      # 全局样式与设计变量
└── utils/       # 通用工具
```

- 页面与组件**不得直接用 `fetch`/`axios`**，一律经 `api/`
- `stores/` 只放跨页面状态；页面局部状态留在页面内
- **Agent 的执行步骤必须可视化**（拆解、调用、重试、补偿都要能看到）——这是本作品的展示核心，不是可选装饰

## 六、核心不变量的文档化

比代码规范更重要的是**把关键规则写成文档化的不变量**，所有实现与 AI 生成都必须遵守（以 `docs/基线文档/存量系统改造说明.md` §六 为准）：

- **零侵入**：不修改 `mock-legacy/` 源码。任何例外必须先在此登记再实施
- **脏不造假**：异构必须来自存量系统的客观现状，不得人为编造
- **写入前必查**：写入类接口在重试前必须先走幂等查证路径
- **歧义不可猜**：409 之类的歧义信号既不能当成功也不能当失败，必须查证消解
- **补偿不保证成功**：补偿失败必须落到明确终态并上报，禁止静默吞掉
- **身份不外泄**：token 只在 `gateway/` 内部流转，不得进入引擎其他模块或前端
- **混沌默认撤防**：演示路径上不得存在默认开启的故障注入

## 七、AI 协作规范

### 7.1 让 AI 写代码前必须提供

1. **规范文件**（本文件与 `项目开发规范.md`）
2. **相关接口文档**（接口注册表 / 存量系统实测结论）
3. **相关数据结构定义**
4. **明确的功能范围**——只做什么，不做什么

### 7.2 AI 产出验收清单

- [ ] 文件行数 ≤ 500
- [ ] 分层正确（接入层无业务逻辑；**接触层之外无对存量系统的请求发起**）
- [ ] **三条结构性约束未被破坏**（唯一 HTTP 出口 / 唯一副作用出口 / 唯一非确定性入口，见 §4.1）
- [ ] 命名符合规范
- [ ] 无硬编码（接口路径、字段名、身份名、状态值均来自配置数据）
- [ ] 接口路径与返回结构与文档一致
- [ ] 错误已按 `BUSINESS`/`TRANSIENT`/`FATAL` 三分类；**"身份错"未与业务失败混为一类**
- [ ] 判定规则未绕过（没有在别处写"看 HTTP 状态码判成败"）
- [ ] 幂等守卫未绕过（没有"查证前直接重试"的路径）
- [ ] 关键业务逻辑（流转、查证、补偿）有注释说明「为什么」
- [ ] 未触碰 `mock-legacy/`
- [ ] 无凭据出现在代码、日志、证据链、界面中

### 7.3 禁止让 AI 做的事

- 一次性生成整个模块（必须按 **接触层 → 判定层 → 编排层 → 接入层 → 理解层** 逐步生成、逐步验证；顺序理由见第 13 章 §一）
- 修改架构或目录结构（架构变更必须人工讨论确认）
- **修改 `mock-legacy/` 的任何文件**
- 不经人工审核写核心业务逻辑（状态流转、幂等查证、补偿）
- 用"顺手修好"的名义抹平存量系统的不一致（见改造说明 §六）
- **把方案文档当逐字实现指令而跳过自检**——方案章节**不含代码**，规定的是契约与边界；三审（2026-09-25）后方案已是实现依据，但实现仍须逐阶段通过第 13 章验收清单与 8 条结构自检，不得用"方案写了"代替验证

## 八、harness 落地形态（AGENTS.md）

`AGENTS.md` 是文档体系的**入口索引**，供 AI 编码工具读取：

- 指向"先读哪些文档"
- 压缩核心规则：依赖方向、接口约定、不变量、验证命令、完成标准
- 明确边界：不编造约定、占位实现不是已实现、不写真实凭据、不碰 `mock-legacy/`
- 给出验证命令，让 AI 能自证

分层关系：**`docs/` 是权威内容源 → `AGENTS.md` 是给 AI 的入口索引 → `变更记录/` 是跨会话记忆**。

## 九、评估：好模型是否还需要这套东西

**需要，但角色应从"约束"转变为"项目记忆 + 验收标准"。**

- 通用工程惯例（分层、单一职责、500 行限制）大量存在于训练数据中，对强模型边际价值最低
- 但 **LLM 没有跨会话记忆，而项目有跨会话事实**：比如"存量系统不能改""409 是歧义信号""上一轮探针推翻了什么假设"——这些不可能从代码里读出来，必须外置
- 强模型的默认行为是"最短路径满足当前 prompt"，倾向在局部上下文里堆逻辑；规范把全局约束注入每个局部决策
- **"知道" ≠ "稳定做到"**：长任务、多文件改动会漂移，checklist 让它在每次改动后自检

**对本项目的具体调整**：
- 少写"禁止 X"，多写"X 的判定口径是 Y，验收时检查 Y"
- 重点写**业务不变量**与**验证命令**（这些模型无法自行推导）
- 记录**被推翻的假设**（如本次"重复提交会产生脏数据"），避免后续会话重蹈覆辙
