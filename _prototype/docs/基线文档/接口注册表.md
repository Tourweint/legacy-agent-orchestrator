# 接口注册表

> **一句话**：这是**边界的可执行载体**。存量系统的每个被纳管接口，在这里登记「它需要什么身份、有没有副作用、怎么查证、怎么撤销、依赖哪些前置事实」。
>
> **代码同源**：`orchestrator/src/registry/interfaces.js`。本文件是它的人读镜像；**两者不一致时以代码为准，并立即回写本文件**。
>
> **修改纪律**：本文件的任何改动都等同于**修改系统边界**，必须同步 `业务边界与责任域.md`，并在 `docs/变更记录/` 留一条记录。

---

## 一、为什么需要一张注册表

把接口地址散在代码里也能跑。之所以要收成一张表，是因为四件事**必须在调用发生之前**就有答案：

| 要回答的问题 | 对应不变量 | 不登记的后果 |
|---|---|---|
| 「这次该用谁的身份？」 | **I5 最小身份** | 调用方随手用 ADMIN，权限最小化失效；或用了 TEACHER 读后勤数据，静默 403 |
| 「调它之前必须先知道哪些事实？」 | **I1 事实齐备方可写入** | 漏查维修窗口——**缺陷静默发生**，脏数据落库 |
| 「超时了怎么判定到底成没成功？」 | **I3 结果必须唯一确定** | `UNKNOWN` 永远收敛不了，只能猜 |
| 「写错了怎么撤销？」 | **I6 副作用可补偿或显式登记不可补偿** | 半成功状态下系统停在中途，无人知晓 |

**核心判据**：**没有查证路径的接口，不得进入可编排清单**。理由见 `智能体设计.md` 判定原则 3——查证不了，就等于永远无法把 `UNKNOWN` 收敛成确定结论，那这条链路就不该被自动执行。

## 二、字段说明

| 字段 | 含义 | 约束 |
|---|---|---|
| `id` | 唯一标识，形如 `edu.classroom.detail` | 全局唯一 |
| `domain` | `edu`（教务域）/ `logi`（后勤域） | 决定需要哪个身份 |
| `method` / `path` | HTTP 方法与路径模板 | **真实路径无 `/api` 前缀**（上游文档写错，见改造说明） |
| `requiredRole` | 调用所需最小身份 | `null` 表示不需要身份（如登录） |
| `sideEffect` | 是否产生副作用（写入） | `true` 时下列四项必填 |
| `keyTemplate` | **幂等业务键**模板 | 有副作用时必填；补偿动作可豁免（重复撤销天然幂等） |
| `verifyBy` | **查证接口 ID** —— 结果不确定时用于收敛 | 有副作用时必填 |
| `compensate` | **补偿接口 ID** —— 失败时撤销自身写入 | 与 `uncompensable` 二选一 |
| `uncompensable` | `true` = 副作用**不可撤销**，此处显式登记 | 不变量 I6 原文即「必须被补偿**或显式登记为不可补偿**」，本字段就是那个"显式登记" |
| `orchestrable` | `false` = 不参与自动编排（仅演示/工具接口） | 默认视为 `true` |
| `preconditions` | 依赖的命题 ID | 引用 `validator/propositions.js` |
| `adapter` | 响应适配器：`edu` / `logi` / `raw` | 决定用哪套三值判定规则 |
| `notes` | 实测注意事项 | **每一条都是实测结论，不是文档推断** |

## 四、身份分布 —— 跨权限域的硬证据

```
ADMIN   ── 6  logi.maintenance.list / logi.reservation.list / logi.maintenance.create
TEACHER ── 5  edu.classroom.* / edu.reservation.classroom.create / edu.reservation.mine / edu.reservation.cancel
STUDENT ── 1  edu.reservation.seat.create
（无）  ── 1  auth.login
```

**这张表就是本项目立论的核心证据**：

- 「教室能不能借」需要三份事实：**教室状态**（教务）、**时段占用**（教务）、**维修窗口**（后勤）。
- 前两份用 TEACHER 身份拿得到，**第三份用 TEACHER 身份拿不到**（实测 HTTP 403，过滤器层拒绝）。
- 于是「一次简单的借教室」**在权限维度上就不可能由单一身份完成**。

→ 跨身份编排不是"我们想秀技术"，而是**不换身份就办不成**。详见 `业务边界与责任域.md` 决策点 P3。

## 五、分域明细与实测备注

### 5.1 教务域 · 事实查询

**`edu.classroom.detail`** — 查教室详情（含容量、状态）
- `status` 是教室可用性的**第三个来源**（前两个是预约占用与维修窗口）。
- 也是把「数智楼222」这种人类可读名称解析成真实 `id` 的入口。

**`edu.classroom.available`** — 按楼栋/容量筛选可用教室
- ⚠️ 参数只有 `building` / `min_capacity`，**没有时间字段** —— 它答不了"这个时段是否可用"。
- ⚠️ **`min_capacity` 是必填参数**：实测缺失时返回**业务码 500「系统内部错误」**，而非 400。参数校验失败被表达成了服务端错误。
  → 调用方必须始终显式传值（本项目统一传 `0` 表示不限容量）。
- 结论：本接口只能用于「按条件挑教室」（降级换教室时用），**不能用于时段冲突判定**。

**`edu.classroom.seats`** — 查教室座位布局
- 返回 `seatVOS` 数组，元素含 `id` / `seatNumber` / `status`。

**`edu.classroom.reservedSeats`** — 查某时段已被占用的座位
- ⚠️ **读写粒度不一致**：返回的是**座位 ID 数组**，而写操作是**整间教室粒度**。
- 入参 `start_time` / `end_time` 为 `OffsetDateTime`（带 `Z`）。
- **★ 本项目最重要的一处语义陷阱**（已核实到源码 `ReservationServiceImpl:182-188`）：

  ```java
  if (整间教室预约冲突 || 维修窗口冲突) {
      return 该教室的全部座位;     // ← 两种完全不同的原因，合并成同一个返回值
  }
  ```

  → 「整间教室被预约」与「教室在维修中」**返回结果字节级相同**，调用方无法区分。
  → 而两者的应对方式完全不同：**被订了**可以换时段/换教室；**在维修**则该教室一段时间内都不可用。
  → **要区分，只能换 ADMIN 身份去后勤域查维修窗口。**

  **这就是「跨权限域聚合」成为技术必然、而非设计偏好的那行代码。**
- 判定口径：该时段占用座位数 > 0 → 视为该教室不可用。**口径由 `validator/propositions.js` 统一，请勿在别处另行判断。**

### 5.2 后勤域 · 事实查询

**`logi.maintenance.list`** — 查教室维修窗口
- ⚠️ **权限实测**：仅 ADMIN 可访问，**TEACHER 与 STUDENT 均被拒**（HTTP 403，过滤器层）。
- 种子数据里两条维护窗口**均为 `CANCELLED`**；演示"教室在检修"需现场用 ADMIN 接口创建。
- 判定口径：`status` 不在失效集合内、且时段与申请时段重叠 → 该教室不可用。
  失效集合采用**排除法**（`CANCELLED/CANCELED/FINISHED/EXPIRED/CLOSED`），**保守优先**——漏放一个"其实在维修"的教室会写入脏数据；多拦一次，用户只是被提示换时段。
- ⚠️ **命名异构**：出参是 camelCase（`resourceType`/`resourceId`/`startTime`），与入参的 snake_case 不一致。

### 5.3 教务域 · 写入

**`edu.reservation.classroom.create`** — 提交整间教室预约（**主轴**）
- 前置命题：`P-CLASSROOM-EXISTS`、`P-CLASSROOM-ENABLED`、`P-NOT-ALREADY-MINE`、`P-SLOT-FREE`、`P-NOT-UNDER-MAINTENANCE`
- ⚠️ 冲突时返回 **HTTP 200 + body `code=409`** —— **只看 HTTP 状态码会误判为成功**。
- ⚠️ **409 是歧义信号**：无法区分「你自己刚才已成功」与「别人占了」→ **既不能当成功也不能当失败，必须查证**。
- ⚠️ ADMIN 身份调用返回 **HTTP 200 + code=403**（方法层拒绝），与过滤器层的 HTTP 403 表达不一致。
- 入参 `classroom_id` / `start_time` / `end_time` / `reason`，为 snake_case。
- 实测**无幂等键、无唯一约束**；重复提交靠"查冲突"拦截，并发下仍可能双双通过 → **幂等由编排层负责**。

**`edu.reservation.seat.create`** — 提交座位预约
- 前置命题：`P-SEAT-EXISTS`、`P-SEAT-SLOT-FREE`
- 入参 `seat_id`（snake），与教室预约风格一致，但与 admin 系列接口的 camelCase 不一致。
- 本项目编排主轴是**教室级**，本接口仅作为「粒度差异」的对照存在。

### 5.4 查证与补偿

**`edu.reservation.mine`** — 查当前身份的预约列表
- ⚠️ **查证能力不足**：返回当前身份的**全量**预约，需在内存中按 (教室, 时段) 比对。
- ⚠️ 由于**身份决定可见范围**，用它查证时**必须使用发起写入时的同一身份**。
- 用途：判定 `P-NOT-ALREADY-MINE`（是不是我自己提交的）。

**`edu.reservation.cancel`** — 撤销预约（补偿动作）
- ⚠️ **补偿不保证成功**：若记录已进入不可撤销状态，撤销会失败。
- 失败时必须**显式登记为"不可补偿"**，落到 `UNRESOLVED` 终态并上报，**不得静默吞掉**（不变量 I6）。
- `keyTemplate` 为 `null` 属**豁免**：重复撤销的影响天然幂等（记录已不存在），无需业务键。
- ⚠️ 补偿动作**不可能出现在可编排写接口清单里作为主操作**，它只能由 `COMPENSATING` 状态发出。

### 5.5 后勤域 · 写证支点与演示工具

**`logi.reservation.list`** — 管理端查预约（**跨身份可见，幂等机制的支点**）
- ⚠️ `keyword` 参数语义模糊：实测 **`keyword=4` 会命中 `resourceId=6`** 的记录（疑似多字段模糊匹配），**不可用于精确过滤**。
- ✅ **不带参数时返回全量列表**（实测 87 条，纯数组，非分页对象）—— 这是可靠的用法。
- ⚠️ 无分页参数，数据量增大后无法保证全量 → 编排层对此设了安全阈值（见 `state-machine/verify.js` 的 `FULL_LIST_SAFETY_LIMIT = 500`）。
- ⚠️ **权限实测**：ADMIN 可访问；TEACHER 与 STUDENT 均被拒（HTTP 403）。
- **它的核心价值在于"跨身份可见"**：Agent 提交时用 TEACHER、查证时用 ADMIN —— 这是幂等收敛能成立的关键支点。

**`logi.maintenance.create`** — 创建维修窗口（演示工具）
- ⚠️ **同一请求体内命名混用**：`resourceType`（camel）+ `start_time`（snake）—— 命名异构的实证。
- `uncompensable: true`：存量系统只提供"创建/取消"，**没有按 ID 删除**，故显式登记为不可补偿。
- `orchestrable: false`：**不进入自动编排链路**，由人工/脚本调用。
- 用途：演示中"现场把教室置为检修中"，从而触发**自动降级换教室**分支。

## 六、注册表自检（`auditRegistry()`）

`orchestrator/src/registry/index.js` 的 `selfCheck()` 在服务启动时自动执行，任一项不过就打屏告警。规则：

| 检查 | 违反时提示 |
|---|---|
| 有副作用必须声明 `verifyBy` | `有副作用但未声明 verifyBy（无法收敛 UNKNOWN）` |
| 有副作用必须「可补偿 **或** 显式登记不可补偿」 | `违反不变量 I6` |
| `compensate` / `verifyBy` 必须指向**已登记**的接口 | `指向未登记的接口 xxx` |
| 只读接口应有身份要求，或属于已知豁免（`auth.login`） | `登记信息不完整（无副作用 / 无前置命题 / 无所需身份）` |

**当前状态：`{ ok: true, problems: [] }`（12 条接口全部合规）。**

> 这套自检在本轮**首次运行时揪出了 3 个真实问题**（2 个写接口未声明补偿语义、1 个状态机死状态误判）。它是有用的，不是装饰。
